## 2. 대신 쓴 것 — **자체 제작 자리표시 덱 시트**

`deck/site_plan.render_deck_sheet_html` 이 만드는, **카드 그림이 하나도 없는**
덱 시트다. 각 칸에는 카드 **이름과 패스코드만** 글자로 찍힌다.

* 🔴 **공식 앱의 내보내기 이미지가 아니고**, 그렇게 부르지 않는다. 시트의
  아래 줄에 `自作プレースホルダー画像（公式アプリの出力ではありません／
  カード画像は含みません）` 이라고 적혀 있다.
* 🔴 다른 카드의 그림을 그 카드인 것처럼 쓰지 않았다 — **그림 자체가 없다.**
* 권리 문제가 없다: 이 저장소가 만든 글자 이미지다.

격자 치수는 사이트의 해석기가 카드를 제대로 잘라내도록 맞췄다 (폭 1169 ·
한 줄 10장 · 카드 116×169 · 타이틀 82px · 헤더 띠 44px). 이 숫자는 공개
리플레이 페이지에 표시된 덱 이미지의 **격자 간격을 재서** 얻었다 (이미지
자체는 쓰지 않았다).

### 입력 결과 확인 — "들어갔다" 로 끝내지 않았다

| 확인 항목 | 결과 |
| --- | --- |
| 자동 검출 | ❌ 틀린다 (`Main Deck: 7 cards (1 rows)`) → **수동 매수 보정** 사용 |
| 메인 장수 | ✅ `Deck (40)` |
| 엑스트라 장수 | ✅ `Extra Deck (6)` |
| 메인/엑스트라 구분 | ✅ 엑스트라 6장이 엑스트라 칸으로 들어갔다 |
| 잘림 | ✅ 잘라낸 카드가 114×167 (비율 0.683 = 카드 비율) |
| 카드 식별 | ❌ **전부 미식별** (`Unrecognized`) — 그림이 없으니 당연하다. 카드 이름은 시트에 찍혀 있어 판에서 읽을 수 있다 |

## 3. 조작 계획 — 엔진 기록에서 나온다

`deck/site_plan.build_site_plan(record)` 가 실행 기록을 사이트 조작 목록으로
바꾼다. 🔴 **정식 입력은 실행 기록이고**, 사람이 읽으라고 쓴 설명문
(`reason` · `resolution_choices`) 을 해석해서 조작을 정하지 않는다.

| 기록 | 조작 | 근거(`basis`) |
| --- | --- | --- |
| `monster_summoned` | 끌어 놓기 (칸 번호대로) | `engine:event#N.monster_summoned` |
| `zone_moved` · `card_drawn` | 끌어 놓기 (존으로) | `engine:event#N.zone_moved` |
| 걸음 `activate_effect` | 우클릭 → Activate Effect | `engine:step#N.kind` + `event#M.source` |
| 걸음의 `targets` | 우클릭 → Target | `engine:step#N.targets` |
| `special_summon_limited` · `zone_shuffled` | **조작 없음** | `plan["unsupported"]` 에 적는다 |

* **개체를 자리로 묶는다.** 시작 패 5장이 `main-0`…`main-4`, 나머지 덱이
  `main-5` 이후, 엑스트라가 `extra-0` 이후다. 그래서 같은 이름의 카드가
  여러 장이어도 섞이지 않고, 사이트의 「왼쪽 위 5장을 패로」 가 기록의 시작
  패와 정확히 같다.
* **공유 엑스트라 몬스터 존**: 엔진의 좌석 0 `EMZONE` → 사이트의
  `Extra Monster Zone1`, 좌석 1 → `Extra Monster Zone2`. 같은 물리적 자리를
  양쪽에 중복 생성하지 않는다.
* 🔴 **엔진 행동 6 · 엔진 사건 8 · 사이트 조작 16** 은 서로 다른 수다.
  계획의 `counts` 가 셋을 따로 센다.

이번 경로에서 **사이트에 대응 조작이 없는 사건** (조용히 빠뜨리지 않고
실행 전에 찍는다):

```
사건 #1 의 zone_shuffled: 덱 섞기 — 사이트의 덱은 순서를 따로 다루지 않습니다
사건 #3 의 special_summon_limited: 특수 소환 제한 등록 — 사이트에 그 표현이 없습니다
사건 #3 의 zone_shuffled: …
사건 #6 의 special_summon_limited: …
```

## 4. 사이트 조작 — 실측

`scripts/duel_simulator_driver.js` 가 **사람이 쓰는 UI 그대로** 조작한다
(끌어 놓기 · 우클릭 메뉴 · 버튼). 내부 엔드포인트를 부르지 않고 번들을
뜯어보지 않는다. 조작마다 화면의 History 줄을 읽어 **도착지**를 확인하고,
어긋나면 **그 자리에서 멈춘다** (확인 없이 다시 시도해 두 번 움직이는 일을
만들지 않는다).

좌표 의존 범위: 존은 `data-droppable` 요소의 **화면 좌표**로 찾는다
(사이트가 존 이름을 DOM 에 적지 않는다). 카드는 좌표가 아니라
`data-card-id`(`main-11-…` 처럼 이동해도 바뀌지 않는 식별자) 로 찾는다.
그래서 레이아웃이 바뀌면 존 찾기가 먼저 깨지고, 그때는 History 확인이
실패해 멈춘다.

### 시작 상태 (기록 시작 직전)

```
Hand 5 · Deck 35 · Extra Deck 6 · Grave 0 · Banish 0 · Free 0
```

사이트 쪽에 표현할 수 없는 것: **상대 정보는 아무것도 넣지 않았다** (상대
덱·패·필드). 엔진 기록의 좌석 1 은 덱 40장뿐이고 이번 전개와 무관하므로,
없는 상대 정보를 검증된 것처럼 다루지 않는다. 특수 소환 제한도 사이트에
표현이 없다 (§3 의 `unsupported`).

## 6. 다시 실행하는 법

```bash
# 계획과 덱 시트만 (브라우저를 열지 않는다)
python3 -m scripts.duel_simulator_share --line orcust-skeleton-longirsu --plan-only

# 사이트에서 실제로 조작하고 확인까지 (공유하지 않는다)
python3 -m scripts.duel_simulator_share --line orcust-skeleton-longirsu

# 🔴 공유 URL 까지 — 되돌릴 수 없는 공개다
python3 -m scripts.duel_simulator_share --line orcust-skeleton-longirsu \
    --share --title "…"

# 이미 있는 기록으로
python3 -m scripts.duel_simulator_share --json combo-replay.json
```

| | |
| --- | --- |
| 필요한 환경 | 이 컨테이너의 Chromium + Node Playwright (추가 설치 없음) |
| 바깥 통신 | `duel-simulator.miyauchidp.dev` 하나 |
| 입력 | 고정 경로 이름 또는 `engine-replay/*` JSON |
| 출력 | `<작업디렉터리>/plan.json` · `deck-sheet.png` · `shot-*.png` · `video/` · `result.json` (+ `--share` 면 `share_url`) |
| 걸리는 시간 | 실측 1~2분 |
| 실패했을 때 | `result.json` 의 `stopped_at` · `stopped_reason` 에 **어느 조작에서 무엇이 달랐는지** 남는다. 기록을 끝내지 않고 공유도 하지 않는다 |

🔴 산출물은 `docs/viewer/local/` 아래라 **커밋되지 않는다**.

## 7. 디스코드 연결

`/share-replay` 슬래시 명령 (`app/discord_bot.py` · `app/site_share.py`).

```
/share-replay hand:<패> recipe:<레시피> [line:<경로>] [title:<제목>]
```

* **봇의 응답 처리를 막지 않는다**: `defer()` 로 먼저 응답을 열고, 브라우저
  조작은 `asyncio.to_thread` 로 보낸다 (`/combo` 와 같은 구조).
* **동시 요청이 브라우저 상태를 섞지 않는다**: 한 칸짜리 자물쇠로 한 번에
  하나만 돌고, 돌고 있으면 기다리지 않고 「바쁘다」 로 답한다.
* **URL 이 실제로 만들어졌을 때만** 성공 링크를 적는다.
* 실패하면 짧은 이유와 함께 `combo-replay.html` 로 계속 재생할 수 있다고
  적는다.
* **외부 공유가 일어나는 조작임을 입구에서 먼저 알린다** (대기 중에 보이게
  첫 메시지로 보낸다).

🔴 **디스코드 실제 전송은 확인하지 않았다.** 봇 토큰이 없는 자리라 응답
생성 함수와 명령 등록만 시험으로 확인했고, 그것을 디스코드 실사용 확인이라고
부르지 않는다.

| 체인 번호·해결 구간 편집 | ❌ 이번 범위 밖 |

### 공식 Neuron 내보내기 이미지가 필요한 경우

**실제 카드 그림이 있는 판**으로 만들려면 아래 한 장이 필요하다.

* 필요한 파일: 遊戯王ニューロン(공식 앱)의 「デッキ画像を保存」 으로 내보낸
  **이 레시피 그대로의 덱 이미지 1장** (PNG/JPG).
* 왜 필요한가: 사이트는 **올린 덱 이미지에서 잘라낸 그림만** 판에 올린다.
  카드 검색으로 카드를 추가할 수 없고, 식별을 고쳐도 그림은 바뀌지 않는다
  (가이드라인 4절). 그리고 이 저장소가 가진 카드 그림은 외부에 올려 공개할
  권한이 없다 (§1).
* 받으면 바뀌는 것: `scripts/duel_simulator_share.py` 에 그 파일을 덱
  시트 대신 넣는 한 줄만 추가하면 된다. 조작·확인·공유 경로는 **지금 그대로**
  쓴다 (이미 끝까지 돌았다).
* 덱 순서 주의: 사이트의 「왼쪽 위 5장」 이 시작 패가 되도록, 내보낼 때
  `69811710 · 703897 · 2930675 · 12989604 · 61654098` 이 맨 앞 5장이어야
  한다. 아니면 계획의 `setup` 이 가리키는 자리를 바꿔야 한다.

운영자에게는 연락하지 않았다.

## 9.1 오류 ① — 최종 검증이 느슨했다

**원인.** `scripts/duel_simulator_driver.js` 의 최종 대조가

* 묘지 · 제외 · 패 · 덱은 **장수만** 비교했고,
* 필드 카드는 `whereIs` 에 **값이 있는지만** 봤다.

그래서 묘지와 제외의 카드가 **서로 바뀌어도** (양쪽 다 2장) 통과했고,
롱기르수가 엑스트라 몬스터 존 **2번 칸**에 있어도 통과했다. 애초에 계획의
`expect_final` 에 **최종 칸 번호가 없었다** — 기록의 `final.zones` 는 존
구성만 담고 칸 번호를 담지 않았기 때문이다.

**고친 것.**

| 자리 | 무엇을 했나 |
| --- | --- |
| `deck/opening.py` | 마지막 판의 **칸 번호**를 값으로 찍는다 (`final_slots`). 칸이 있는 존만 읽는다 — 묘지처럼 칸이 없는 자리는 나오지 않는다 |
| `deck/replay_export.py` | 형식 `/4` → `/5`. `final.slots` 를 더했다. 🔴 **더한 것이 전부**이고 옛 형식도 그대로 읽는다 |
| `deck/site_plan.py` | `expect_final` 이 **사이트의 19개 칸 전부**에 대해 카드 자리의 집합을 적는다. 칸 번호가 기록에 없으면 **지어내지 않고** `unsupported` 에 남긴다 |
| `scripts/duel_simulator_verify.js` | 판정부를 순수 함수로 분리 (브라우저 없이 시험할 수 있게) |
| `scripts/duel_simulator_driver.js` | 아래 여섯 가지를 본다 |

이제 보는 것:

1. **존마다 카드 개체의 집합**을 맞춘다 — 빠진 카드(`missing`) 와
   **예상 밖 카드**(`unexpected`) 를 둘 다 센다.
2. **필드는 칸까지** 맞춘다 (`Monster Zone2` · `Extra Monster Zone1` …).
3. **빈 존은 실제로 비어 있으면 통과**한다 (14개 칸이 그렇다).
4. 크기가 0이거나 어느 칸에도 안 들어가거나 같은 자리가 두 번 나오면
   `problems` 에 남고 **전체가 실패**다 — 읽을 수 없는 상태를 성공으로
   치지 않는다.
5. 좌표로 읽은 수와 **화면의 장수 표시**를 교차 확인한다 (`cross_check`).
   좌표만 믿지 않는다.
6. 검증에 실패하면 **공유하지 않고** 차이를 그대로 남긴다.

> ⚠ **§10.3 에 정정이 있습니다** — 아래 문단은 썸네일(그림) 일치를 개체
> 확정의 근거처럼 적었습니다. 실제 덱 이미지에서는 같은 카드가 여러 장인
> 것이 정상이라 그림만으로는 가릴 수 없고, 지금은 **안정 ID**가 1차
> 근거입니다.

**조작 하나하나도 개체까지 확인한다.** 실측으로 알아낸 사실 하나를 쓴다 —
조작 이력(History) 각 줄의 **썸네일 `src` 가 판 위 그 카드의 `src` 와
바이트 단위로 같다**. 그래서 이동마다

* 이력이 **정확히 한 줄** 늘었는가,
* 그 줄의 썸네일이 **이 카드**의 것인가,
* 카드가 **정말 그 칸에** 있는가 (좌표로 다시 읽어서)

를 함께 본다. 발동 · 대상도 **이력이 늘었다는 사실만으로 통과시키지
않는다**: 줄의 종류(`Activate Effect · ` / `Target · `) 와 줄에 적힌 칸이
카드가 실제로 있는 칸과 같아야 하고, 썸네일이 이 카드의 것이어야 한다.
같은 그림이 둘 이상이면 **모호하다고 적는다** — 맞았다고 하지 않는다
(이번 덱 시트에서는 46장 모두 그림이 달라 모호한 경우가 없었다).

## 9.2 오류 ② — 실패한 요청이 과거 공유 결과를 재사용했다

**원인.** `app/site_share.py` 가 **고정 작업 폴더**를 쓰고
`deck/site_session.py` 가 거기 남아 있는 `result.json` 을 읽었다. 새 실행이
**결과를 쓰기 전에** 죽으면 (실행 실패 · 시간 초과 · 즉시 종료) 지난번의
성공 `share_url` 이 이번 요청의 성공으로 돌아왔다.

**고친 것.**

* 요청마다 **실행 ID** 를 만들고 (`new_run_id`),
  `<기준 폴더>/<시각>-<실행 ID>/` 라는 **빈 폴더**에서 돌린다.
* 계획(`plan.json`) 과 결과(`result.json`) 에 그 ID 를 넣고, 돌아온
  결과의 ID 가 **이번 요청의 것인지** 확인한다.
* 실패를 **뭉치지 않는다** — `RunStatus` 가 가른다:
  `launch_failed` · `timeout` · `missing_result` · `bad_json` ·
  `run_id_mismatch` · `stopped` · `ok`.
* **공유 성공은 URL 하나로 판정하지 않는다.** 이번 실행이 끝까지 갔고
  (`ok`), 조작이 **전부** 확인됐고, 최종 검증을 통과했고, 그러고도 URL 이
  있을 때만 성공이다 (`SiteRunResult.shared`).
* 시간이 초과되면 **프로세스 그룹 전체**를 끝낸다 — `node` 만 죽이면
  크로뮴이 남아 다음 요청과 겹친다.
* 공유 뒤 URL 을 읽지 못하면 **자동으로 다시 누르지 않는다** (두 번
  공개할 수 있다). 그 사실을 결과에 적는다.
* 지난 실행 산출물은 **자기 폴더에 그대로 남는다** — 지우지 않는다.
  6-AX 의 산출물은 `00-6AX-first-share/` 로 옮겨 두었다.

## 9.3 EDOPro 이미지 출처 — **연결하지 않았다**

조사한 것 (모두 원문 확인):

| 확인한 것 | 결과 |
| --- | --- |
| `gframe/image_downloader.cpp` | URL **템플릿 문자열이 코드에 없다**. `SetPayloadAndUrl(epro::format(src.url, code), fp)` 로, `src.url` 은 실행 중에 등록된 값이다 |
| `gframe/image_downloader.h` | `struct PicSource { std::string url; imgType type; }` · `AddDownloadResource(PicSource)` |
| 등록 지점 `gframe/data_handler.cpp` | `AddDownloadResource({ DEFAULT_PIC_URL, imgType::ART })` — `DEFAULT_PIC_URL` 은 **빌드 시 정의되는 매크로** |
| `premake5.lua` · `travis/build.sh` · `.github/workflows/edopro.yml` | `--pics="$PICS_URL"` 이고, `PICS_URL: ${{ secrets.PICS_URL }}` — **GitHub Actions 시크릿**이다 |
| `gframe/game_config.cpp` | 실행 중에는 `./config/configs.json` · `user_configs.json` 의 `urls` 배열을 읽는다 |
| 저장소의 `config/` | `.gitkeep` 하나뿐 — **configs.json 을 배포하지 않는다** |
| 저장소에 카드 그림 | **없다** (최상위에 `pics` 폴더가 없다) |
| 핫링크 허용 안내 | **찾지 못했다** (README · 위키에 이미지 출처나 직접 참조에 관한 문구가 없다) |

🔴 **결론: 실제 이미지 출처의 호스트명이 공개돼 있지 않다.** 코드에
URL 템플릿이 쓰인다는 사실과, 배포본이 실제로 쓰는 출처는 다른 것이고,
후자는 빌드 시크릿과 배포본의 설정 파일 안에 있다. 그래서

* 주소 형식과 출처를 **확정할 수 없고**,
* 그 출처의 제공자가 외부 뷰어의 **직접 참조를 허용하는지도 확인할 수
  없다**.

확인할 수 없는 출처는 연결하지 않는다는 원칙대로, **이미지 URL 참조는
이번에 구현하지 않았다.** 추측한 호스트명을 코드에 넣지 않았고, 기존
YGOPRODeck 주소를 EDOPro 출처라고 바꿔 부르지도 않았다.

참고로 지금 쓰는 출처(YGOPRODeck)는 **직접 참조를 명시적으로 금지**한다
(`Do not continually hotlink images directly from this site`,
`docs/replay-viewer.md` §3). 그래서 그쪽도 URL 참조로 바꿀 수 없다.

**이것이 풀리려면 필요한 것 하나.** 사용자의 PC 에 설치된 EDOPro 의
`config/configs.json` (또는 `user_configs.json`) 안 `urls` 배열. 거기에
실제 호스트가 적혀 있다. 그 값을 알려 주면 그 호스트의 이용 조건을 확인한
뒤에 연결 여부를 판단할 수 있다. 🔴 **값을 보기 전에 만들지 않는다.**

## 9.4 정정 — 안내문이 정한 것과 구현자가 판단한 것

6-AX 보고서 §1 은 "합성 덱 이미지를 올리는 것은 가이드라인 5절이 이름을
붙여 금지한 바로 그 행위다" 라고 적었다. **그 단정을 정정한다.**

* 안내문이 **실제로 적은 것**: ① 4절은 기대 입력을 "공식 앱에서 출력한
  덱 이미지, 또는 PC판 마스터듀얼 화면 취득" 으로 **想定(상정)** 한다고
  적는다 — "그것만 허용한다" 고 적지 않는다. ② 5절은 "**이용할 권한이
  없는** 이미지를 읽어 공유URL·리플레이로 공개하는 행위" 를 금지한다.
* **구현자의 판단**: 이 저장소가 가진 카드 그림(YGOPRODeck 경유 코나미
  저작물)에 대해 우리가 재배포 권한을 갖지 않는다고 보았고, 그래서 그
  그림을 합성해 올리지 않았다.

따라서 정확히는 — **"합성 이미지는 무조건 금지" 가 아니고, "공식 이미지만
가능" 도 아니다.** 금지되는 것은 **권한이 없는 이미지를 올려 공개하는
것**이고, 권한이 있는 이미지(예: 이번에 쓴 **자체 제작 자리표시 시트** —
그것도 합성 이미지다) 는 그 조항에 걸리지 않는다. 새로운 허용 여부를
여기서 단정하지도 않는다: 어떤 이미지의 권한 유무는 그 이미지마다 따로
판단할 일이다.

## 9.5 자체 뷰어와 외부 사이트의 **그림 지원 상태는 다르다**

| | 카드 그림 | 어떻게 |
| --- | --- | --- |
| **갈라테아 자체 뷰어** (`docs/replay-viewer.md`) | ✅ 실제 카드 그림 | 한 번 받아 `data/cache/card_images/` 에 보관하고 HTML 안에 `data:` 로 담는다 (6-AW) |
| **외부 Duel Simulator** | ❌ **글자 대체 이미지** | 자체 제작 자리표시 덱 시트 — 카드 이름과 패스코드만 글자로 찍힌다 |

🔴 둘을 섞어 말하지 않는다. 자체 뷰어에 그림이 보인다고 해서 외부 사이트의
리플레이에 카드 그림이 연결된 것이 아니다. 공유 리플레이를 열면 **글자가
찍힌 자리표시 카드**가 보인다 (§5 의 화면이 그대로다).

**남은 과제**: 외부 사이트에 실제 카드 그림이 있는 판을 올리려면 공식
Neuron 내보내기 이미지 한 장이 필요하다 (§8 의 설명 그대로, 바뀐 것이
없다). 이미지 URL 참조가 생기더라도 그것과는 **별개 문제**다 — 그 사이트는
업로드된 이미지에서 카드를 잘라 쓰지, 바깥 URL 을 참조하지 않는다.

## 9.6 윈도우 실행 준비

🔴 **이 컨테이너에 깔려 있다는 이유로 사용자 PC 에도 있다고 가정하지
않는다.** `node` · `playwright` · 크로뮴은 따로 준비해야 한다.

* `package.json` 에 `playwright` 버전을 **고정**했다 (`1.56.1`). 그래서
  `npm install` 이 같은 것을 받는다. `node_modules/` 와
  `package-lock.json` 은 커밋하지 않는다.
* `scripts/check_browser.js` 가 node · playwright · 크로뮴 **실행 파일의

* `deck/site_session.preflight()` 가 그것을 부르고, CLI 는 **브라우저를
  띄우기 전에** 확인해 없으면 설치 명령을 적고 멈춘다 (종료 코드 2).
  디스코드 입구도 같은 확인을 먼저 해서 1~2분 기다리게 하지 않는다.

### 경로와 글자

* 경로는 **인자로** 넘어간다 (셸을 거치지 않는다). 그래서 공백이나 한글이
  들어 있어도 따옴표 처리를 신경 쓸 필요가 없다. 다만 PowerShell 에서
  `--out` 에 공백이 있는 경로를 줄 때는 그 인자만 `"..."` 로 감싼다.
* 모든 파일을 UTF-8 로 읽고 쓴다 (`plan.json` · `result.json` ·
  `deck-sheet.html`). 콘솔 출력만 윈도우 코드 페이지의 영향을 받으므로
  위 1번 줄을 권한다.

### 🔴 확인하지 못한 것

**실제 윈도우에서 돌려 보지 않았다.** 이 컨테이너는 리눅스다. 위 절차는
코드와 공개 문서에서 나온 것이고, 다음은 **미확인**이다:

* `npm install` · `npx playwright install chromium` 이 그 PC 에서 성공하는지
* 윈도우의 크로뮴 경로를 `playwright` 가 바로 찾는지
* PowerShell 에서 한국어 출력이 깨지지 않는지 (`PYTHONUTF8` 로 충분한지)
* 공백·한글이 든 경로에서 Node 가 파일을 쓰는지
* 시간 초과 시 프로세스 그룹 종료 (`CREATE_NEW_PROCESS_GROUP` 경로) 가
  윈도우에서 크로뮴까지 정리하는지 — 리눅스 경로만 실측했다

# 10. Neuron 덱 이미지 등록과 세 오류 수정 (Phase 6-AZ)

## 10.1 오류 ① — 윈도우 타임아웃에서 자식 브라우저가 남았다

**원인.** `deck/site_session.py` 의 윈도우 분기가 `process.kill()` 만
불렀다. `CREATE_NEW_PROCESS_GROUP` 은 **신호 그룹**을 나눌 뿐이라 node 가
띄운 크로뮴은 그대로 남고, 다음 요청과 겹친다.

**고친 것.** `_kill_tree()` 가 이 실행이 만든 프로세스를 **자식까지** 끝내고,
**정리됐는지 확인해서** 돌려준다 (`Cleanup`).

| | |
| --- | --- |
| POSIX | `killpg(SIGKILL)` → 자식을 거둔 뒤 그룹이 사라졌는지 **폴링으로 확인** |
| 윈도우 | `taskkill /F /T /PID <pid>` — 그 프로세스의 **트리**를 끝낸다 |
| 사용자의 다른 브라우저 | 🔴 **건드리지 않는다** — 우리 프로세스의 자손만 트리에 든다 |
| 확인 실패 | `ok=False` 또는 `None`(확인 못 함) 으로 남고, 결과의 사유에 `프로세스 정리 미확인` 이 붙는다 |

🔴 **정리가 확인되지 않았는데 정상 종료처럼 적지 않는다.**
🔴 **윈도우 분기는 호출만 시험했고 실제 윈도우에서 돌려 보지 않았다**
(§9.6 의 미확인 목록에 그대로 남는다).

## 10.2 오류 ② — 종료 코드가 성공 판정에 없었다

**원인.** 종료 코드를 저장만 하고 보지 않았다. 또 "조작을 다 했는가" 를
**실행된 조작끼리** 셌다 — 중간에 멈추면 `operations_total` 도 함께 줄어
"2/2 성공" 처럼 보였다.

**고친 것.** 조작기가 `operations_planned`(계획한 조작 수)를 결과에 적고,
판정이 **여섯을 함께** 본다.

| 보는 것 | 어긋나면 |
| --- | --- |
| 실행 ID 일치 | `run_id_mismatch` |
| 종료 코드 0 | `bad_exit` |
| 결과 구조 (파일 존재 · JSON) | `missing_result` · `bad_json` |
| 계획한 조작 수 = 실제 조작 수 = 성공 수 | `incomplete` |
| 최종 상태 검증 통과 | `final_ok=False` |
| 그러고도 URL 이 있는가 | — |

🔴 **URL 이 있어도** 검증 실패나 비정상 종료면 공유 완료로 안내하지 않는다
(`SiteRunResult.shared` 가 위 전부를 함께 본다). 🔴 공유 뒤 결과가
불명확하면 **자동 재시도하지 않는다** (이미 공개됐을 수 있다).

## 10.3 오류 ③ — 같은 그림이면 "모호" 라면서 통과시켰다

**원인.** `identityOf()` 가 같은 그림이 여러 장이면 `모호` 라고 적으면서도
`ok: true` 를 돌려줬다. 실제 덱 이미지에서는 **같은 카드가 여러 장인 것이
정상**이므로, 그 길로는 개체를 가릴 수 없다.

**고친 것 — 근거의 순서를 바꿨다.** 그림은 **보조 근거**로 내리고, 개체
확정은 사이트의 **안정 ID**(`data-card-id`, 이동해도 바뀌지 않는다) 로 한다.

이동 (`decideMove`):

1. 끌기를 시작한 **그 지점에 있던 카드**가 `data-card-id` 로 그 개체였는가
   (`document.elementFromPoint`) — 🔴 **1차 근거**
2. 판에서 **자리를 옮긴 개체가 정확히 그 하나**인가 (조작 전후 판 읽기의
   차분)
3. 그 개체가 지금 **목적지 칸**에 있는가
4. 이력이 한 줄 늘었는가 · 판 읽기 문제가 없는가

발동 · 대상 (`decideMenu`) — 판이 바뀌지 않으므로 차분으로는 가릴 수 없다:

1. **우클릭한 지점의 개체**가 그 개체였는가 — 🔴 **1차 근거**
2. 메뉴 항목을 실제로 골랐는가
3. 이력이 한 줄 늘고 그 줄의 **종류**(`Activate Effect ·` / `Target ·`)가 맞는가
4. 그 줄에 적힌 칸이 **그 개체가 지금 있는 칸**과 같은가
5. 판에서 **아무것도 움직이지 않았는가**
6. (보조) 카드 상세 패널의 칸이 같은가 — 실측에서 `Monster Zone 1` ·
   `Grave` 로 읽혔다

🔴 **모든 중복 카드를 거부하지도, 그림이 같다고 통과시키지도 않는다.**
위 근거로 개체가 서면 정상 진행하고, 그중 하나라도 세우지 못하면 **그
자리에서 멈춘다**. `identityOf` 는 이제 "맞는가(`match`)" 와 "그 그림이
판에서 유일한가(`unique`)" 라는 **사실만** 돌려주고, 통과 여부를 정하지
않는다.

## 10.4 Neuron 덱 이미지 등록

🔴 **Neuron 앱에 접속하지 않는다.** 자동 로그인도 비공개 API 호출도 하지
않는다. **사용자가 자기 손으로 저장한 이미지 파일 한 장**을 받는다.

### 등록에 남는 것

| | |
| --- | --- |
| 등록 ID · 소유 사용자 | `dk…` · 소유자별로 나뉜 폴더 (해시) |
| 보관한 이미지 | `data/deck_images/<소유자>/<등록 ID>/image.<확장자>` — 🔴 **첨부 URL 을 들고 있지 않고 바이트를 복사해 둔다** |
| 이미지 해시 | SHA-256 |
| 정규화한 레시피 · 해시 | 카드 ID 와 매수만 남겨 정렬 — 순서·표기에 흔들리지 않는다 |
| 메인 · 엑스트라 · 사이드 | 사이트의 매수 칸에 그대로 넣는다 |
| 자리별 카드 | `main-0` … 가 어느 패스코드인가, 그리고 `site` / `user` 중 누가 확정했는가 |
| 확인 상태 · 방법 | `verified` · `사이트 식별` 또는 `사이트 식별 + 사용자 확정 N자리` |

### 어떻게 확인하는가 — OCR 이나 순서가 아니다

> 🔴 **정정 (Phase 6-BA · §11.6)**: 아래의 「`Deck` 탭 썸네일로 묶는다」 는
> **46자리에서만 됐다.** 그 목록은 가상 스크롤이라 55자리에서는 끝까지
> 읽히지 않는다. 지금은 **판의 카드를 자리마다 눌러 「Card details」 칸을
> 읽는다.**

사이트의 **`Deck` 탭 카드 목록**을 읽는다 (`Review card information` 과 같은
자리). 각 줄에는 그 자리에서 잘라낸 **썸네일**이 붙고, 그 `src` 는 판 위
카드의 `src` 와 같다. 🔴 **줄과 자리를 그 그림으로 묶는다** — 잘라낸 위치가
다르면 그림도 다르므로, 같은 카드가 여러 장이어도 일대일로 묶인다. 묶이지
않으면 **순서로 때우지 않고** 묶지 못했다고 적는다.

그 다음 **카드별 매수**까지 레시피와 맞춰 본다 (이름이 아니라 카드 ID 로 —
사이트가 보여 주는 일본어 이름을 저장소의 `name_ja` 로 되짚는다).

* 전부 식별되고 매수가 맞으면 → **확인됨**
* 못 읽은 자리가 있으면 → **확인되지 않은 등록**. 그 자리만
  `--confirm main-7=57835716` 으로 직접 확정할 수 있고, 확정하면
  `사이트 식별 + 사용자 확정` 으로 기록된다.
* 🔴 **확인되지 않은 등록으로는 사이트 조작을 시작하지 않는다**
  (`RunStatus.NOT_VERIFIED` — 브라우저를 열지도 않는다).

### 이미지 순서와 시작 패를 떼어 놨다

전에는 **시작 패가 이미지 맨 앞**이어야 했다 (시트를 우리가 구웠으므로).
실제 Neuron 이미지에는 그 가정을 걸 수 없다.

* 🔴 **이미지 순서를 바꾸라고 요구하지 않는다.**
* 지정 패는 **등록된 자리별 패스코드**에서 찾아 꺼낸다
  (`deck_image_registry.assign_slots`).
* 같은 이름의 카드가 여러 장이면 자리를 하나씩 나눠 가진다.
* 🔴 **매 실행마다 새로 묶는다** — 이전 세션의 임시 DOM ID 를 쓰지 않는다
  (`main-7` 은 이미지 안의 위치이지 브라우저가 만든 값이 아니다).
* 패를 꺼낸 뒤 **패에 든 개체 집합**을 확인하고 (장수만 세지 않는다),
  남은 덱 수도 본다.
* 레시피가 달라지면 등록 해시가 달라져 **불일치**가 된다.
* **같은 레시피에서 패만 바뀌면** 등록 ID 만 주면 된다 — 이미지를 다시
  올리지 않는다. 🔴 **정정 (Phase 6-BA · §11.2)**: 6-AZ 시점의 코드는
  그렇게 적어 놓고도 `/share-replay` 가 `recipe` 를 **필수로** 받고
  있었다. 6-BA 에서 고쳐, 이제 정말로 등록 ID 와 패만으로 돈다.
* 글자 자리표시 시트 모드는 **별도 모드로 남는다**. 🔴 실제 이미지 모드가
  실패했을 때 **말없이 시트로 바꾸지 않는다**.

1. `images.ygoprodeck.com/images/cards_small/<패스코드>.jpg` 에서 저장소
   카드 DB 의 카드 **14,319장**을 내려받았다 (이미 쓰고 있던 출처다 — §6).
2. 덱 이미지의 자리마다 **카드 전체**와 **그림칸**을 각각 16×16 으로 줄여

3. 🔴 **방법을 먼저 검증했다** — 사이트가 이미 이름을 읽어 준 35자리에서
   이 방법의 **1위가 35/35 일치**했다 (따옴표 표기 차이 1건은 §11.6 에서
   고쳤다). 2위와의 거리 차이는 보통 8~15 로 벌어졌다.
4. 그 다음에야 나머지 20자리에 같은 방법을 썼다. 모두 1위가 2위를 크게
   앞섰다 (가장 좁은 것이 `extra-1` 의 20.8 대 27.8).

읽어 낸 이름은 카드 그림의 **제목 글자**와도 맞춰 봤다 (예: `extra-0` 의
제목 끝이 「…ルシエラーゴ」, `extra-1` 이 「…シルヴィア」).

## 11.3 레시피 **완전 일치** — 남는 카드도 불일치다

6-AZ 의 `assign_slots` 는 **기록이 쓰는 카드가 등록에 있는지만** 봤다.
그래서 등록한 이미지 쪽에 **쓰이지 않고 남는 카드**가 있어도 통과했다 —
다른 덱인데 통과하는 구멍이다.

이번에 양쪽 다중집합을 **정확히** 맞춘다.

* 시작 패 + 남은 덱 + 엑스트라를 합친 것이 등록 구성과 **같아야** 한다.
* 모자람 · 남음 · 매수 차이를 **각각** 적는다
  (`… 가 등록한 이미지에 없습니다` / `… 가 등록한 이미지에 2장 남습니다` /
  `매수가 다릅니다 — 이번 기록 3장 · 등록 이미지 2장`).
* 엑스트라도 같은 잣대로 센다.
* 확인되지 않은 자리가 하나라도 남아 있으면 **시작하지 않는다**.
* 사이드 자리는 **조용히 버리지 않고** 「아직 쓰지 않는다」 고 적는다
  (`SIDE_UNSUPPORTED`, 계획의 `notes`).
* 🔴 **실행 기록을 직접 넣는 입구**(`--json`)도 같은 관문을 지난다 —
  레시피를 거치지 않는다고 검사가 비켜 가지 않는다.

### 등록된 이미지 **파일 자체**도 쓰기 전에 다시 센다

`registration_image_problem()` 이 보관한 파일의 **크기와 sha256** 을 등록
당시와 맞춰 본다. 다르면 `RunStatus.NOT_VERIFIED` 로 **브라우저를 열지
않는다.** 파일이 바뀌었는데 "등록된 실제 덱 이미지로 돌았다" 고 적으면
거짓이 되기 때문이다.

## 11.6 정정 — 자리 식별은 **「Deck 탭 썸네일」이 아니라 「카드 상세」** 다

약 20줄만 있고, 스크롤해 모아도 25줄에서 멈췄다.

그래서 `scripts/duel_simulator_register.js` 를 바꿨다: **판 위의 카드를
자리마다 눌러 「Card details」 칸을 읽는다.** 판의 카드는 전부 DOM 에 있고,
누르면 상세 칸이 **그 카드**를 가리키므로 자리와 이름이 어긋날 수 없다.
이 방법으로 **55/55 를 읽었다** (묶지 못한 줄 0).

저장소의 이름은 곧은 따옴표였다. NFKC 는 이 둘을 같게 만들지 않아 **멀쩡한
카드가 미식별로 떨어졌다.** `_tidy()` 가 따옴표 모양을 맞추도록 고쳤다.
