# Phase 3-F-46 — 분석 요약의 한국어 데이터 표시 정책 감사

**결론부터:**

* 🔴 **질문의 전제가 뒤집혔다.** `summarise()` 는 한국어 카드에 영어 이름이나
  영어 텍스트를 출력하지 **않는다**. **이름도 텍스트도 아예 출력하지
  않는다.** AST 로 센 결과 `name`·`name_ko`·`desc`·`display_name`·
  `summary_ko` 중 **하나도** 읽지 않는다. 따라서 "적용된 한국어가 영어로
  나온다" 는 사례는 **존재할 수 없다** → **`CONFIRMED_SAFE`**.
* 따라서 "한국어 이름은 이미 나오는데 라벨만 없다" 도 **아니다.**
  `summarise()` 는 순수 집계 표이고, 없는 것은 **집계 행 하나**다.
* **언어 표시 책임은 이미 올바른 곳에 있다.** 이름·텍스트를 고르는 소비자
  (`app/main.py`) 가 카드마다 언어를 표시하고 있고, 2 x 2 네 칸 전부
  자기 일관적이다 (실측).
* **기존 provenance 로 충분하다.** `name_ko` · `CardSource.KOREAN_OVERLAY` ·
  `korean_available` 세 증거가 **14,520 레코드 전수에서 카드 단위로 일치**
  한다. 어긋나는 카드 **0개** → 새 enum·필드·API 불필요.
* 남는 것은 갱신 요약의 **집계 행 부재** 하나이고, 그것은 요구사항이
  정해져 있지 않다 → **`UNKNOWN_BY_DESIGN`**.
* 참고로 집계 행을 추가해도 **기존 단정 하나도 깨지지 않는다** (실측).
* **production 을 한 줄도 바꾸지 않았다** (audit-only).

### 2.2 🔴 `summarise()` 가 읽는 것 전부

AST 로 `summarise()` 안의 속성 접근을 전부 셌다.

```
읽는 속성 : Counter · LUA_VERIFIED · NO_EFFECT · TEXT_DERIVED ·
            UNAVAILABLE · all_cards · analysis_status · get · items ·
            provenance · stats · value
부르는 것 : Counter · all_cards · get · items · stats · print

언어/이름/텍스트 관련 접근 : 없음
```

`name` · `name_ko` · `name_en` · `name_ja` · `desc` · `desc_en` ·
`display_name` · `summary_ko` — **하나도 없다.**

실제 출력에서도 확인했다. 한국어 이름(`패러렐 텔레포트`), 같은 카드의
영어 이름(`Parallel Teleport`), 한국어가 없는 카드의 영어 이름
(`Trap of the Poisonous Scorpion`) **셋 다 출력에 없다.**

현재 출력 전문 (실측, 319자):

```
카드 데이터 현황 (저장소 전체)
------------------------------------------------------------
  카드            : 14,127장 (판본 포함 14,520)
  Lua 근거 있음 (스크립트 첨부)         : 12,687장
  텍스트 유래 (Lua 없음)             : 756장
  효과 없음 (통상 몬스터·토큰)           : 684장
  분석 근거 없음                    : 0장
  (이 표는 분석 근거만 셉니다 — 블록·핸들러 결합 증명은 별도 표에서 셉니다.)
```

### 2.3 이름·텍스트를 고르는 자리

`core/card_model.py:510`

```python
def display_name(self) -> str:
    """표시용 이름. 한국어 > 공식 DB 원문 > 일본어 순."""
    return self.name_ko or self.name or self.name_ja or f"#{self.id}"
```

필드 fallback 하나이고 **provenance 를 보지 않는다.** `apply()` 가
`name_ko` 와 `name` 을 **둘 다** 채우므로 오버레이 후에는 두 필드가 같다.

언어를 사용자에게 **표시**하는 자리는 `app/main.py` 다 —
`print_card_detail` 의 이름 표(`한국어` / `공식 DB` / `일본어` 행)와
텍스트 라벨(`카드 텍스트(한국어)` 대 `카드 텍스트`). 즉 **고르는 자리와
표시하는 자리가 같은 모듈**이고, 그것이 맞는 구조다.

## 5. provenance 의 충분성 — 전수 확인

세 증거가 **카드 단위로** 일치하는지 14,520 레코드 전수로 확인했다.

| 증거 | 의미 |
|---|---|
| `card.name_ko` | 한국어 이름이 채워졌다 |
| `CardSource.KOREAN_OVERLAY in card.sources` | 오버레이가 이 레코드에 적용됐다 |
| `provenance.availability.korean_available` | 한국어 근거가 있다고 기록됐다 |

**세 값이 어긋나는 카드: 0개.** (`test_07` 이 전수로 못 박는다.)

따라서 한국어 적용 상태를 알기 위해 새 enum·새 필드·새 공개 API 가
필요하지 않다. §5 금지 조항과 같은 방향이다.

🔴 다만 논리적으로는 어긋날 수 있는 틈이 있다: `apply()` 는 이름이 비어
있으면 `name_ko` 를 채우지 않고도 플래그를 붙인다. 현재 어긋나지 않는
이유는 `data/ko` 항목 **전부가 이름과 텍스트를 둘 다** 갖고 있기 때문이다
(Phase 3-F-45 실측: 이름만 0개 · 텍스트만 0개). 데이터의 성질에 기댄
일치이고, 그 성질은 3-F-45 의 테스트가 지키고 있다.

## 6. 집계 행을 추가하면 기존 단정이 깨지는가 (§2 질문 6)

실측으로 확인했다. 현재 `summarise()` 출력에 후보 행을 덧붙인 문자열을
만들어, 기존 테스트들이 이 출력에 걸어 둔 단정을 모두 다시 돌렸다.

후보 행:

```
  한국어 데이터 있음            : 13,728장 (없음 399장)
```

| 검사 | 결과 |
|---|---|
| 기존 **긍정** 단정 literal 9개 (`Lua 근거 있음` · `텍스트 유래` · `분석 근거만 셉니다` · `결합 증명은 별도` · 네 라벨 전문 · `14,127`) 가 여전히 있는가 | **전부 있음** |
| 기존 **부정** 단정 literal 8개 (`Lua 검증됨` · `표에 없는 분석 상태` · `효과 블록 결합 상태` · `결합 상태` · `일반 몬스터` · `미증명 블록` · `다시 분석했습니다` · `🔴`) 가 걸리는가 | **하나도 안 걸림** |
| 후보 행 자체가 부정 literal 을 포함하는가 | **없음** |

기존 단정은 전부 `in out` / `not in out` 부분 문자열 검사이거나 소스
검사다. **출력 길이나 행 집합을 고정한 단정은 없고, 행 추가를 금지한
단정도 없다.** 따라서 추가는 기존 계약을 바꾸지 않는다.

🔴 Phase 3-F-40 에서 새 문구가 기존 단정과 충돌해 실패한 적이 있다
(결합 표 제목을 그대로 반복해서). 그래서 이번에는 추가 전에 **미리**
측정했다. 후보 행의 문구는 그 결과에 맞춰 고른 것이다.

### 7.1 N62 의 최소 수정안 (제안만 — 구현하지 않았다)

```
scripts/update_cards.py 의 summarise() 에 한 행 추가 (기존 형식 유지):
  "  한국어 데이터 있음            : {N:,}장 (없음 {M:,}장)"
  N = all_cards() 중 KOREAN_OVERLAY 보유 수   (= 13,728)
  M = len(all_cards()) - N                    (=    399)
```

지켜야 하는 것:

* **정본 기준으로 센다.** 사용자가 보는 계층이고, 적용된 alias 판본
  164개를 "미적용" 으로 오해하게 만들지 않는다.
* **`apply()` 의 반환값을 받는 방향으로 고치지 않는다.** 도달 가능한
  실패 모드에서는 `apply()` 가 호출조차 되지 않는다 (Phase 3-F-45 §5.3).
* **새 API 를 만들지 않는다.** 공개 `all_cards()` + 공개
  `CardSource.KOREAN_OVERLAY` 로 충분하다 (§5).
* **미적용 7개를 이 행에 섞지 않는다.** 그것은 카드가 없는 항목이고
  사용자 계층의 수가 아니다.
* 분석 근거 표와 **섞지 않는다.** 근거 계층(Lua/텍스트)과 언어 계층은
  다른 축이다 — 한 표에 합치면 Phase 3-F-40 이 분리한 것을 되돌린다.

🔴 이것은 **제안**이다. 요구사항이 정해지지 않았으므로(N62 =
`UNKNOWN_BY_DESIGN`) 구현 여부는 지시를 기다린다.

#### 9.2.1 작성 중 잡은 내 오류

`_name_rows()` 의 정규식을 공백 **4개**로 짚었으나 `app/main.py` 는

#### 9.2.2 🔴 저장소 tripwire 에 실제로 걸렸다

전체 회귀 **전에** 돌린 사전 점검에서 **1건 실패**했다.

```
FAILED tests/test_update_coverage_contract_audit.py::test_41_no_test_was_deleted_and_no_skip_was_added
AssertionError: ('tests/test_summary_korean_display_policy_audit.py',
                 'pytest.skip("cards.cdb 없음")')
```

원인: `repo_without_korean` fixture 안에서 데이터 유무를
`pytest.skip("cards.cdb 없음")` 으로 걸렀다. 이 저장소는 **새로 추가된
테스트 파일의 모든 조건부 건너뛰기**가 `"이 Phase 의 commit 이 아직
없다"` 여야 한다고 못 박아 두었고(`test_41` 이 전수 검사),
**예외가 없다.** `tests/conftest.py` 의 `repository` fixture 가 같은
문구를 쓰고 있어서 그 관용구를 그대로 가져왔는데, conftest 는 **기존
파일**이라 이 검사 대상이 아니었다.

고친 방법 — **테스트를 약화시키지 않고 내 쪽을 저장소 규칙에 맞췄다.**

1. fixture 안의 skip 을 **없앴다.** 데이터 게이트는 이 fixture 를 쓰는
   두 테스트(`test_05` · `test_06`)에 이미 붙어 있는
   `requires_cards_cdb` **마커**가 담당한다. 마커는 fixture 생성보다
   먼저 평가되므로 데이터가 없으면 fixture 자체가 돌지 않는다. 그
   전제를 fixture docstring 에 적어 두었다.
2. 내 파일의 자체 점검(`test_10`)이 `"cards.cdb 없음"` 을 **예외로
   허용하고 있었다.** 그래서 내 tripwire 자체 점검이 이 문제를 놓쳤다.
   그 예외를 **제거해** 저장소와 똑같이 엄격하게 만들었다.

🔴 즉 이번 실패는 "저장소 규칙이 과하다" 가 아니라 **내 자체 점검이
저장소보다 느슨했다**는 문제였다. 느슨한 쪽을 조인 것이 맞는 방향이다.
기존 테스트는 한 글자도 바꾸지 않았다.
