## 2. 기존 구현 조사와 **실제** 결함

조사한 것: 6-Z 보고서와 부록, `TriggerRequirement` / `TriggerEligibilityJudge`
/ `trigger_order` / `trigger_compiler`, `integration.autonomy.trigger_offers`
와 `TriggerSource`, `Duel` 의 후보 생성 · 재검증 · `consumed_events` · 우선권,
`GameState.rule_uses`, `EffectRef` 의 식별 범위, `agent.simulation._fork`,
그리고 6-Y·6-Z 가 고친 구조 감사들.

### 이미 보장되어 있던 것 — **재작성하지 않았다**

| 이미 있는 것 | 근거 |
|---|---|
| 유발 후보의 다섯 관문 | `TriggerEligibilityJudge` (EVENT_RELATION · ACTIVATION_ZONE · TRIGGER_CONDITION · EXECUTION_AUTHORITY · COST_FEASIBILITY) |
| 정상 경로 · 상대 응답 · 해결 중 선택 | 6-Z. 이 Phase 가 그 경로를 **그대로 쓴다** (`test_b01` 이 끝까지 밟는다) |
| 거절된 발동이 사건을 소비하지 않는다 | 6-Z 가 수락 **뒤에만** 적게 했다. 6-AA 가 불법 셋으로 다시 센다 (`test_c04`) |
| 카드명 단위 횟수 제한 | `GameState.rule_uses`. 🔴 개체별 제약과 **다른 축**이고 섞지 않았다 |
| 사본의 값 격리 | `consumed_events` 가 `frozenset` 이므로 `dataclasses.replace` 가 값으로 가져간다 (`test_d04` 가 확인) |

### 실측으로 확인한 결함 다섯

#### 결함 1 — 🔴 모름이 **임의로 승격**되고 있었다

6-Z 의 `_trigger_actions` 가 강제 · 임의 · 모름을 한 덩어리로 `allowed` 에
올리고 발동 여부를 전부 정책에 맡겼다. 그 docstring 이 그렇게 적어 두었다:
*"🔴 강제/임의를 가르지 않는다 … 후보로 내놓기만 하고, 발동할지는 고르는
쪽이 정한다."*

그러면 **정책의 거절과 규칙이 허락한 포기가 구별되지 않는다.** 실제로 강제인
효과였다면 규칙이 요구한 처리가 조용히 생략되고, 어디서도 그 사실이 적히지
않는다.

#### 결함 2 — 🔴 발동 기회가 **만료되지 않았다**

`_trigger_offers` 가 기록 **전체**를 매번 다시 펼쳤다. 실측 (오르페골 레시피 ·
기르수 일반 소환 뒤 페이즈를 넘기며 같은 발동의 관문을 물었다):

```
MAIN1    offers=1  gate=valid/ok
BATTLE   offers=1  gate=valid/ok   ← 결함
MAIN2    offers=1  gate=valid/ok   ← 결함
END      offers=1  gate=valid/ok   ← 결함
DRAW(T2) offers=1  gate=valid/ok   ← 결함
STANDBY  offers=1  gate=valid/ok   ← 결함
```

메인 페이즈 1 의 소환 유발을 배틀 페이즈에, 심지어 **다음 턴**에 발동할 수
있었다. ("다음 턴에는 후보가 0건" 으로 보이던 것은 그 자리가 턴 플레이어가
아니라 `legal_actions` 의 어느 분기도 밟지 않았기 때문이고, 기회는 **잠복해
있었다** — 우선권이 열리는 순간 다시 열린다.)

#### 결함 3 — 🔴 소비 단위가 **카드 개체를 가르지 않았다**

키가 `(event_key, effect_ref)` 둘이었다. `EffectRef` 는
`(card_id, ordinal)` 이므로 (`engine/ids.py`) **개체를 가르지 않는다.** 한
사건이 같은 이름의 카드 두 장을 유발시키면 한 장의 발동이 다른 장의 적법한
기회까지 닫는다.

#### 결함 4 — 🔴 **사본의 `legal_actions` 가 터졌다** (6-Z 회귀)

`trigger_offers` 가 기록 없는 듀얼에서 `AutonomyError` 를 던졌다. 그런데
`agent.simulation._fork` 는 `journal=False` 로 한 벌을 바꿔 끼운다 (6-B — 사본의
전개가 진짜 기록에 남지 않게). 실측:

```
Simulator.simulate(유발 발동) → ERROR
reason: AutonomyError: 이 듀얼에는 EventJournal 이 없습니다.
```

후보를 **묻는 일**이 예외를 던지면 그 사본으로는 아무 행동도 평가할 수 없다.
6-Z 의 시험들이 사본을 뜨지 않았으므로 놓쳤다.

#### 결함 5 — 출력 모순 넷 (사용자가 Discord 에서 찾았다) → §7

## 3. 강제 · 임의 · UNKNOWN — 근거와 처리

### 3.1 근거의 우선순위

| 순위 | 근거 | 이 질문에 대해 |
|---|---|---|
| 1 | **공식 규칙 (룰북)** | 🔴 **없다.** 구조화 데이터의 `effect_types` 가 유발 효과의 발동 시점만 적고 강제 · 임의를 적지 않는다. `test_a03` 이 그 사실을 데이터에서 직접 읽어 고정한다 (`mandatory` 라는 낱말이 0회) |
| 2 | **카드 텍스트** | 🔴 **여기서 답이 나온다.** 「발동**할 수 있다**」는 허가의 진술, 「발동**한다**」는 수행의 진술 |
| 3 | **Lua 선언 접미사** | 🔴 **혼자 답을 만들지 못한다.** 텍스트와 **어긋날 때 판정을 거두는** 데만 쓴다 |

🔴 **Phase 3-F-26 의 결론을 뒤집지 않았다.** 그 Phase 가 `TRIGGER_O` /
`TRIGGER_F` 의 뜻풀이를 **근거 없음**으로 기록했다 (공식 자료에 그 이름이
0회). 6-AA 는 그 뜻을 **쓰지 않는다** — 접미사의 역할은 좁히는 것뿐이므로,
뜻풀이가 틀렸더라도 판정이 넓어지지 않는다 (`test_a02` 가 센다: 접미사만
주면 어느 쪽도 나오지 않는다).

### 3.2 판정 표 (`engine.trigger_compiler.requirement_from`)

| 텍스트 | 선언 | 판정 |
|---|---|---|
| 「…할 수 있다」만 | `TRIGGER_O` | **OPTIONAL** |
| 「…한다」만 | `TRIGGER_F` | **MANDATORY** |
| 둘이 어긋난다 | — | UNKNOWN ← 3-F-26 의 반례들 |
| 텍스트가 섞였다 / 없다 | — | UNKNOWN |
| 한 블록이 `O` 와 `F` 를 함께 선언 | — | UNKNOWN |

### 3.3 효과 단위인 이유 — 그리고 그것이 정당한 이유

🔴 **카드 전체를 한 분류로 뭉개지 않았다.** 판정은 블록의 **제 선언**을 보고
하므로, 한 카드의 두 블록이 다른 답을 받는다 (실측 10장 이상, `test_a06`).

텍스트는 카드 단위인데 어떻게 효과 단위 판정에 쓰는가 — 문장과 블록을 잇는
계층이 이 저장소에 **없다** (`tests/test_effect_block_alignment_audit.py` 가
그 공백을 적어 두었다). 그래서 「①」이 어느 블록인지 모른다. 그런데 **모든
발동 문장이 같은 쪽을 말할 때**는 그것을 몰라도 답이 하나다 — 어느 문장이
어느 블록에 붙든 결론이 같다. 섞여 있으면 붙이는 방법에 따라 답이 달라지므로
**판정하지 않는다** (`None` → UNKNOWN).

### 3.4 실측 — 유발 선언 블록 8,052개 · 카드 5,857장

```
OPTIONAL    5,176 (64.3%)   텍스트=임의만 × TRIGGER_O
MANDATORY     514 ( 6.4%)   텍스트=강제만 × TRIGGER_F
UNKNOWN     2,362 (29.3%)
   ├ 텍스트 미기재  1,517   「발동…」 문장이 아예 없다
   ├ 텍스트 혼재      766   붙이는 방법에 따라 답이 달라진다
   └ 둘이 어긋남       79   (임의텍스트×F 72 · 강제텍스트×O 7)
```

기르수 `e[0]` · `e[1]` → **OPTIONAL**. 🔴 그 근거는 그 카드의 텍스트이고 카드
번호가 아니다 — `test_a04` 가 프로덕션 네 파일에 `69811710` 이 없음을 센다.

🔴 **「발동…」 문장이 없는 1,517 블록을 넓히지 않았다.** 「파괴되었을 때 …
특수 소환**할 수 있다**」처럼 **행동 동사**가 허가를 지는 모양이 흔하지만,
그 문구를 넣으면 「1턴에 1번밖에 사용할 수 **없다**」 같은 제약과 효과 자체의
행동 문구가 섞여 들어온다. 좁게 두고 측정으로 적는다.

### 3.5 처리 — `Duel._trigger_actions` 가 셋으로 가른다

| 판정 | 후보 | 흐름 | 그 밖 |
|---|---|---|---|
| **OPTIONAL** | 올린다 | 막지 않는다 | 발동도 포기도 고르는 쪽의 것 |
| **MANDATORY** | 올린다 | 🔴 **막는다** — `END_PHASE` 를 보류 | 🔴 **대신 발동해 주지 않는다** |
| **UNKNOWN** | 🔴 **올리지 않는다** | 막지 않는다 | 보류에 무엇을 모르는지 적는다 (`TRIGGER_REQUIREMENT_MISSING`) |

**왜 강제를 대신 발동해 주지 않는가.** 엔진이 대신 고르면 해결 중의 선택
(어느 카드를 묘지로 보내는가)까지 엔진이 정하게 되고, 그것은 6-Z 가 세운
경계를 무너뜨린다. 그래서 **흐름을 막고 후보를 남긴다** — 고르는 쪽에게
남은 길은 그 발동을 집는 것이다 (`test_b03` · `test_b04`).

**왜 UNKNOWN 은 흐름을 막지 않는가.** 막으면 **영영 막힌다** — 모름은 후보가
아니므로 발동해서 해소할 길이 없고, 듀얼이 그 자리에서 끝난다 (`test_b05`).
그래서 모름의 처리는 "보류에 적고 흐름은 열어 둔다" 이고, 그것이 강제와
다른 점이다.

🔴 **조건 · 비용 · 발동 가능성과 섞지 않았다.** `requirement_from` 은 "규칙이
발동을 요구하는가" 하나만 답한다. 조건이 참인가 · 비용을 낼 수 있는가 ·
지금이 그 시점인가는 전부 다른 질문이고 `TriggerEligibilityJudge` 의 다섯
관문이 답한다. **강제 효과도 조건이 거짓이면 발동하지 않는다.**

## 4. 발동 기회의 수명과 사건 소비 단위

### 4.1 수명 — `Duel.timing_floor`

```
timing_floor : int = 0   # 이번 페이즈가 시작될 때의 기록 번호
```

제안은 `event_sequence >= timing_floor` 일 때만 열린다
(`Duel._opportunity_is_open`). 바닥은 `_apply_end_phase` 에서 올라간다 —
페이즈를 바꾸는 **유일한** production 자리다.

🔴 **근거는 룰북의 페이즈 구조다**: *"After a card's activation, and at the
end of each phase or step, Priority passes to the opponent"* (TURN PLAYER'S
PRIORITY). 메인 페이즈 1 에 일어난 사건의 유발을 배틀 페이즈에 발동하는 것은
그 사건의 시점이 아니다.

🔴 **새 식별자를 만들지 않았다.** `JournalEvent.sequence` 는 기록이 identity
로 쓰는 값이고 (`EventJournal` 의 설명), 그것을 그대로 쓴다. 번호를 **모르는**
제안(`-1`)도 열리지 않는다 — 지금 것인지 말할 수 없으면 내놓지 않는다.

**EventJournal 의 기록과 "지금 유효한 기회" 를 가른 자리가 이것이다.** 기록은
과거 전부를 들고 있고, 기회는 **바닥 위**의 기록에서만 나온다.

### 4.2 소비 단위 — 세 짝

```
consumed_events : frozenset[(event_key, effect_ref, source)]
```

| 축 | 무엇을 가르는가 |
|---|---|
| `event_key` | **어느 사건인가.** `TimingEvent` 자체 (불변 · 값 동치) |
| `effect_ref` | **어느 효과인가.** `(card_id, ordinal)` |
| `source` | 🔴 **어느 카드 개체인가.** 6-AA 가 더했다 |

🔴 **카드명 단위 횟수 제한과 다른 축이다.** 「이 카드명의 ①의 효과는 1턴에
1번」 같은 제약은 개체가 아니라 **이름**에 걸리고, 그것을 세는 자리는
`GameState.rule_uses` 다. `consumed_events` 는 **한 사건이 한 기회를 두 번
열지 않는다** 만 말한다 (RULE-EFFECT-004 — 시점을 정하는 것은 사건이다).

### 4.3 분기 · 복제 · 재현에서 어디에 보존되는가

| 값 | 어디 | 사본이 어떻게 가져가는가 |
|---|---|---|
| `consumed_events` | `Duel` 의 칸 | `frozenset` → `dataclasses.replace` 가 **값으로** |
| `timing_floor` | `Duel` 의 칸 | `int` → 값으로 |
| 사건 기록 | `Duel.journal` | 🔴 `_fork` 가 **떼어 낸다** → BLOCKER-6AA-1 |

🔴 **`GameState.state_hash` 가 같다고 발동 가능성이 같지 않다** (`test_d05`).
해시는 판의 **모양**이고 기회는 흐름 위의 자리다. 실측으로 그 둘이 갈라지는
상태를 만들어 고정했다 — 발동만 하면 (해결 전) 판의 모양은 그대로인데
`consumed_events` 가 다르고, 한쪽은 후보가 있고 다른 쪽은 없다.

## 5. 게임 구조 · AI · 연결 계층의 책임

| 계층 | 이 Phase 에서 | 어떻게 지켰는가 |
|---|---|---|
| **엔진** | 규칙 · 시점 · 후보 · 재검증 · 상태 변경 | 판정 셋(강제/임의/모름)이 `Duel` 안에서 일어난다. 흐름을 막는 것도 엔진이다 |

- `✅ 엔진이 실제로 5걸음 실행했습니다 (효과 해결 **1걸음** · 상태 변경 5걸음)`
- `막히지 않고 끝난 걸음 5 / 5 (🔴 효과를 그만큼 해결했다는 뜻이 아닙니다)`
- `그중 효과가 실제로 해결된 걸음 1걸음`
- 멈춘 이유에 `🔴 이것은 이 저장소의 현재 지원 범위 …` 한정이 붙는다
- 정적 계획 절 끝에 `🔴 … recipe: 로 이미 검사했습니다` 가 붙는다
- 최종 상태는 그대로 (몬스터 1 / 마법함정 3 / 패 1 / 묘지 1 / 덱 34)

### 명령 2 — 매수 초과 (실험 3 과 같다)

```
/combo recipe:<위와 같음>
       hand:69811710, 69811710, 69811710, 69811710, 93920420
```

예상:

- `🔴 실행하지 않았습니다 — 입력 검증을 통과하지 못했습니다`
- `패의 매수가 덱 보유 매수 이내인가: … 패 4장 > 덱 3장`
- 🔴 **정적 계획이 나오지 않는다.** 대신
  `🔴 정적 전개 추천은 내지 않았습니다 — 이번 요청의 입력이 규칙 검증을
  통과하지 못했습니다` 와 고쳐서 다시 보내 달라는 안내
- `"확정"` · `"엔진이 허가"` 가 **한 번도 나오지 않는다**

### 🔴 이 Phase 로 **달라지지 않는** 것

- 기르수의 유발은 **임의**이므로 `/combo` 의 기준점 정책(`first-permitted`)이
  여전히 발동을 집는다. 전개 결과는 6-Z 와 같다.
- **강제 유발을 실제로 보는 명령은 없다** — 실행 구현이 등재된 유발이 임의
  하나뿐이다 (BLOCKER-6AA-3).
- 같은 페이즈 안에서 발동을 거른 뒤 다시 제안되는 것은 그대로다
  (BLOCKER-6AA-2).
