# 검증된 복수 전개 결과의 비교·추천 v1 (Phase 6-AK)

같은 입력과 같은 목표로 탐색해 얻은 **검증 완료 결과들** 사이에서, 이름과
판이 붙은 기준에 따라 **무엇을 먼저 검토할지** 고르는 단계다. 앞 단계
(6-AH · 6-AH 보완 · 6-AI · 6-AJ, `docs/orcust-first-bounded-search.md` 와
`docs/orcust-multiple-path-resource-comparison.md`)가 만든 탐색 · 재생 검증 ·
자원 비교를 **그대로** 쓴다.

> 🔴 **이 단계는 강한 집 평가가 아니다.** 실전 승률도, 최강 전개도, 상대
> 방해 대응력도 계산하지 않는다. "최선 전개 탐색 완료" 도 "범용 AI 완성" 도
> 아니다. 이번에 더한 것은 **자원 보존 중심의 제한적 휴리스틱** 하나다.

---

## 0. 기존 기능과 이번 기능의 차이

| | 기존 (6-AI · 6-AJ) | 이번 (6-AK) |
|---|---|---|
| 하는 일 | 서로 다른 결과를 **모으고 재생 검증하고 자원 차이를 늘어놓는다** | 그 결과들 중 **무엇을 먼저 볼지** 고른다 |
| 판단 | 🔴 하지 않는다 ("어느 쪽이 더 좋은지 고르지 않았습니다") | 🔴 **두 보존 축에서만** 한다 (그 밖은 여전히 판단하지 않는다) |
| 출력 | 결과별 자원 + 차이 문장 | 그 위에 **추천 절**이 붙는다 |
| 자리 | `agent/bounded_search.py` · `deck/report.py` | `agent/result_ranking.py` (새 모듈) + 기존 렌더러에 **선택 인자** |

🔴 **독립 단계다.** 평가는 탐색과 재생 검증이 **끝난 뒤**에 값만 읽고 돈다.
받은 결과 · 경로 · 재생 결과를 하나도 바꾸지 않으며(전부 frozen),
`ranking` 을 주지 않은 호출은 6-AJ 와 **한 글자도 다르지 않다**
(`test_c03` · `test_d04`).

```
탐색(run_many) → 수집(_collect) → 재생 검증(rerun_results)
                                      ↓  (끝난 뒤)
                            평가(rank_results)  ← 이번 단계
                                      ↓
                 표시(render_multi_search_brief / render_multi_search)
```

## 1. 평가 정책 — 이름과 판

| 칸 | 값 |
|----|-----|
| 이름 | `resource-preservation` (`POLICY_NAME`) |
| 판 | `v1` (`POLICY_VERSION`) |
| 기준 | `CRITERIA_V1` — 세 개 (아래) |
| 구조화 | `Ranking.policy` · `.version` · `.criteria` · `.unjudged` |

🔴 **정책의 이름과 판을 자료형에 넣어 두었다.** 기준이 바뀌면 보고에 그대로
드러난다 — "언제 어떤 기준으로 추천한 것인가" 를 나중에 되돌릴 수 있어야
한다.

### 1.1 기준 셋 — 무엇을 읽고, 무엇을 증명하지 않는가

| 기준 | 읽는 것 | 쓰임 | 🔴 증명하지 **않는** 것 |
|------|---------|------|------------------------|
| `hand_left` (남은 패 장수) | 재생으로 검증된 상태의 자기 패 장수 | 보존 축 | 패를 **더 남겼다**는 뜻이고, 그 패의 **활용도가 더 높다는 증명이 아니다**. 무엇을 할 수 있는 패인지 세지 않았다 |
| `normal_summon_right` (일반 소환권) | 엔진이 기록한 이 턴의 일반 소환권 사용 여부 | 보존 축 | 쓰지 않았다는 것은 **이 턴에 아직 쓰지 않았다**는 뜻이고, **지금 합법적으로 일반 소환할 수 있다는 증명이 아니다** (그 판정은 `legal_actions` 의 일이다) |
| `spend_actions` (비흐름 행동 수) | 경로의 걸음 중 흐름 행동이 아닌 것의 수 | **표시 순서** | 적다는 것이 **패 트랩에 강하거나 실전적으로 더 좋다는 뜻이 아니다**. 짧은 경로를 먼저 검토하게 하는 표시 기준일 뿐이다 |

🔴 **흐름 행동은 비용으로 세지 않는다** — `FLOW_ACTION_KINDS` =
`{pass, end_phase, change_phase}`. 패스는 무엇을 쓰는 수가 아니라 우선권을
넘기는 수이고, 세면 "패스를 한 번 더 한 경로" 가 더 비싼 전개로 읽힌다.
흐름 행동의 수는 `Measures.flow_actions` 에 **참고로** 남고, 보고에
"비용에서 제외" 라고 적힌다(`test_a02`).

🔴 **카드별 실전 강도를 지어내지 않았다.** `Measures` 에 있는 칸은 위 세
수치와 `flow_actions` 뿐이고, 합계 칸이 없다. "전개 점수 87점" 같은 수도
가중치도 없으며, 코드에 `score` · `weight` · `점수` · `총점` · `순위` ·
`승률` 이라는 이름이 **하나도 없다** (`test_a07` 이 AST 로 센다).

## 2. 추천 방법

### 2.1 두 보존 축의 비지배 후보

후보 A 가 후보 B 를 **지배**한다 = 남은 패와 일반 소환권 **두 축 모두**
나쁘지 않고, **최소 한 축**이 더 낫다. 아무에게도 지배당하지 않은 후보가
**추천 후보**다.

- 서로 장단점이 있으면 **둘 다 남는다** (`test_a04`).
- 두 축이 같으면 서로 지배하지 못하므로 **둘 다 남는다** (`test_a05`).

🔴 **이것을 게임 전체에서의 우월성이나 안전한 가지치기 근거로 해석하지
말 것.** 밀린 후보가 필드 구성이나 세트한 카드 때문에 실제로 더 좋을 수
있고, **이번 기준은 그것을 보지 못한다.** 보고가 그 문장을 그대로 적는다
(`test_a03` · `test_c02`).

### 2.2 표시 순서와 공동 후보

비지배 후보 안에서 **비흐름 행동 수가 적은 순서로 표시**한다. 같으면 같은
자리(`Candidate.order`)에 두어 **공동 후보**가 된다.

- 🔴 이것은 **표시 기준**이다 — 짧은 경로를 먼저 검토하게 하는 것이고 우열이
  아니다.
- 🔴 **결과 ID 는 표시 순서를 가르는 데만** 쓰고 우열 근거로 쓰지 않는다.
- 🔴 **억지로 하나로 줄이지 않는다.** 동률이면 동률이라고 말한다
  (`test_a06`: 세 수치가 모두 같으면 `order` 가 같고 "모두 같습니다" 가
  이유에 적힌다).

### 2.3 추천 이유

수치와 함께 적는다. 실제 출력(`Ranking.reason_ko`):

```
이번 자원 보존 기준(resource-preservation v1)의 추천 후보입니다. 패 4장을
남겼고 일반 소환권을 사용했습니다. 비흐름 행동은 2회입니다 (흐름 행동 0회는
비용으로 세지 않았습니다). 다른 추천 후보와 **장단점이 갈립니다**: 결과 2 는
패가 2장으로 적습니다 · 일반 소환권을 쓰지 않았습니다 · 비흐름 행동이
1회입니다 — 🔴 어느 쪽이 더 좋은지 고르지 않았습니다.
```

밀린 후보에도 이유가 적힌다:

```
이번 두 보존 축에서 다른 후보에 밀렸습니다 — 밀린 상대: 결과 1 (두 축 모두
나쁘지 않고 최소 한 축이 더 낫습니다). 🔴 그쪽이 게임 전체에서 더 좋다는 뜻은
아닙니다. 패 2장을 남겼고 일반 소환권을 사용했습니다. …
```

## 3. 재생 검증과 평가의 경계

| 상태 | 추천 대상인가 | 어떻게 남는가 |
|------|---------------|---------------|
| `verified` | ✔ | 평가하고 추천 후보를 가린다 |
| `mismatched` · `errored` · `timed_out` · `not_started` · `disabled` | 🔴 아니다 | `Exclusion.NOT_VERIFIED` 로 **원래 재생 상태와 함께** 남는다 |
| 검증됐지만 관측값을 읽을 수 없음 | 🔴 아니다 | `Exclusion.UNMEASURABLE` + 못 읽은 이유 |

- 🔴 **같은 실행에서 수집된 결과끼리만** 비교한다 — `Ranking` 은 하나의
  `MultiSearchOutcome` 에서만 만들어진다.
- 🔴 **수치가 유리해도 미검증 결과는 추천하지 않는다** (`test_b01`: 패 9장을
  남긴 불일치 결과가 패 2장의 검증 결과에 밀린다).
- 🔴 **다섯 미검증 상태를 하나로 뭉개지 않는다** (`test_b02`) — 6-AJ 가 가른
  구분을 평가가 되돌리지 않는다.
- 🔴 **읽을 수 없는 값을 0 점이나 유리한 기본값으로 대체하지 않는다**
  (`test_b03`: 자원 요약이 없거나, 패 장수를 못 읽거나, 걸음 종류를 못
  읽거나, 소환권 기록이 참/거짓이 아니면 **평가 불가**).
- 검증 결과가 **없으면** "🔴 추천할 검증 결과가 없습니다", **하나면**
  "유일한 검증 후보입니다 — 🔴 다른 결과보다 우수하다는 뜻이 아닙니다"
  (`test_b04`).
- 🔴 **평가가 입력을 바꾸지 않는다** (`test_a08`: 평가 전후로 결과 ·
  경로 · 재생 결과가 바이트 단위로 같고, 다시 돌려도 같은 추천이 나온다).
- 🔴 **평가 때문에 경로가 사라지지 않는다** — `Ranking.candidates` 는 제외된
  것까지 **모든 결과**를 원래 ID 순서로 들고 있다.

## 4. 평가가 판단하지 못하는 것

`Ranking.unjudged` 에 **이름으로** 적어 두었다 (보고가 "평가했다" 로 읽히지
않게).

- 상대에게 남긴 카드와 **토큰** (몇 칸을 줬는지는 기존 비교가 보여 주지만,
  유리한지 불리한지는 판단하지 못한다)
- 이미 쓴 **효과 사용 제한** (무엇을 더 못 쓰게 됐는지의 가치)
- 자신 **필드 · 묘지 · 제외 · 엑스트라 덱의 구성** 차이
- **세트한 카드가 무엇인지**, 그것이 막는 것
- **공격력 · 링크 수치** 등 수치 자체
- **다음 턴의 후속 전개와 상대의 방해 수**

🔴 **필드 카드 수나 세트 카드 수가 늘어도 추천이 자동으로 오르지 않는다**
(`test_b05`: 필드 몬스터 5장 · 세트 3장을 붙여도 세 수치와 추천이 그대로다).
그 차이들은 **기존 비교 정보로 그대로 보여 주고**(`결과들의 차이` 와 각
결과의 자원 칸), 점수로 바꾸지 않는다 (`test_d04`).

🔴 **목표 카드에 처음 도달한 시점의 비교다.** 탐색은 목표에 닿은 분기를 더
펼치지 않으므로(6-AI §1.2), 여기 있는 자원은 "전개를 끝까지 수행한 최종 집"
이 아니다. 요약과 상세에 **둘 다** 그 문장을 적는다.

## 5. 사용자 실행 진입점

🔴 **새 명령도 새 옵션도 만들지 않았다.** 복수 결과 모드(`--results` ·
`/combo results`)의 출력에 추천 절이 **붙기만** 한다 — `/combo` 의 인자는
6-AI 가 만든 일곱 그대로이고, CLI 에도 추천용 플래그가 없다
(`test_c05` 가 센다).

### 5.1 CLI

```bash
python3 -m app.main combo \
  "69811710, 703897, 2930675, 12989604, 93920420" \
  --recipe path/to/orcust.ydk \
  --search galatea \
  --results 3
```

### 5.2 자리 배치 (ADR-007)

| 층 | 하는 일 |
|----|---------|
| `agent/result_ranking.py` | 평가. `engine` 과 `agent` 만 import 하고 카드 ID 리터럴이 없다 |
| `deck/report.py` | 표시. 🔴 `agent` 를 import 하지 않고 넘어온 평가 결과의 **모양만** 읽는다 |
| `app/main.py::rank_search_results` | 둘을 **잇는 자리 하나** — CLI 와 Discord 가 같은 것을 꽂는다 |

🔴 **어댑터가 각자 평가하지 않는다.** 둘이 각자 하면 같은 입력에 다른 추천이
나오고 어느 쪽이 맞는지 알 수 없다. 그리고 Discord 어댑터는 `agent` 를 직접
import 하지 않는다(기존 경계 `test_15`).

### 5.3 기본 응답과 상세

| 기본 응답 (요약) | 상세 기록 (첨부) |
|---|---|
| 평가 정책 이름과 판 | 정책 이름 · 판 · 기준마다 읽는 것과 🔴 제한 |
| 검증된 후보 수 | 후보별 평가 항목과 값 (추천/비추천 · 표시 순서 포함) |
| 추천 후보 ID 또는 **공동 후보** | 비지배 후보 선정 이유와 🔴 "가지치기 근거가 아니다" |
| 핵심 추천 이유와 주요 장단점 | 추천 대상에서 **제외된 결과와 사유** |
| 🔴 범위 ("재생 검증한 후보 사이의 비교") | 🔴 평가하지 못한 필드·후속·상대 자원 차이 |
| 🔴 "실전 최강·승률 평가가 아님" | 기존 탐색 예산 · 미지원 규칙 한계 (6-AH~6-AJ 그대로) |
| 🔴 "처음 도달한 시점" | 🔴 같은 문장 (요약에서 잘려도 첨부에 남는다) |

🔴 **길이 제한 때문에 추천이나 제한 설명이 잘리지 않게** 범위·시점 문장을
요약과 상세에 **둘 다** 적고, 기존 요약·첨부 구조(6-AE)를 그대로 쓴다.

## 6. 실측 — 실제 오르페골 입력

🔴 아래는 **이번 구현에서 실제로 돌려 얻은 것**이다. 적어 둔 전개 경로
(`ORCUST_GIRSU_LINE` 의 수순)를 **호출하지 않았다** — 그 상수에서 가져온 것은
레시피와 시작 패, 즉 **입력**뿐이다.

예산은 CLI 기본값이고 `--results 3` 이다. 탐색 결과: 검증된 서로 다른
결과 **3개** (불일치 0 · 예외 0 · 시간 초과 0 · 미시작 0), 종료 사유
`max_results=3`.

**기본 응답의 추천 절** (실행 출력 그대로, 긴 줄만 접었다):

```
  추천 — 어느 후보를 먼저 볼까
    평가 정책: resource-preservation v1 (자원 보존 중심의 제한적 휴리스틱)
    검증된 후보 3개
    공동 후보: 결과 1 · 결과 2  — 🔴 **둘 이상입니다**: 장단점이 갈리거나
      동률이고, 억지로 하나로 줄이지 않았습니다.
    [결과 1] 이번 자원 보존 기준(resource-preservation v1)의 추천 후보입니다.
      패 3장을 남겼고 일반 소환권을 사용했습니다. 비흐름 행동은 4회입니다
      (흐름 행동 0회는 비용으로 세지 않았습니다). 다른 추천 후보와 **두 보존
      축이 같습니다**: 결과 2: 비흐름 행동이 5회입니다 (🔴 비흐름 행동은
      **표시 순서 기준**일 뿐이고 보존 축이 아닙니다 — 두 보존 축은
      같습니다) — 🔴 어느 쪽이 더 좋은지 고르지 않았습니다.
    [결과 2] … 비흐름 행동은 5회입니다 … (같은 꼴)
    🔴 **탐색에서 발견하고 재생 검증한 후보 사이의 비교**입니다 — 자원 보존
      중심의 제한적 휴리스틱이고, **실전 최강·승률 평가가 아닙니다**. 상대의
      방해 대응력도 계산하지 않았습니다.
    🔴 **목표 카드에 처음 도달한 시점**의 후보 비교입니다 — 탐색이 목표에
      닿은 분기를 더 펼치지 않으므로, 전개를 끝까지 수행한 최종 집의 평가가
      아닙니다.
```

**상세 기록의 후보별 값** (실행 출력 그대로):

```
    후보별 평가 항목과 값
      [결과 1] ✔ 추천 · 표시 순서 1 · 남은 패 3장 · 일반 소환권 사용
               · 비흐름 행동 4회 (흐름 0회는 비용에서 제외)
      [결과 2] ✔ 추천 · 표시 순서 2 · 남은 패 3장 · 일반 소환권 사용
               · 비흐름 행동 5회 (흐름 0회는 비용에서 제외)
      [결과 3] — 비추천 · 표시 순서 - · 남은 패 2장 · 일반 소환권 사용
               · 비흐름 행동 6회 (흐름 0회는 비용에서 제외)
        이번 두 보존 축에서 다른 후보에 밀렸습니다 — 밀린 상대: 결과 1 ·
        결과 2 (두 축 모두 나쁘지 않고 최소 한 축이 더 낫습니다). 🔴 그쪽이
        게임 전체에서 더 좋다는 뜻은 아닙니다. …
```

### 6.1 읽는 법

| 결과 | 남은 패 | 일반 소환권 | 비흐름 행동 | 판정 |
|------|---------|-------------|-------------|------|
| 1 | 3장 | 사용 | 4회 | ✔ 추천 (표시 순서 1) |
| 2 | 3장 | 사용 | 5회 | ✔ 추천 (표시 순서 2) |
| 3 | 2장 | 사용 | 6회 | — 결과 1 · 2 에 밀렸다 |

- **결과 1 과 2 는 공동 후보다.** 두 보존 축이 **똑같고**(패 3장 · 소환권
  사용) 다른 것은 비흐름 행동 수뿐이다 — 그것은 **표시 순서 기준**이므로
  결과 1 을 먼저 적고, 🔴 **결과 1 이 더 좋다고 말하지 않는다.** 출력이
  "두 보존 축이 같습니다" 라고 적고 "장단점이 갈립니다" 라고 적지 **않는
  것**이 그 구분이다.
- **결과 3 은 밀렸다.** 패가 1장 적고 소환권도 썼으므로 두 축 모두 나쁘지
  않은 후보가 있다. 🔴 그래도 "결과 3 이 나쁘다" 가 아니다 — 결과 3 은
  세트를 한 장 더 했고(§6 의 기존 자원 비교), **그 세트가 무엇을 막는지는
  이번 기준이 판단하지 못한다.**
- 🔴 **세 결과는 세트 장수와 묘지 한 장 차이다.** 전략적으로 완전히 다른
  전개를 셋 찾은 것이 아니고, 보고가 그렇게 적지도 않는다
  (`test_d05` 가 "최강" · "승률" · "총점" · "점수" · "전략적으로" 의 부재를
  센다).

production 평가 함수(`rank_results`)와 production 렌더러를 그대로 부른다** —

## 8. 남은 한계

1. 🔴 **강한 집 평가가 아니다.** 자원 보존 두 축과 표시용 행동 수뿐이고,
   §4 의 차이들은 판단하지 못한다.
2. 🔴 **처음 도달한 시점**의 비교다 (§4 마지막).
3. 🔴 **비지배가 가지치기 근거가 아니다** — 밀린 후보가 실제로 더 좋을 수
   있다.
4. 🔴 **돌려준 후보가 가능한 모든 전개가 아니다** — 탐색 예산과 지원 범위가
   그대로 남아 있다(6-AI §6 · 6-AJ §9).
5. 🔴 **상대의 선택을 탐색하지 않는다**(무방해는 명시적 정책이다). 승률도
   방해 대응력도 계산하지 않았다.
6. 평가 불가 결과는 **추천되지 않은 채** 사유와 함께 남는다 — 버리지도,
   유리한 기본값으로 메우지도 않는다.
