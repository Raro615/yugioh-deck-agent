## 3. SearchPolicy 가 Duel 을 들지 않는 이유

Phase 3-A 가 정한 경계는 **정책에게 `Duel` 도 `GameState` 도 가지 않는다**였다.
그런데 시뮬레이션에는 복제할 판이 필요하다. 이것을 Engine 변경 없이 푼 방법:

`Simulator` 를 **좁은 창**으로 두고, 정책은 그 창만 들고 있다.

- `decide(view, legal)` 의 **인수는 그대로 둘**이다 — 3-A 의 AST 시험이 그대로 통과한다
- 시뮬레이터가 돌려주는 것은 `SimulationResult` 이고, 그 안에 **판을 담는 칸이 없다**
  (`{action, status, viewer, reason, code, future}` — `future` 는 `GameStateView`)
- 그래서 정책은 판을 바꿀 수단도, 가려진 정보를 읽을 수단도 **구조적으로** 갖지 못한다

`search.py` 와 `evaluation.py` 에 `state` · `clone` · `project` · `randomness` ·
`set_result` 라는 이름이 **하나도 없다**는 것을 AST 시험이 지킨다.

## 5. Evaluation — 단위는 LP 하나다

가중치를 임의의 점수로 두면 "왜 100 인가" 에 답할 수 없다. 그래서 모든 항을
**"이것을 얻기 위해 LP 를 얼마까지 내줄 것인가"** 로 적었다.

| 항 | 값 | 뜻과 근거 |
|---|---|---|
| `terminal` | **등급** (숫자 아님) | WIN > ONGOING > DRAW > LOSS. 아래 설명 |
| `lp` | 내 LP − 상대 LP, **×1** | 실제 승리 조건. 단위의 기준점 |
| `atk` | (내 필드 공격력 − 상대) × **1** | **환산이 필요 없다** — 공격력은 그대로 LP 로 들어오는 피해다 |
| `monsters` | (내 몬스터 − 상대) × **500** | 공격력과 별도. 한 마리 더 있으면 한 번 더 때리고 한 번 더 막는다 |
| `spells` | (내 마법·함정 − 상대) × **300** | 몬스터보다 낮다 — 지금 **발동이 후보에 오르지 않는다** (3-B 측정 0회) |
| `deck` | (내 덱 − 상대 덱) × **300** | **자원 중 가장 무겁다.** 지금 도달 가능한 패배 조건이 덱아웃 하나이므로 덱의 한 장은 패배로부터의 거리 1 이다 |
| `hand` | 내 패 장수 × **200** | 아직 쓸 수 없는 자원. **상대 패는 세지 않는다** (§26 — 장수는 보이지만 값은 모른다) |
| 묘지·제외 | **세지 않는다** | 0 점으로 두지 않고 `excluded` 에 적는다 — 지금 되살릴 수단이 후보에 없다 |

### 승리를 "매우 큰 수" 로 적지 않았다

§22 는 "WIN → 매우 높은 평가" 를 제안하지만, 큰 수는 휴리스틱 항이 자라면
**조용히 추월당하고** 그때 AI 는 이기는 수를 버린다. 그래서 `Terminal` 을
**등급**으로 두고 비교를 `(등급, 휴리스틱)` 로 했다 — 등급이 다르면 휴리스틱을
아예 보지 않으므로 추월이 **불가능하다**. 시험은 휴리스틱에 10¹² 를 넣어도
순서가 뒤집히지 않는 것을 확인한다.

`DRAW < ONGOING` 인 이유: **진행 중인 판은 아직 이길 수 있고 무승부는 더 이상
이길 수 없다.** (지금 엔진에 무승부를 만드는 자리는 없다.)

### 모르는 것을 0 으로 바꾸지 않았다 (§20 · §28)

| 모르는 것 | 처리 |
|---|---|
| 공격력이 `?` 인 몬스터 | 합에서 **제외** + `excluded` 에 기록 |
| 정의가 없는 카드 (상대 뒷면) | 합에서 **제외** + 기록 |
| 상대 패의 값 | 합에서 **제외** + 기록 |
| 묘지·제외 존 | 합에서 **제외** + 기록 |

그래서 **실제 듀얼의 모든 평가는 부분 평가**(`StateValue.partial`)다 — 상대 패의
값을 모르기 때문이다. 그것을 "다 재었다" 고 적지 않는다.

`UNKNOWN` 으로 끝난 시뮬레이션의 후보는 **점수가 아예 없다**(`value is None`).
0 점도 최저 점수도 아니다. 점수 있는 후보들 뒤에 서지만 그것은 "나쁘다" 가 아니라
**"견줄 수 없다"** 는 뜻이고, 점수 있는 후보가 하나도 없으면 고르기는 하되
`"견줄 수 있는 후보가 없었습니다 — 내다보지 못한 채 결정론적 순서로 골랐습니다"`
라고 흔적에 남긴다.

## 6. Simulation Safety

| 항목 | 결과 | 어떻게 확인했나 |
|---|---|---|
| original state unchanged | **YES** | `state_hash` + `draws` + 턴 + 페이즈 + `step` + `priority` + `result` + 양쪽 LP + 덱·패·필드·묘지·제외의 **instance_id 순서**까지 비교 |
| clone independence | **YES** | 후보 A·B 를 각 사본에 두면 세 판이 따로 존재하고, 각 사본의 필드에는 **자기 수만** 반영 |
| RNG isolation | **YES** | 사본의 난수원을 50회 돌려도 원본 `draws` 그대로. `project()` 는 같은 일에서 원본을 오염시킨다 (실측 대조) |
| hidden information protection | **YES** | 미래 관측의 `opponent.hand.cards == ()`, 양쪽 `deck.cards == ()`, 내 패만 `is_identified` |
| determinization | **NO** (하지 않았다) | 상대의 가려진 카드를 추측해 world 를 만들지 않았다 (§19) |

### 탐색이 승리를 "보았는데" 진짜 판은 끝나지 않았다

가장 강한 확인이다. 상대 LP 를 0 으로 둔 판에서 탐색을 돌리면 모든 후보의 미래가
`WIN` 으로 나온다. 그런데 **`duel.is_over` 는 여전히 False** 이고 `board_snapshot`
도 그대로다 — 탐색이 승리를 본 것이지 만든 것이 아니다.

### 주의: 지금은 RNG 격리를 "게임을 돌려서" 확인할 수 없다

측정: 듀얼 한 판 전체에서 `randomness.draws` 가 **2 에서 한 번도 움직이지
않는다** (초기 셔플 2회가 전부). 즉 **현재 행동 공간에는 난수를 꺼내는 수가
없다.** 그래서 `clone` 을 `project` 로 바꿔도 §11/§14 식 시험은 통과한다 —
실제로 그 둘만 두고 고의 위반을 심었을 때 통과했다.

그래서 `test_16_rng_isolation` 은 **사본의 난수원을 직접 돌려서** 격리를 확인한다.
이 시험만이 `project` 치환을 잡는다. 이것을 숨기지 않고 적어 둔다.

| | |
|---|---|
| 규칙기반과 탐색이 **같은 수** | **200곳** |
| 다른 수 | **0곳** |

이유는 분명하다. 지금 행동 공간에서 한 수 뒤의 판은 현재 판과

바꾸는** 자리이고, 지금 엔진에는 그런 자리가 없다.

## 11. ATTACK 제한의 영향 (§46)

Phase 3-B 측정 그대로 **`ATTACK` 은 후보에 오르지 않는다.** 이번 Phase 에서
그것을 고치지 않았고, **Engine 을 한 줄도 수정하지 않았다.**

그래서 다음은 **주장하지 않는다**:

- 탐색이 공격 전략을 고려했다 ✗
- 탐색이 전투 유불리를 계산했다 ✗
- 탐색이 LP 를 줄이는 길을 찾았다 ✗ (LP 는 8000 에서 움직이지 않는다)

이번 Phase 가 검증한 것은 **"현재 엔진이 내놓는 행동 공간 안에서, 한 수를 진짜로
해 보고 그 미래를 평가해 고를 수 있는가"** 하나다. 그리고 그것은 작동한다.

또한 탐색이 `ATTACK` 을 상상해도 **구조적으로 막힌다**: `search.py` 에
`PlayerAction` 을 만드는 자리가 없고(AST 확인), 시뮬레이터는 후보 목록에 없는
수를 `NOT_A_CANDIDATE` 로 되돌린다.

- **그때 한 일**: §2 의 금지 이름들을 `agent/` 코드에서 **부분 문자열**로 찾았다.
- **왜 틀렸나**: `ppo` 가 `supported` 안에서 걸린다. 금지하려던 것은 **이름**인데
  글자 조각을 찾고 있었다. Phase 3-B 시점에는 그런 이름이 없어서 드러나지 않았고,
  3-C 가 `SimulationStatus.SUPPORTED` 를 들여오면서 드러났다. 엔진의 어휘를
  바꿔서 시험을 통과시키는 것은 **거꾸로**다.
- **어떻게 고쳤나**: 코드를 **식별자 단위로 쪼개서** 집합 멤버십으로 본다
  (`re.findall(r"[A-Za-z_][A-Za-z_0-9]*", …)`). `train(` · `fit(` 은 토큰화가
  처리하므로 `train` · `fit` 으로 바꿨다. 더 정확해졌을 뿐 느슨해지지 않았다 —
  고의로 `rollout = 0` 을 심으면 여전히 깨진다 (확인).
- **삭제한 테스트**: 없음. 기대값을 완화한 테스트: 없음.
