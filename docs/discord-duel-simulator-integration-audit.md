## 3. Discord 인터페이스 조사

### 3.1 라이브러리 선택

| 후보 | 상태 | 판단 |
|---|---|---|
| **discord.py** | 유지보수 재개 후 현역. 슬래시 명령·버튼·`defer` 지원 | **권장**. 동기 코드가 많은 이 저장소에 붙이기 쉽고 `asyncio.to_thread` 로 분리 가능 |
| py-cord / nextcord | discord.py 포크 | 굳이 갈 이유 없음 |
| hikari + lightbulb | 저수준·고성능 | 이 규모에 과함 |

🔴 **의존성을 설치하지 않았다.** 현재 `requirements` 성격의 파일에 Discord
관련 패키지는 없고, 추가는 별도 단계다.

### 3.2 장시간 작업의 구조적 제약

Discord 상호작용은 **초기 응답 3초**, `defer` 후 **후속 15분**이라는 제약이
있다. 덱 구성 + 전개 탐색은 그보다 오래 걸릴 수 있다 (우리 저장소의 전체
분석이 분 단위인 것을 이미 측정했다).

그래서 **동기 응답을 전제로 설계하면 안 된다.**

```
/deck …  →  즉시 defer  →  job_id 발급  →  큐에 적재  →  즉시 "접수" 응답
                                              ↓
                                      워커가 단계별로 진행
                                              ↓
          단계가 끝날 때마다 follow-up 메시지 **편집**으로 진행 보고
                                              ↓
                            완료 시 결과 + (있으면) 리플레이 URL
```

### 3.3 상태 보고 · 실패 · 취소 · 재시도

| 요구 | 설계 |
|---|---|
| 상태 보고 | 작업을 **명시적 단계 열거형**으로 쪼개고(접수→후보선정→덱확정→전개탐색→검증→표현) 단계 전이마다 메시지 편집 |
| 실패 | 단계별 실패를 **구분해서** 보고한다. "실패" 하나로 합치지 않는다 — 이 저장소가 `UNKNOWN`/`MISMATCHED`/`UNPROVABLE` 을 합치지 않기로 정한 것과 같은 원칙 |
| 취소 | `job_id` 단위 취소 플래그. 워커가 단계 경계에서 확인 |
| 재시도 | **멱등성 키**(사용자 ID + 정규화된 요청 해시)로 중복 실행 방지. 같은 키의 진행 중 작업이 있으면 새로 돌리지 않고 기존 `job_id` 를 돌려준다 |
| 사용자별 식별 | Discord user ID + guild ID + `job_id`. 로그에는 **user ID 만** 남기고 표시 이름·토큰은 남기지 않는다 |

### 3.4 🔴 자연어 계층과 실행 계층의 분리

지시대로 분리한다. 그리고 **분리의 이유를 계약으로 고정한다**:

```
Request Parser   : 자연어 → StructuredRequest (테마/목표/제약)
                   실패 시 "해석 못 했다" 를 돌려준다. 추측해서 채우지 않는다
AI Orchestrator  : StructuredRequest → 단계 계획. 카드 지식 없음
Deck Builder     : 카드 지식 사용. Discord 를 모른다
```

이 저장소가 이미 같은 규율을 쓰고 있다 — `core/query_parser.py` 가 한국어
질의를 `SearchFilters` 로 바꾸고, 검색 엔진은 자연어를 모른다. **같은
패턴을 재사용하면 되고, 새 추상화를 만들 필요가 없다.**

### 3.5 토큰 관리

* 환경 변수만 사용 (`DISCORD_BOT_TOKEN`). 코드·설정 파일에 넣지 않는다.
* 저장소에 커밋되는 예시 파일에는 **플레이스홀더만**.
* 로그·에러 리포트·예외 메시지에 토큰과 비밀번호를 넣지 않는다. 특히
  장기 목표의 EDOPro **방 비밀번호**는 마스킹 대상이다.
* 이 저장소는 이미 `YGO_CARDS_CDB`·`YGO_KO_DIR` 환경 변수 관용구를 쓴다 —
  같은 방식으로 맞춘다.

| 외부 실행 환경 어댑터 | 없음 | — |
| 효과 컴파일러 (분석 결과 → 엔진 실행 정의) | **없다**. `STRUCTURAL-7` 로 지목되어 있음 | `engine/effect/library.py` docstring |

### 4.3 🔴 Engine V1 의 실제 실행 범위 — 가장 중요한 측정

엔진이 **실행할 수 있는 카드 효과 목록은 손으로 쓴 16개**이고, 그중
`executable=True` 는 **13개**다.

```
EFFECT_LIBRARY 항목 수 : 16
  executable=True      : 13
  executable=False     :  3
```

| 실행 | 카드 |
|---|---|
| ✅ | 욕망의 항아리 · 은혜의 단비 · 싸이크론 · 치료의 신 다이안 켓 · 욕망의 선물 · 갑부 고블린 · 육신보살 · 벌금 · 강제 탈출 장치 · 어리석은 매장 · 무정한 말살 · 의적의 입문서 · 리로드 |
| ❌ (의미만 확인) | 블랙홀 · 죽은 자의 소생 · 로스트 |

**13 / 14,127 = 0.09%.** 그리고 13개 전부 마법·함정이다.

더 결정적인 제약:

| 제약 | 실측 근거 |
|---|---|
| `PlayerActionKind` 는 **11종**: NORMAL_SUMMON · SPECIAL_SUMMON · SET_MONSTER · SET_SPELL_TRAP · ACTIVATE_CARD · ACTIVATE_EFFECT · CHANGE_POSITION · ATTACK · CHANGE_PHASE · END_PHASE · PASS | enum 열거 |
| `ACTIVATE_CARD` 는 **V1 에서 유효하지 않다** — 후보로 나오지 않고 `apply` 가 거절 | docstring + 검증 코드 |
| `SPECIAL_SUMMON` 은 **언제나 `UNKNOWN`** — `UnimplementedRule("special-summon-condition (카드마다 다르다)")` 가 붙는다 | `engine/action_validation.py:116·520·581` |
| **융합·싱크로·엑시즈·링크 소환 절차가 없다** — 코드에 있는 것은 `is_xyz` 플래그와 docstring 언급뿐 | 전수 grep |
| 파괴를 실행하지 않는다 (파괴 내성·대체·트리거가 없어서) | `engine/__init__.py` |
| 되돌리기·재생 없음 (ADR-008) | `engine/__init__.py` |
| Engine V1 은 Phase 2-AO 에서 **동결**됨 | `engine/__init__.py:945` |

🔴 **따라서**: "AI 가 전개를 계획하고 엔진으로 검증한다" 는 **지금 성립하지
않는다.** 현대 전개의 핵은 특수 소환(링크·엑시즈·융합·싱크로)이고, 엔진은
그것을 허가조차 하지 못한다. `agent/search.py` 의 탐색 골격은 살아 있지만
**탐색할 수 있는 행동 공간이 사실상 비어 있다.**

이것을 "엔진이 곧 지원할 것" 으로 가정하지 않는다. 지시 §4 가 금지한
가정이고, 실제로 금지할 만한 가정이다.

이것을 뒤로 미루면 안 된다. 자동화를 전제로 쌓은 설계가 전부 버려질 수

### 5.2 B. 브라우저 자동화 — 가능성과 취약성

전제: **허락을 받은 경우에 한해** 의미가 있는 분석이다.

| 항목 | 현재 말할 수 있는 것 |
|---|---|
| Playwright 로 페이지 제어 | 환경에 Chromium + Playwright 가 이미 있다 (`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`). **기술적으로는 가능**하다 |
| DOM 으로 요소 식별 | 🔴 **미확인 (U4).** 서버가 주는 것은 SPA 셸(`<div id="root">`)뿐이고 UI 는 번들이 그린다. 번들 분석은 규약 금지이므로 선택자를 **하나도 조사하지 않았다** |
| 드래그&드롭 자동화 | 조작이 드래그&드롭이라는 것은 확인됨(F8). HTML5 DnD 인지 pointer 이벤트인지 **미확인** — 이 차이가 자동화 난이도를 크게 가른다 |
| 이미지/OCR 접근이 필요한 경우 | **덱 입력에서 필요하다** (§5.3). 판 조작에는 원칙적으로 불필요 |
| 화면 변경·지연 로딩 취약성 | 🔴 **높다.** 규약이 조사 4일 전(2026-10-09)에 갱신됐고(F26), 제작자가 기능을 활발히 갱신 중이다(타임라인·동시 이동·듀얼 중 카드 생성). **선택자 기반 자동화는 상시 깨질 것으로 가정해야 한다** |

🔴 **요소 식별 방식에 대한 권고 (지시 §7)**: 선택자를 모르는 상태에서
설계할 수 있는 것은 **격리 전략**이다.

1. **모든 선택자를 한 파일에 모은다.** 자동화 코드에 선택자를 흩지 않는다.
   UI 가 바뀌면 그 파일 하나만 고친다.
2. **접근성 기반 식별을 1순위로 한다** (역할·이름). 클래스 해시는 번들
   빌드마다 바뀔 수 있어 최후순위다.
3. **다국어가 함정이다.** UI 가 ja/en/zh/ko 를 지원하므로(F18) 라벨
   문자열로 요소를 잡으면 언어 설정에 따라 깨진다. **언어를 고정하고
   그 사실을 기록**하거나, 라벨에 의존하지 않는다.
4. **조작 전후로 판 상태를 독립적으로 확인한다** (§5.4).

### 5.3 C. 덱 입력 — 🔴 가장 큰 위험

확인된 입력 경로는 **하나**다: 니어런에서 내보낸 **덱 이미지**(F1).
사이트는 그 이미지에서 카드를 **잘라내고**(F2), **이미지 특징을 照合해**
카드를 식별하며(F3), 머리글의 **장수만 OCR** 한다(F2).

이 구조가 뜻하는 것:

| 함의 | 설명 |
|---|---|
| 🔴 **카드 목록을 직접 넣을 길이 문서상 없다** | AI 가 고른 40장을 "텍스트로" 전달할 수 없다. **이미지를 만들어야 한다** |
| 🔴 **우리가 니어런 덱 이미지를 합성해야 한다** | 그런데 카드 **이미지**가 필요하다. 우리 저장소에는 카드 이미지가 **없다** — `cards.cdb` 는 텍스트·수치이고, 사이트의 照合 데이터도 "카드 이미지 파일을 포함하지 않는다"(F5) |
| 🔴 **카드 이미지 조달이 권리 문제다** | 규약 제6·7조가 카드 이미지 권리를 각 권리자에게 돌리고, 가이드라인 5 가 "이용할 권한이 없는 이미지를 읽어 공유 URL·리플레이로 공개하는 행위"를 금지한다 |
| 식별 오류가 **기대값**이다 | 운영자가 오류 존재를 명시(F6). 자동 입력은 **오식별 검증 단계가 필수**다 |
| 정정 경로는 있다 | 카드명 검색으로 교체 가능(F7) → 자동화 가능성은 있으나 단계가 늘어난다 |

**판단**: AI 가 구성한 덱을 **자동으로** 사이트에 넣는 것은, 지금 아는
범위에서 **현실적이지 않다.** 니어런 이미지 합성 + 권리 문제 + 오식별
정정이 겹친다. 반대로 **사용자가 자기 니어런 이미지를 직접 올리는 것**은
정상 사용 흐름이고 아무 문제가 없다.

→ 그래서 §8 의 MVP 는 **덱 입력을 자동화하지 않는 쪽**으로 잡는다.

### 5.4 D. 전개 실행과 결과 확인

🔴 **지시가 경고한 그대로였다. 이 사이트는 규칙을 집행하지 않는다.**

* 자기 설명이 "**盤面を動かせる**シミュレーター"(판을 움직일 수 있는)이고
  "デュエルを**再現**できる"(재현할 수 있는)다.
* 카드 메뉴의 `효과 발동`·`무효화`·`대상으로 잡기`(F9)는 **표시·연출용
  표식**이다. 발동 조건을 검사한다는 서술이 문서에 **없다**.
* 리플레이 후편집으로 **待機·컷인·턴 종료를 사람이 끼워 넣는다**(F14).
  규칙 엔진이라면 있을 수 없는 기능이다.

| 사이트가 하는 일 | 사이트가 하지 않는 일 |
|---|---|
| 카드 이동 재현 · 상태 표식 · 기록 · 재생 · 공유 | 발동 조건 검사 · 체인 처리 · 합법성 판정 · 승패 판정 |

**결론**: 사이트는 **표현(presentation) 계층**이다. 전개가 올바른지는
**전적으로 우리 쪽 책임**이다. 그리고 §4.3 에서 보았듯 우리 엔진도 그것을
검증하지 못한다. → **지금 단계에서 "검증된 전개" 를 만들 수 있는 주체가
양쪽 모두 없다.** 이 사실을 사용자에게 숨기지 않는 것이 설계 요구사항이다
(§6.4).

조작 결과 확인과 실패 감지 (지시 §5.D):

| 방법 | 평가 |
|---|---|
| 조작 **전후 판 상태를 우리가 따로 모델링**하고 비교 | 🟢 **1순위.** 사이트를 신뢰원으로 쓰지 않는다 |
| `조작 이력`/`타임라인` 패널을 읽어 조작 수 확인 | 🟡 보조. 선택자 미확인(U4) |
| 스크린샷 비교 | 🟡 느리고 취약. 최후 수단 |
| Undo 로 복구 | 🟢 **있다**(F10). 실패 시 되돌릴 수 있다는 것은 중요한 안전장치 |
| 구간 기록(F15) | 🟢 실패 구간만 다시 기록 가능 |

리플레이 링크 획득: 기능은 확실히 존재한다(F11·F12). 다만
**보존을 보장하지 않고**(F16) **접근 제어가 없으며**(F13) **이용자가 삭제할
수 없다**(F17). → Discord 에 뿌린 URL 은 **영구 산출물로 취급하면 안 되고**,
공개돼도 문제없는 내용만 담아야 한다.

## 6. AI 덱 구성과 전개 계획 — 구현 순서

### 6.1 지금 가능한 것 / 불가능한 것

| 단계 | 가능성 | 근거 |
|---|---|---|
| 테마 → 카드 후보 집합 | 🟢 **지금 가능** | `by_archetype`·`by_setcode`·`relations_for_term` 이 있다 |
| 후보의 효과 성질 요약 | 🟢 가능 (단 §6.4) | 효과 블록 34,635개 |
| 매수 결정 | 🟡 **규칙을 새로 써야 함** | 로직 없음 |
| 덱 규격 검증 (40~60·EX 15·3장) | 🟡 쉬움, 다만 없음 | 금지제한 데이터 출처는 별도 확인 필요 |
| 테마 간 시너지 판정 | 🟡 부분적 | 관계 모델은 있으나 "시너지" 는 정의되지 않음 |
| 소환 조건 검증 | 🔴 **불가능** | 특수 소환이 언제나 `UNKNOWN` (§4.3) |
| 초기 패 분포 | 🟢 가능 (조합 계산) | 엔진 불필요 |
| 전개 경로 탐색 | 🔴 **불가능** | 행동 공간이 비어 있다 (§4.3) |
| 전개 결과 평가 | 🔴 불가능 | 위와 동일 |

### 6.2 그래서 순서를 이렇게 바꾼다

원래 목표는 "덱 구성 → 전개 계획 → 시뮬레이터 실행" 순이지만, **전개 계획이
막혀 있다.** 막힌 단계를 건너뛰고 뒤를 만들면 "검증되지 않은 전개를 성공으로
처리" 하게 된다 — 지시 §6 이 금지한 것이다.

```
1단계  테마 → 후보 집합 + 매수 제안 + **근거와 UNKNOWN 명시**   ← 지금 가능
2단계  덱 규격·금지제한 검증                                      ← 지금 가능
3단계  초동 확률 계산 (엔진 없이)                                 ← 지금 가능
──────────── 여기까지가 엔진에 의존하지 않는 영역 ────────────
4단계  효과 컴파일러 (STRUCTURAL-7) — 분석 결과 → 실행 정의        ← 큰 작업
5단계  특수 소환 조건 계층 + 소환법 절차                           ← 큰 작업
6단계  전개 경로 탐색                                             ← 4·5 이후
7단계  시뮬레이터 표현 (허락 전제)                                 ← 별개 축
```

🔴 **1~3 단계는 Duel Simulator 와 Discord 없이도 가치가 있고, 검증도
가능하다.** 4~6 은 Engine V1 동결을 푸는 결정이 필요한 별도 사안이다.

### 6.3 출력 형식 (지시 §6 예시 대응)

```
테마: 오르페골 + K9 / 목표: 초동 안정성
→ 메인 덱 (매수 포함) · 엑스트라 덱 · 카드별 채용 이유
→ 🔴 "불확실한 카드 효과" 섹션을 **필수 항목으로** 둔다
```

### 6.4 🔴 불완전한 정보와 UNKNOWN 처리 — 기존 계약을 따른다

이 저장소는 이미 다음을 정해 두었고, Phase 4 가 그것을 깨면 안 된다:

* 파싱할 수 없는 효과를 **추측해서 구조화하지 않는다**.
* `UNKNOWN` 을 임의로 `true`/`false` 로 바꾸지 않는다.
* 근거(출처) 계층과 증명 계층을 **합치지 않는다** (Phase 3-F-40).
* 실행은 `LUA_VERIFIED` + 등록된 구현일 때만 (ADR-004·006).

따라서 Deck Builder 의 출력에는 카드마다 **(근거, 증명, 실행가능)** 세
상태가 따라붙어야 하고, "AI 가 이 카드 효과를 이해했다" 고 말해서는 안 된다.
덱 추천은 **검색·분류·통계 근거**로 제시하고, 전개 성공 주장은 하지 않는다.

## 7. 아키텍처 — 역할 분리와 EDOPro 경계

### 7.1 계층

```
Discord Adapter      슬래시 명령 · defer · follow-up 편집 · job 상태
      │  StructuredRequest
Request Parser       자연어 → 구조화. 못 하면 "못 했다"
      │
AI Orchestrator      단계 계획 · 취소 · 멱등성. 카드 지식 없음
      ├── Deck Builder       core/card_search + analysis 재사용
      ├── Combo Planner      agent/policy·search 재사용 (단 §4.3)
      │
Execution Adapter    (추상) 외부 실행 환경
      ├── DuelSimulatorAdapter   표현 전용 · 허락 전제
      └── EdoProAdapter          미구현
      │
Result Validator     우리 모델과 외부 상태 비교
Replay/Artifact      URL · 보존 보장 없음(F16) 명시
```

### 7.2 🔴 Duel Simulator 와 EDOPro 를 같은 인터페이스로 묶지 않는다

지시가 경고한 그대로, 억지로 묶으면 안 된다. 성질이 **근본적으로 다르다**:

| | Duel Simulator | EDOPro |
|---|---|---|
| 규칙 집행 | **없음** (§5.4) | **있음** (ocgcore) |
| 우리 역할 | 판을 그려 보여 준다 | 규칙에 **응답**해야 한다 |
| 실패의 의미 | 표현이 틀렸다 | 행동이 불법이었다 |
| 입력 | 덱 **이미지** | `.ydk` 덱 파일 |

**공통화할 수 있는 것**은 데이터뿐이다: 덱 목록, 전개 계획(행동 열),
결과 산출물 참조. **공통화하면 안 되는 것**: 합법성 판정의 주체. 한쪽은
우리가, 다른 쪽은 서버가 가진다.

→ 공통 인터페이스는 `제출(덱) → 실행(계획) → 산출물(참조)` 수준으로 얕게
두고, 그 아래는 각자 다르게 둔다.

### 7.3 EDOPro 확장 — 조사 결과

| 항목 | 확인된 것 | 미확인 |
|---|---|---|
| WindBot 계열 참고 가능성 | WindBot 은 **C#** 이고 YGOSharp/SRVPro 서버 호환으로 설명된다. CLI 로 `Deck`·`DeckFile(.ydk)`·`Host`·`Port`·비밀번호 옵션을 받고, HTTP 로 봇 생성을 받는 "server" 모드가 있다 | 실제 와이어 프로토콜. 우리 Python 스택과의 통합 방식 |
| 🔴 중요한 한계 | WindBot 문서가 **"봇의 원래 덱에 없는 카드는 대부분 모르고, 소환·발동하지 않는다"** 고 명시 | — |
| 현재 서버 프로토콜 호환성 | **미확인.** EDOPro 는 YGOPro 포크이고 누적 변경으로 **이 포크에서 파생되지 않은 시뮬레이터와 호환되지 않는다**고 설명된다 | 버전별 호환성 |
| 필요한 별도 계층 | 서버 접속 · 방 참가 · 비밀번호 · 덱 전달(.ydk) · 행동 응답 — **전부 없음** | — |

🔴 WindBot 의 한계가 중요하다. 그것을 참고해도 "덱에 있는 카드만 아는 봇"
이 되고, 그것은 우리가 §4.3 에서 본 한계와 **같은 종류**다. EDOPro 연결은
이번 단계에서 구현하지 않으며, **규칙 응답 능력이 생긴 뒤에나 의미가 있다.**

### 8.3 MVP 성공 기준

🔴 **MVP 에서 Duel Simulator 자동화와 전개 자동 계획을 제외한다.** R1·R2·R3
가 전부 치명이고 세 개 중 둘은 우리가 풀 수 없다.

**MVP = Discord 에서 테마를 주면 근거 있는 덱 초안을 돌려준다.**

| 성공 기준 | 측정 방법 |
|---|---|
| `/deck theme:"…" goal:"…"` 로 메인 40~60 · EX ≤15 · 동일명 ≤3 을 만족하는 덱 초안이 나온다 | 규격 검증 테스트 |
| 카드마다 **채용 이유**와 **(근거·증명) 상태**가 붙는다 | 출력 검사 |
| 불확실한 카드 효과가 **별도 섹션**에 열거된다. 추측 0건 | 출력 검사 |
| 전개 성공을 **주장하지 않는다** | 출력에 금지 문구 부재 확인 |
| 3초 내 응답(defer) · 완료 시 follow-up 편집 | 수동 확인 |
| 토큰이 로그·커밋에 없다 | grep + 환경 변수 확인 |
| 같은 요청 중복 실행 안 됨 | 멱등성 키 테스트 |

리플레이 공유는 **사용자가 수동으로** 사이트를 쓰고 URL 을 붙이는 흐름으로
두면 규약 범위 안에서 지금도 가능하다 (F22).
