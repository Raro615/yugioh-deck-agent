### 3.3 자료가 충돌한 자리와 수정한 기존 해석

🔴 **충돌 하나를 찾았고, 틀린 쪽은 이 저장소의 기존 해석이었다.**

Phase 6-AA 는 *"임의 유발은 controller 를 강제하지 않는다"* 에서
*"그러므로 임의 유발은 페이즈 전환을 막지 않는다"* 를 끌어냈고
(`test_b01` 이 그 문장을 들고 있었다), 6-AB 보완은 *"그 확인 자리에서 유발
대신 다른 일을 골랐다면 그 자리의 기회는 지나간 것이다"* 로 기회 종료를
구현했다 (`test_b02`).

그 둘이 공식 Fast Effect Timing 도표와 충돌한다. 도표는 **판이 열린
상태(box A)** 에서만 할 수 있는 행동을 따로 적고, 유발 처리 기회는 box A 가
아니다. 그래서 *"다른 일을 고른다"* 는 선택지가 **애초에 없다.**

| 항목 | 전 해석 | 정정 |
|---|---|---|
| 임의 유발의 포기 | 적법한 **다른 행동**으로 한다 | **`PASS` 한 걸음**으로 한다 |
| 임의 유발과 페이즈 전환 | 막지 않는다 | **막는다** — 판이 열린 상태가 아니다. 포기 한 걸음 뒤에 열린다 |
| 강제 · 임의의 구분 | 강제만 흐름을 막는다 | **그대로 남는다** — 임의면 `PASS` 가 오르고, 강제면 오르지 않는다 |

🔴 **그 전 해석이 BLOCKER-F3-1 을 만들었다.** 내 일반 행동 하나가 상대의
미처리 기회까지 닫았다 (§4.1 의 실측). 즉 "포기를 어떻게 적는가" 를 느슨하게
둔 것이 규칙이 보장해야 할 처리를 조용히 지우는 길이었다.

🔴 **해결되지 않은 것은 UNKNOWN 으로 남겼다.** *"강제 「때」 효과는 타이밍을
놓치지 않는다"* 는 이번에도 공식 문언을 찾지 못했다. 첨부 문서 §7.1 은
그렇게 적지만 (*"'때' 임의 효과만 타이밍을 놓친다"*) 비공식 정리본이므로
근거로 쓰지 않았고, `_missed_timing` 은 그 조합을 계속 `None` 으로 둔다.

## 4. 양측 유발 등재 · 포기 · 응답 · 해결의 상태 전이

### 4.1 재현한 결함 둘 (A · B)

**A — 내 일반 행동이 상대의 기회를 닫는다** (BLOCKER-F3-1). 실측:

```
내 claims 1 · 상대 claims 1 · _window_actor()=0 · to_act=0
내 허가 ['activate_effect', 'end_phase', 'pass', 'set_spell_trap']
🔴 내 세트 수락 True
🔴 세트 뒤 상대 claims 0 · _window_actor() None
🔴 내 END_PHASE 수락 True · 페이즈 BATTLE
```

**B — 첫 등재가 응답 단계를 열어 남은 묶음이 사라진다.** 실측:

```
제안 2 · 후보 ['69811710:e[1]', '69811710:e[0]']
발동 전 priority.is_open=False
🔴 첫 등재 뒤 priority.is_open=True · 보유 1 · 체인 1
   남은 내 유발 후보 ['69811710:e[0]']   ← 제안은 남았는데
   _window_actor() None · to_act 1       ← 아무도 묻지 않는다
   to_act 자리의 허가 ['pass']
```

(`test_a02` 가 센다).

### 4.3 각 요구에 대한 대응

| 요구 (이번 지시 §3-①) | 대응 |
|---|---|
| 내 임의 유발은 포기할 수 있다 | `_flow_actions` 가 **임의 묶음**일 때 `PASS` 를 올린다. 강제 묶음이면 올리지 않는다 |
| 내 포기가 상대의 미처리 기회를 없애지 않는다 | 포기는 `window_passed` 에만 적히고 `window_floor` 를 옮기지 않는다. 상대의 claims 는 그대로다 (`test_a01`) |
| 필요한 양측 처리가 끝난 뒤 일반 행동 · 페이즈 이동으로 돌아간다 | `_window_actor()` 가 `None` 이 되면 `_enforce_mandatory` 가 좁히지 않는다 (`test_a02`) |
| 다른 행동 요청을 포기로 처리하는 기존 방식을 유지한다면, 적용 전에 상대 기회를 보장한다 | **그 방식을 버렸다** — 더 단순하고 안전한 쪽(명시적 `PASS`)으로 정리했다. 지시의 둘째 선택지다 |
| 과거 테스트가 즉시 일반 행동 · 페이즈 이동을 요구하면 정정한다 | 일곱 건을 정정했다 (§8) |

### 4.4 `PASS` 의 세 가지 뜻 — 그대로다

최종 보완이 세운 구분이 유지된다. 단계는 `priority` 가 열려 있는지와 등재
자리가 있는지로 갈린다.

| 단계 | `PASS` 가 하는 일 |
|---|---|
| `priority.is_open` | 체인 응답 · 빠른 효과 응답의 포기 (`priority.passed()`) |
| 닫혀 있고 내 등재 자리다 | **유발 처리 기회의 포기** (`window_passed`), 그리고 그것이 마지막 묶음이었으면 **응답 단계를 연다** |
| 둘 다 아니다 | 통상 우선권 넘김 |

### 4.5 교착을 만들지 않는다

`_window_can_act(seat)` 가 **관문까지** 본다. 그러지 않으면 관문이 막은
claim 으로 자리를 가리키면서 다른 자리를 막아 **양쪽 다 고를 것이 없어
듀얼이 멈춘다**. 실측(고치는 중에 한 번 만들었다):

```
상대 강제 claims 1 (관문이 거절: 자신이 쥐고 있는 카드가 아니다)
🔴 _window_actor()=1 · 내 허가 [] · 상대 허가 []      ← 교착
```

지금은 그 자리를 건너뛰고, **미지원 사유를 잃지 않는다** —
`MANDATORY_TRIGGER_UNPLAYABLE` 검사를 `to_act` 비교보다 앞으로 옮겼기
때문이다. 실측:

```
상대 자리 보류:
  None                              69811710:e[0] … 자신이 쥐고 있는 카드가 아닙니다.
  '우선권을 여는 규칙 (Phase 2-F)'    우선권이 열려 있지 않습니다.
  '강제 유발의 발동 절차 (6-AB …)'    강제 유발 1건이 열려 있는데 발동 관문을 …
P0 허가 ['end_phase', 'set_spell_trap']   ← 흐름은 막지 않는다
```

🔴 **임의 묶음일 때는 관문을 다시 돌리지 않는다** — `PASS` 가 있으므로 고를
것이 반드시 있다. 비용을 치르는 자리를 강제 묶음 하나로 좁혔다.

## 5. 원본 · 사본의 정의 보존과 분기 격리

### 5.1 재현한 결함 (C)

```
원본 후보 ['69811710:e[0]', '69811710:e[1]']
🔴 사본 후보 ['69811710:e[0]']
원본 정의 등재 True
🔴 사본 정의 등재 False
```

`Simulator._fork` 가 `duel_components()` 로 수행기 한 벌을 **새로** 만들고,
그 등록부는 `definition_registry()` · `implementation_registry()` —
**프로덕션 목록**에서 나온다. 그래서 원본 듀얼이 자기 등록부를 들고 있으면
사본이 그것을 잃었다.

🔴 **최종 보완은 이것을 "올바른 설계" 로 적었다** (`test_e04` 의 이름이
`a_fork_rebuilds_the_production_registry` 였다). 그 판단이 틀렸다 — 사본이
원본보다 **못 해결하면** 미래의 값이 규칙이 아니라 **배선** 때문에 달라진다.
``_forked_journal`` · ``_forked_chooser`` 가 이미 고친 것과 같은 결의 결함이다.

### 5.2 고친 방식 — 불변은 공유, 변경 가능은 격리

```
Simulator._forked_definitions()      원본의 두 등록부를 꺼내 준다 (읽기만)
        │  definitions = duel._activator.definitions
        │  implementations = duel._activator.lookup
        ▼
duel_components(definitions=…, implementations=…)
        │  🔴 **같은 내용의 새 등록부**를 만든다
        │     EffectDefinitionRegistry(definitions.definitions())
        │     EffectImplementationRegistry(implementations.refs())
        ▼
duel_activator(…) · duel_resolver(…) · build_executor(implementations=…)
```

| 무엇 | 공유 / 격리 | 왜 |
|---|---|---|
| `EffectDefinition` 객체 | **공유** | frozen 이다 — 바뀌지 않으므로 분기가 서로를 볼 수 없다 |
| `EffectRef` | **공유** | 값이다 |
| `EffectDefinitionRegistry` | **격리** (새 객체) | `register()` 가 있다 — 한 분기의 등록이 다른 분기에 보이면 안 된다 |
| `EffectImplementationRegistry` | **격리** (새 객체) | 같은 이유 (`register()`) |
| `EventJournal` | **격리** | 이미 그랬다 (`_forked_journal`, Phase 6-B · 6-AB) |
| 해결 시점 정책 | **격리** | 이미 그랬다 (`_forked_chooser`, 최종 보완) |
| 난수 | **격리** | `state.clone()` 이 가져간다 |
| 기회 상태 (`window_passed` · `window_floor` · `chain_floor`) | **격리** | 값(`frozenset` · `int`)이므로 `dataclasses.replace` 가 복사한다 |

🔴 **``agent`` 가 ``engine.effect`` 를 직접 import 하지 않는다.** 사본을
만드는 쪽은 꺼내 주기만 하고, 복사는 ``engine.spell_activation`` 한 자리에서
한다.

### 5.3 실측 — 사본이 원본과 **같은 결과**를 낸다

`test_e05_synthetic_a_fork_resolves_the_two_link_chain_like_the_original`:

```
원본 후보 = 사본 후보 = ['69811710:e[1]', '69811710:e[0]']
사본 링크 [(0, '69811710:e[1]'), (1, '69811710:e[0]')]
사본 EffectEvent ['69811710:e[0]', '69811710:e[1]']        ← 역순
사본 묘지/덱/패 1/33/5                                      ← 원본 경로와 같은 값
🔴 원본은 그대로: 체인빔 True · 후보 2 · EffectEvent 0
```

🔴 **"누락을 미지원으로 표시" 로 끝내지 않았다** — 지시가 금지한 자리다.
사본이 실제로 **같은 후보를 만들고 같은 결과로 해결한다.**

형제 분기 격리 (`test_c04` · `test_e01` · `test_e02`):

```
left.window_passed [0] · right [] · 원본 []
left 정의 is right 정의 = False
```

## 6. 실제 카드 검증과 합성 검증의 구분

### 6.1 조사 — 실제 카드로 양측 시나리오를 만들 수 있는가

**없다.** 실측으로 확인했다.

| 항목 | 값 |
|---|---|
| `EFFECT_LIBRARY` 항목 | 18 (실행 구현 등재 **15**) |
| 그 가운데 `ActivationKind.TRIGGER` | **1** — `69811710:e[0]` (기르수 ①) |
| 그 가운데 `ActivationKind.IGNITION` | 1 — `37742478:e[0]` |
| 기르수의 등재된 효과 | `69811710:e[0]` **하나뿐** (② 는 `EFFECT_TYPE_IGNITION` 이고 등재되지 않았다) |

그래서 **상대의 카드가 내 소환 사건에 유발하는 실제 카드가 없다.** 양측이
같은 사건의 기회를 갖는 자리는 실제 카드로 만들 수 없다.

🔴 **같은 카드 여러 개체도 안 된다.** 기르수 2장을 같은 기회에 소환하려면
**일반 소환이 턴에 두 번** 필요하고, 특수 소환은 이번 범위 밖이며 실행
구현도 없다. 카드명별 횟수 제한은 지켰다 (기르수는 금제상 3장까지이고,
막은 것은 소환권이다).

### 6.2 그래서 무엇을 합성했는가

| 합성한 것 | 어떻게 | 왜 |
|---|---|---|
| **보드 배치** | 상대 덱의 기르수 한 장을 `GameState.move` 로 상대 몬스터 존(앞면 공격)으로 | 그러지 않으면 발동 관문이 *"자신이 쥐고 있는 카드가 아닙니다"* 로 거절한다. 🔴 최종 보완의 `_TheirDuty` 가 그 상태였고, 그래서 그 시험이 **처리할 수 없는 의무**로 "의무가 막는다" 를 재고 있었다 |
| **제안의 자리 · 효과 칸 · 필수 여부** | `dataclasses.replace(offer, controller=…, source=…, effect_ref=…, requirement=…)` | 상대 쪽 유발이 실제로 등재되어 있지 않다 |
| **상대 쪽 효과의 내용** | 기존 공통 연산 `DrawOperation(count=1)` 하나 (`SYNTH_REF`, 최종 보완이 만든 정의) | 대상 선택이 없어 상대 덱의 **내용**에 기대지 않는다. 상대 덱은 `build_opening` 이 채우는 채움 덱이다 (실측: 같은 카드 40장) |

🔴 **주입하지 않은 것**: 허가 · 체인 링크 · 소비 기록 · 최종 상태. 전부
`legal_actions` → `_activation_gate` → `Duel.apply` → `ChainResolver` 가
만든다. 행동은 모두 후보 목록을 지난다.

🔴 **실제 카드 지원이 완료되었다고 보고하지 않는다.** ②가 증명한 것은
**엔진이 네 묶음 순서로 등재하고 등재가 끝난 뒤 응답을 연다**는 것이고,
그렇게 할 실제 카드 조합이 이 저장소에 등재되어 있다는 것이 아니다.

### 6.3 실제 카드 검증 — 그대로다

| 시험 | 재는 것 | 결과 |
|---|---|---|
| `test_trigger_execution_and_timing::test_f01` | 기르수 소환 → 유발 발동 → 상대 응답 → 해결 시점 선택 → 덱 → 묘지 | 묘지 +1 · 덱 −1 · 선택 기록 1 (변경 전과 같다) |

## 7. 테스트 — 명령 · 결과 · 시간 · 실제 종료 코드

### 7.1 실행 방식

`scratchpad/run/runtests.sh <로그> <pytest 인자…>` 가 묶음 하나를
**포그라운드로** 돌리고 `PYTEST_EXIT=<코드>` 를 로그 안과 표준출력에 적고
`exit $CODE` 한다. 6-AB 보완까지 쓰던 `nohup … &` + `$?` 는 백그라운드로
보낸 결과였고 pytest 의 종료 코드가 아니었다 (그 보고서의 정정 공지).

### 7.2 단계 순서와 범위 판단

1. **최소 재현** — 세 결함을 scratchpad 스크립트로 각각 쟀다
   (`f4/repro.py` — A · B · C 를 한 번에).
2. **타깃** — 고치면서 그 스크립트를 다시 돌렸고 (`f4/verify.py` ·
   `verify2.py` · `verify3.py`), 양측 판을 실제 카드 개체로 바꿀 필요를
   그 과정에서 찾았다.
3. **관련 통합** — 유발 관련 네 파일을 돌려 회귀 16건을 찾았다.
4. **전체 회귀** — 🔴 **이번 변경이 공유 계약을 건드렸으므로 네 묶음 전부
   돌렸다**: `engine/duel.py`(등재 · 응답 · 허가) ·
   `engine/spell_activation.py`(수행기 조립) ·
   `engine/effect/{definition,executor,library}.py`(등록부 접근자) ·
   `agent/simulation.py`(사본). 예상 시간은 묶음별 6~50분이고 네 묶음을
   병렬로 돌렸다.

🔴 **같은 대규모 묶음을 불필요하게 반복하지 않았다** — 네 묶음은 **한
번**씩 돌렸고, 그 뒤 production 을 고치지 않았다.

### 8.4 남은 BLOCKER

#### BLOCKER-F4-1 — SEGOC 의 **7순위**가 없다 (②의 미달성 범위)

첨부 문서 §6.2 의 표에서 구현한 것은 **1~4** 다 (공식 룰북이 그 넷을
적는다). 없는 것은 셋이다.

| 순위 | 무엇 | 왜 없는가 |
|---|---|---|
| 5 · 6 | TP · NTP 의 **강제 유발 즉시** | 실행 구현이 등재된 유발 즉시 효과가 **0개**다 (`EFFECT_LIBRARY` 실측) |
| 7 | 우선권 교대로 쌓는 **임의 유발 즉시** · **비공개 영역 유발**(패 · 덱) | 같은 이유. 그리고 비공개 영역 유발은 *"SS2 처럼 발동"* 이라는 별도 재정이 필요하다 (§8.5) |

🔴 **지원하지 못하는 조합을 임의 순서로 실행하지 않는다.** 등재가 끝나면
`_response_priority()` 가 응답 단계를 열고, 그 단계에서 발동할 수 있는 것은
**기존 관문이 허가하는 것**뿐이다 — 유발 즉시 효과를 7순위로 끼워 넣는
코드를 짓지 않았다.

#### BLOCKER-F4-2 — 비공개 영역 유발의 포맷별 차이를 **조사만** 했다

첨부 문서 §6.3 이 적는 것: 패 · 덱 유발은 공개 유발을 다 쌓은 뒤 **SS2
처럼** 발동하고, 패가 공개 정보가 되면 SEGOC 순서를 따르며, **패에서
특수 소환하는 패 유발은 같은 타이밍에 1장만** 발동할 수 있다.

🔴 **공식 문언을 찾지 못했다.** 공식 룰북의 §동시 발동은 영역을 구분하지
않고, Fast Effect Timing 도표도 그렇다. 구현 권위 쪽에서는
`EFFECT_TYPE_TRIGGER_O` 등의 상수가 영역을 담지 않는다 (영역은
`SetRange(LOCATION_HAND)` 로 따로 적힌다). 그래서 **UNKNOWN 으로
남겼고**, 이 엔진에는 비공개 영역 유발이 등재되어 있지 않으므로 지금
동작에 영향이 없다.

#### BLOCKER-F4-3 — 「경우」 효과의 **장소 검사**가 없다

첨부 문서 §7.5: 2020 마스터 룰 이후 「경우」 효과도 **발동 타이밍에 발동할
장소에 없으면** 발동할 수 없다. 공식 근거는 OCG 카드 데이터베이스
cid=5883 보충(이미 쓰고 있다)과 같은 결이지만, **그 보충이 말하는 것은
"체인이 끝난 뒤 발동한다" 까지**이고 "장소에 없으면 발동 불가" 는 그
문장에 없다. 이 엔진은 그 검사를 하지 않는다 — 등재된 유발이 필드의
몬스터 하나뿐이어서 지금 경로에서 밟히지 않는다.

#### BLOCKER-F4-4 — 묶음 **안**의 순서를 정책에게 **묻지 않는다**

룰북은 묶음 안의 순서를 *"in any order"* 로 둔다. 이 엔진은 그 선택을
**후보 목록으로** 제공하고 (`test_b06` 이 센다) 고르는 쪽이 하나씩
`Duel.apply` 한다. 🔴 **그것이 룰북의 "한 번에 쌓는다" 와 같은 모양이라고
적지 않는다** — 플레이어가 차례로 올리는 것이고, 그 사이에 다른 효과가
끼어들지 못한다는 점만 보장된다 (`test_b01` 이 우선권이 안 넘어가는 것을
센다).

#### BLOCKER-F4-5 — `_window_claims` 는 관문을 **두 번** 돌린다 (강제 묶음)

`_window_can_act` 가 강제 묶음일 때 `_trigger_actions` 를 다시 돌린다.
같은 관문을 `legal_actions` 안에서 두 번 지나므로 비용이 든다. 🔴 **고르지
않은 대안**: 관문 결과를 창 판정에 캐시하면 "묻는 것만으로 아무것도
바뀌지 않는다" 를 지키기 어려워진다 (캐시가 상태다). 임의 묶음에서는
돌리지 않으므로 (PASS 가 있다) 실제 경로의 비용은 **0** 이다.

#### BLOCKER-F4-6 — 창에 사건이 **하나뿐**이다 (그대로)

최종 보완의 BLOCKER-F3-4 가 그대로다 (`test_b04b` 가 고정한다). 어휘
판정(「때 / 경우」)은 실제 실행 경로에서 답을 가르지 않는다.

## 11. 선행 보고서의 정정

### 11.1 최종 보완 §4.3 — *"내 창이 내 행동을 좁히지는 않는다"*

그 절은 임의 유발 창이 **내 행동을 좁히지 않는다**고 적고, 근거로 6-AA 의
*"임의 유발은 controller 를 강제하지 않는다"* 와 `test_b01` 을 들었다.

🔴 **그 추론이 틀렸다.** 공식 Fast Effect Timing 도표는 **판이 열린
상태(box A)** 에서만 할 수 있는 행동을 따로 적고, 유발 처리 기회는 box A 가
아니다. *"발동을 강제하지 않는다"* 와 *"그 기회를 열어 둔 채 다른 일을 해도
된다"* 는 다른 문장이고, 그 둘을 섞은 것이 BLOCKER-F3-1 을 만들었다.

지금은 등재 자리의 허가를 그 묶음의 발동과 `PASS` 로 좁힌다. 🔴 **강제 ·
임의의 구분은 사라지지 않았다** — 임의면 `PASS` 가 오르고 강제면 오르지
않는다.

### 11.2 최종 보완 §10 의 ② — *"부분 완료"* 의 이유가 바뀌었다

그 절은 ②를 "부분 완료" 로 적고 미달성 이유를 **BLOCKER-F3-1**(양쪽이 같은
사건에 기회를 들 때)로 들었다. 그것은 **해소되었다** (§4). 지금 ②가 부분
완료인 이유는 **SEGOC 의 5~7 순위**이고, 그것은 다른 사실이다 (§8.4
BLOCKER-F4-1).

### 11.3 최종 보완 §9 BLOCKER-F3-5 — *"관문을 돌리면 두 번 돌린다"*

그 절은 `_window_claims` 가 관문을 돌리지 않는 것을 **고치지 않은 이유**로
*"같은 관문을 두 번 돌리게 된다"* 를 들었다.

🔴 **그 비용이 교착보다 가볍다.** 관문이 막은 claim 으로 자리를 가리키면서
다른 자리를 막으면 **양쪽 다 고를 것이 없어 듀얼이 멈춘다** (§4.5 의
실측). 그래서 이번에 `_window_can_act` 로 돌리고, **강제 묶음일 때만**
돌려 비용을 좁혔다 (임의 묶음에는 `PASS` 가 있다). 남은 비용은
BLOCKER-F4-5 에 적었다.

### 11.4 최종 보완의 `test_e04` — 이름과 단정

`test_e04_synthetic_a_fork_rebuilds_the_production_registry` 는 사본이
원본의 정의를 잃는 것을 *"결함으로 적지 않는다 — 사본이 진짜와 다른 규칙으로
돌지 않게 하는 설계다"* 라고 적었다.

🔴 **그 판단이 틀렸다.** 사본이 원본보다 **못 해결하면** 그것이 바로 "다른
규칙으로 도는" 것이다. 시험을 고쳤고 (`…keeps_the_parents_effect_definitions`)
`test_e05` 를 더해 **같은 결과**까지 센다.

### 11.5 과장하지 않은 것

- ②는 **네 묶음까지**이고 SEGOC 전체가 아니다 (§8.4).
- 양측 시나리오는 **합성**이고 실제 카드 지원이 아니다 (§6).
- 구현 권위에서 확인한 것은 **네 묶음의 축이 자료형에 있다**는 사실이고,
  **순서 자체를 구현에서 확인한 것은 아니다** (§3.2).
- 첨부 문서는 **비공식 정리본**이고, 그 설명 · 의사코드를 규칙이나 구현
  지시로 채택하지 않았다. 출처 URL · 열람일을 직접 확인한 것으로 적지
  않았다 (§2).
- Discord 쪽은 **토큰 없는 응답 생성 검사**이고 실제 접속 검증이 아니다
  (§9).
- 통과한 시험 수가 많다는 이유로 미달성 기준을 완료로 바꾸지 않았다 — §10
  에 **부분 완료 · 미달성**을 그대로 남겼다.
- `Journal` 순번을 규칙상 동시성 · 처리 순서와 같다고 가정하지 않았다 —
  역순 해결의 근거는 `chain.links` 의 `sequence` 와 기록 순서다.
