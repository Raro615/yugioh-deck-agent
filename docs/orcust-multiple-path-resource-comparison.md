# 복수 전개 경로 수집과 최종 자원 비교 (Phase 6-AI)

같은 초기 상태에서 **서로 다른 성공 결과 여럿**을 모으고, 각 결과를 새 초기
상태에서 재생하고, 재생된 실제 상태를 근거로 **남은 자원의 차이**를 적는
단계다. 앞 단계(6-AH · 6-AH 보완, `docs/orcust-first-bounded-search.md`)가
만든 제한 탐색을 **그대로** 쓴다.

> 🔴 **이 단계는 최강 전개·승률·방해 수 평가가 아니다.** 평가 함수가 없고,
> 임의의 점수로 전개를 강한 순서처럼 정렬하지 않는다. 아래의 모든 표는
> **남은 자원을 늘어놓은 것**이고 순위가 아니다.

## 1. 복수 성공 결과 수집

### 1.1 별도 탐색기를 만들지 않았다

복수 결과 수집은 **같은 탐색기**가 한다. 고리는 `BoundedSearch._drive`
하나이고, 노드를 펼치는 `_open`, 중복 제거 `node_key`/`admit`/`superseded`,
해결 중 선택 분기 `_attempts`/`_apply_once` 는 단일 결과 모드와 **같은
코드**를 지난다. `run_many` 가 더하는 것은 셋뿐이다.

1. 목표에 닿은 자리를 **값으로 모아 두고**(`_collect`) **그 분기를 더
   펼치지 않는다.**
2. 결과 수 상한(`SearchBudget.max_results`).
3. 탐색이 **끝난 뒤** 모은 결과를 재생한다(`rerun_results`).

단일 결과 모드는 한 글자도 달라지지 않았다. `_open` 의 목표 분기가
`self.budget.many` 가 거짓이면 예전처럼 `return path, child_duel, verdict`
로 **그 자리에서** 멈춘다(시험: `test_e08`).

### 1.2 목표에 닿은 분기는 더 펼치지 않는다

비교하는 것은 "목표에 **처음** 도달하고 체인과 필수 처리가 정리된 상태"다.
그래서 목표 상태를 스택에 쌓지 않는다 — 쌓으면 **같은 경로에서 목표 달성
뒤 세트만 더 한 결과**가 별개의 "좋은 전개" 로 늘어난다.

격리 그래프로 그 사실을 고정했다(`GOAL_THEN_MORE`: `R→G1`, `G1→G1b`, 둘 다
목표). 결과는 **1개**이고, 탐색이 `G1→G1b` 간선을 펼친 기록이 없다
(`test_a02`).

### 1.3 예산 다섯 칸과 종료 사유

| 칸 | 기본값 | 뜻 |
|----|--------|-----|
| `max_depth` | 6 | 경로 길이 |
| `max_nodes` | 200 | 펼친 노드 수 |
| `max_seconds` | 300 | 탐색 시간 |
| `max_choice_branches` | 4 | 한 행동의 해결 중 선택 대안 각본 수 |
| `max_results` | **1** (복수 모드 권장 3, 상한 `RESULTS_CAP=5`) | 모을 결과 수 |
| `max_rerun_seconds` | 180 | **재생 전체**의 시간 — 🔴 결과마다가 아니다(§9.2) |

🔴 **결과 수 상한에 닿아 멈춘 사실은 종료 사유에 남는다.**
`budget_hit` 에 `max_results=N` 이 적히고 `MultiSearchOutcome.hit_result_cap`
이 참이 된다. 그래서 그 결과 묶음은 "가능한 전부" 가 아니다(`test_a03`).

🔴 **"찾은 결과가 있음" 과 "탐색을 끝까지 수행함" 을 가른다.** 앞의 것은
`reached`(결과가 비어 있지 않은가), 뒤의 것은 `search_exhausted` 다.
`search_exhausted` 는 **네 가지가 모두 참일 때만** 참이다 — 스택이 비어서
끝났고, **탐색** 예산에 걸린 칸이 없고, 오류가 없고, **확인하지 못한 해결 중
선택 대안도 없다**.

> 🔴 **정정 (Phase 6-AJ §9.4).** 6-AI 는 탐색 예산과 재생 예산의 사유를
> `budget_hit` **한 칸**에 담았다 — 그러면 "재생 시간이 끝났다" 가 "탐색
> 범위를 끝까지 펼치지 못했다" 로 읽힌다. 지금은 칸이 둘이다:
> `budget_hit`(탐색)과 `rerun_budget_hit`(재생). 소진 판정은 **탐색 쪽만**
> 본다. `termination` 은 **고리가 왜 멈췄는가**이고, 복수 모드에서는
결과를 찾았더라도 `exhausted` 나 `budget_exceeded` 로 남는다(목표 분기를
펼치지 않고 고리를 계속 돌리기 때문이다).

🔴 **예산이 끝나도 찾은 결과는 보존한다**(`test_a04`).

🔴 **중복을 발견했다는 이유로 서로 다른 결과 수가 늘지 않는다.** 같은
결과에 닿은 다른 경로는 `duplicate_results` 로 따로 센다(`test_a06`).

## 2. 결과 동일성과 대표 경로

### 2.1 두 중복 제거는 목적이 다르다

| | `node_key` (6-AH) | `outcome_key` (6-AI) |
|---|---|---|
| 묻는 것 | 이 상태를 **또 펼칠** 필요가 있는가 | 이것이 **같은 성공 결과**인가 |
| 체인 중 | `None` — 중복 제거를 **끈다** | **거절한다**(정리되지 않은 자리를 성공으로 세지 않는다) |
| 쓰는 곳 | `_open` 의 자식 등재 | `_collect` 의 결과 합치기 |

🔴 **기존 `node_key` 를 무조건 재사용하지 않았다.** 두 함수가 보는 것이 겹치는
부분(상태 해시 · 고를 사람 · 진행 단계 · 우선권 창 · 그 자리의 허용 후보
집합)은 같지만, 체인 중인 자리를 다루는 방식이 **정반대**다. 탐색 중에는
"모르니까 펼쳐 둔다" 가 안전하고, 결과 집계에서는 "모르니까 세지 않는다" 가
안전하다(`test_b01`).

### 2.2 동일성은 양쪽 자리의 실제 상태를 본다

`outcome_key` 의 상태 해시는 `GameState.state_hash()` 이고, 그것은
`canonical_state()` 에서 나온다 — 양쪽 플레이어의 모든 존(패 · 덱 ·
엑스트라 · 몬스터 존 · 엑스트라 몬스터 존 · 마법함정 존 · 묘지 · 제외 ·
필드 · 펜듈럼), 턴과 단계, 그리고 `uses` · `rule_uses` · `summon_uses`
전부가 들어 있다.

🔴 **카드 장수나 카드명 목록만 같다는 이유로 합치지 않는다. 필드가 같아도
사용 제한이 다르면 다른 결과다.** 격리 그래프로 그 경우를 만들어 고정했다
(`SAME_FIELD_OTHER_USES`: 두 꼬리표의 **카드 ID 목록이 완전히 같고**
기록된 카드명 사용만 다르다 → 결과 **2개**, 합친 경로 0개;
`test_b02` · `test_b03`).

🔴 **안전하게 판단할 수 없으면 따로 둔다.** `_is_settled` 가 거짓인 자리는
결과로 세지 않고(위), 개체 번호를 지우는 공격적 정규화는 하지 않았다.

### 2.3 대표 경로

같은 결과에 닿은 경로가 여럿이면 **대표 하나**만 제시한다. 기준은
`representative_order` 이고, **명시적이고 결정론적**이다.

1. 걸음이 적은 쪽
2. 같으면 행동 열쇠들의 안정된 순서
3. 같으면 해결 중 선택들의 안정된 순서

🔴 **발견한 경로 중의 대표이고, 전체 최단 경로 보장이 아니다.** 탐색이 보지
않은 더 짧은 경로가 있을 수 있다.

🔴 **대표가 교체될 수 있으므로 재생은 탐색이 끝난 뒤에 돈다.** 중간에
돌리면 교체된 대표가 검증되지 않은 채 보고된다. 격리 그래프
`SAME_GOAL_TWICE`(긴 경로가 먼저, 짧은 경로가 나중에 같은 상태에 닿는다)로
교체와 "교체된 쪽이 재생된다" 를 둘 다 고정했다(`test_b04` · `test_c05`).

### 2.4 남은 한계 — 잔여 중복

이 기준은 **"지금 상태가 같다"** 만 본다. 상태가 다르면 따로 세므로
**사람 눈에 "사실상 같은 전개"** 가 둘로 남을 수 있다 — 실측에서도 그런
쌍이 나왔다(§5.1 의 결과 2 와 결과 3: 세트 한 장만 더 했고 그 외의 차이가
없다). 🔴 이것을 "서로 다른 좋은 전개 두 가지" 로 읽지 말아야 한다. 그
판단(어느 차이가 의미 있는가)은 평가에 속하고, 이번 단계에 평가는 없다.

## 3. 실제 자원 요약

`summarize_resources(duel, seat)` 가 그 자리에서 **값**을 뜬다.

🔴 **살아 있는 `Duel` 을 공유하지 않는다.** 돌려주는 `ResourceSummary` 는
frozen 이고 어떤 칸에도 `Duel` · `Simulator` 가 없다 — 공유하면 뒤의 탐색이
그 판을 더 밟았을 때 요약이 **조용히 달라진다**(`test_d07`).

### 3.1 적는 것

| 자리 | 내용까지 | 장수만 |
|------|----------|--------|
| 자신 | 패 · 몬스터 존 · 엑스트라 몬스터 존 · 마법함정 존 · 필드 존 · 펜듈럼 존 · 묘지 · 제외 | 남은 메인 덱 · 엑스트라 덱 |
| 상대 | 몬스터 존 · 엑스트라 몬스터 존 · 마법함정 존 · 필드 존 · 펜듈럼 존 · 묘지 · 제외 (**앞면만 정체를 적는다**) | 패 · 덱 · 엑스트라 |

여기에 턴 번호와 단계, 상태 해시, **엔진에 기록된 사용 제한**(효과별 ·
카드별 · 카드명별 · 소환별 · 규칙별)과 **일반 소환권 사용 여부**가 함께
들어간다.

### 3.2 지우지 않는 것

- 같은 이름 여러 장은 **각각** 남는다(개체 번호 · 앞뒷면 · 표시 형식 ·
  칸 순서까지).
- 토큰도 한 칸으로 남는다(실측: 상대 몬스터 존의 `[46647145]`).
- 🔴 **입력에 상대의 비공개 정보가 없으면 만들어서 평가하지 않는다.**
  상대의 패 · 덱 · 엑스트라는 **장수만**이고, 상대 필드의 뒷면 카드는
  정체를 적지 않는다(`CONCEALED_CARD`) — "없다" 가 아니라 **"모른다"** 다
  (`test_d06`).

### 3.3 한국어 이름은 표시 층이 붙인다

요약은 **카드 ID 만** 들고 있다. 한국어 이름은 `deck/report.py` 가
`repository` 로 붙인다 — `agent/` 는 표시 경계 감사의 제한 대상이고, 저장소를
주지 않으면 ID 만 적는다(`test_e03`: 저장소를 주면 "오르페골 갈라테아
[30741503]", 주지 않으면 "[30741503]").

### 3.4 요약에 담기지 않는 차이

🔴 **실제 차이를 요약으로 표현할 수 없으면 "같다" 고 적지 않는다.** 두 결과가
비교 항목에서 모두 같게 보이면, 보고는 "차이를 찾지 못했다" 와 **"두 결과는
엔진 상태가 다르다(그래서 따로 셌다)"** 를 함께 적고 상태 해시와 전체 존
목록을 보라고 적는다.

## 4. 비교와 설명

같은 초기 상태에서 나온 **검증된 성공 결과들** 사이에서만 비교한다.

비교표의 항목: 행동 수(와 해결 중 선택 횟수) · 남은 패 장수와 구성 · 자신
필드 · 자신 마법함정 존 · 상대 필드에 남긴 칸 · 자신 묘지 구성 · 자신 제외
구성 · 남은 덱 장수 · 일반 소환권 사용 · 기록된 사용 제한 · **재생 검증
여부**.

### 4.1 적지 않는 것 — 🔴 금지 목록

| 금지 | 이유 |
|------|------|
| 패와 필드 장수를 더한 **총점**으로 "자원 N" 을 만들고 강하다고 적는 것 | 자원의 종류가 다르다. 더하면 평가가 되고, 평가 함수가 없다 |
| 묘지·제외에 간 카드를 **손실**로 세는 것 | 이 덱에서 묘지는 자원이다. 손실로 세면 틀린 전제가 들어간다 |
| 상대 필드의 토큰을 **항상 나쁜 것**으로 세는 것 | 그 칸이 무엇을 막고 무엇을 돕는지는 이 단계에서 세지 않는다 |
| 쓰지 않은 효과를 **지금 쓸 수 있다 / 다음 턴에 쓸 수 있다**로 읽는 것 | 사용 기록은 "무엇이 이미 쓰였나" 만 말한다. 발동 가능 판정은 `legal_actions` 의 일이다 |
| 카드 텍스트를 읽어 **방해 수·후속 전개**를 세는 것 | 엔진이 실행한 것만 적는다 |
| **"행동 수가 적으니 센 전개"** | 걸음 수는 길이이고 강함이 아니다 |

🔴 **주고받는 차이는 양쪽을 그대로 적는다**(한쪽은 패가 남고 다른 쪽은
묘지가 쌓이는 식). 🔴 **자동 순위도 승자도 없다.** 금칙어 부재를 시험이
고정한다(`test_e02`).

## 5. 실측

아래 수치는 **이번 구현에서 실제로 돌려 얻은 것**이다. 이전 단계의 수치를
옮겨 적은 칸은 없다.

### 5.1 실제 카드 입력 — 『성장』 입력

입력은 기존 입력과 같다(레시피와 시작 패). 🔴 **적어 둔 전개 경로
(`ORCUST_GIRSU_LINE` 의 수순)를 호출하지 않았다** — 그 상수에서 가져온 것은
**입력**뿐이다.

예산 `max_depth=6, max_nodes=400, max_results=3`.

| | 값 |
|---|---|
| 종료 | `budget_exceeded` (`max_results=3`) |
| 모은 결과 | **3개** (검증 3 · 재생 실패 0 · 재생 못 함 0) |
| 같은 결과에 닿아 합친 경로 | 0개 |
| 펼친 노드 / 최대 깊이 | 21개 / 5 |
| 탐색 소요 | **36.9초** |
| 재생 소요 | **28.5초** (🔴 탐색과 따로 적는다) |
| 범위를 끝까지 펼쳤는가 | **아니오** (결과 수 상한) |

| 항목 | 결과 1 | 결과 2 | 결과 3 |
|------|--------|--------|--------|
| 행동 | 4걸음 (선택 2회) | 5걸음 (선택 2회) | 6걸음 (선택 2회) |

## 6. 미지원과 한계

1. 🔴 **돌려준 결과가 가능한 모든 전개가 아니다.** 깊이 · 노드 · 시간 ·
   선택 분기 · 결과 수 상한이 모두 남은 길을 가리고, 지원하지 않아 후보가
   되지 못한 수와 확인하지 못한 선택 대안도 그렇다. 보고는 그 사실을
   `search_exhausted` 와 생략 줄로 적는다.
2. 🔴 **강약 평가가 아니다.** 순위도 점수도 승자도 없다.
3. 🔴 **상대의 선택은 탐색하지 않는다**(무방해는 명시적 정책이고 사실이
   아니다). 상대 자리에 고를 것이 남으면 그 노드에서 멈추고 그 사실을 적는다.
4. 🔴 **이번 턴만** 본다. `end_phase` 는 펼치지 않는다.
5. 🔴 **잔여 중복이 남는다**(§2.4). 상태가 다르면 따로 세므로 사람 눈에
   사실상 같은 전개가 둘로 남을 수 있다.
6. 🔴 **대표가 전체 최단 경로라는 보장이 없다**(§2.3).
7. 재생 시간 상한에 걸린 결과는 **검증되지 않은 것으로** 남는다 — 버리지도
   않고 검증된 비교에 섞지도 않는다.

   > 🔴 **정정 (Phase 6-AJ §9.2 · §9.3).** 6-AI 의 이 줄은 두 가지를
   > 뭉개고 있었다.
   >
   > 1. 상한은 **각 결과를 시작하기 전에만** 보았다. 재생 도중과 완료
   >    직후에는 보지 않았으므로, 한 결과가 상한을 넘겨도 **검증 성공으로**
   >    적힐 수 있었다(격리 재현: 예산 1초, 가상 시계 10초 → `verified=True`).
   >    지금은 마감 하나를 **모든 결과가 공유**하고, 경로 시작 전 · 각 행동
   >    전후 · 필수 걸음 반복의 경계 · 최종 검증과 자원 요약 뒤 · **재생이
   >    돌아온 자리**에서 본다.
   > 2. "시간이 없어 **시작조차 못 한** 결과" 와 "**시작했는데** 마감을 넘긴
   >    결과" 는 다른 사실인데 한 칸에 있었다. 지금은
   >    `RerunState.NOT_STARTED` 와 `RerunState.TIMED_OUT` 이다.
8. 🔴 **협력적 시간 제한이다** — 안전한 경계에서만 멈춘다(§9.2). 돌고 있는
   **엔진 호출 하나**는 끊지 않으므로, 그 호출이 길면 마감 시각을 **넘겨서**
   돌아올 수 있다. 그래서 "지정한 초 안에 강제 종료된다" 고 말하지 않는다.
   돌아온 자리에서 초과를 보고 **성공 처리를 막는 것**까지가 이 구현의 약속이다.
9. 🔴 **결과별 예외 격리의 범위는 복수 결과 재생뿐이다**(§9.3). 한 결과의
   재생·최종 검증·자원 요약에서 난 일반 실행 예외는 그 결과의 실패로 적히고
   다음 결과가 계속 검증되지만, 종료·취소 신호(`KeyboardInterrupt` ·
   `SystemExit` 등 `BaseException` 직계)는 **삼키지 않고** 그대로 올라간다.



`results` 는 **맨 뒤의 선택 인자**다 — `search` 를 주지 않은 요청의 동작은

### 8.3 기본 응답에 적는 것

1. 검증된 서로 다른 결과 수(모은 수와, **상태별 집계** — 검증 · 불일치 · 예외 · 시간 초과 · 미시작 · 재생 끔 — 와 함께, §9.4)

## 9. 후속 보완 (Phase 6-AJ) — 공유 재생 마감과 결과별 예외 격리

§1–§8 의 복수 경로 수집·자원 비교는 그대로 두고, 외부 검토가 격리 재현한
두 결함을 고쳤다. 🔴 **새 카드 효과도, 강약 평가도, 탐색 알고리즘 교체도,
외부 연동도 더하지 않았다.**

### 9.1 두 결함

| | 기준 코드(`95d18e9`)의 동작 | 왜 문제인가 |
|---|---|---|
| **A** | `rerun_results` 가 `max_rerun_seconds` 를 **각 결과를 시작하기 전에만** 보았다. `rerun_steps` 안과 완료 직후에는 보지 않았다 | 한 결과가 상한을 한참 넘겨도 **검증 성공**으로 적혔고, 재생 예산 기록도 남지 않았다 |
| **B** | `rerun_results` 가 `BoundedSearchError` **만** 결과별 실패로 받았다 | 그 밖의 일반 실행 예외가 호출자까지 전파되어 **남은 결과가 재생되지 않았다** |

### 9.2 A — 공유 재생 마감

🔴 **가상 시계와 대체 재생 함수를 쓴 격리 재현이다. 실제 카드 전개가 1초
예산에서 10초를 썼다는 뜻이 아니다.**

재현 (재생 예산 1초 · 재생 함수가 가상 시계를 10초 진행하고 **정상 결과를
반환**):

```
(기준 95d18e9)                       (이번 보완)
verified        = True               verified        = False
rerun.timed_out = (칸 없음)          rerun.timed_out = True
상태            = (칸 없음)          상태            = RerunState.TIMED_OUT
재생 예산 기록  = ()                 재생 예산 기록  = ('max_rerun_seconds=1',)
가상 시계 경과  = 10.0초 (예산 1초)   가상 시계 경과  = 10.0초 (예산 1초)
```

**구현.** `RerunDeadline(limit, clock=time.monotonic)` 하나를 만들어 **모든
결과가 돌려 쓴다.**

- 🔴 **결과마다 예산을 새로 시작하지 않는다.** `rerun_results` 가 고리 밖에서
  하나를 만들고(또는 받고) `rerun_steps` 까지 그대로 넘긴다.
- 🔴 **단조 시계**(`time.monotonic`)를 쓴다. 벽시계는 뒤로 갈 수 있어서 마감
  판정이 뒤집힌다. `clock` 은 시험이 **제어 가능한 단조 시계**를 꽂는 자리다.
- 🔴 **마감과 정확히 같은 순간은 만료로 본다**(`spent >= limit`). 경계를
  한쪽으로 고정해 두어야 구현마다 달라지지 않는다(`test_a08`).

검사하는 자리 — 실제 카드 경로(4걸음)에서 **24곳**이고, 자리 수를 손으로
적지 않고 시험이 센다(`check_points`).

| 자리 | 코드 | 멈추면 적히는 단계 |
|------|------|--------------------|
| 경로 시작 전 | `rerun_steps` | `경로 시작 전` |
| 각 행동 **앞** | `rerun_steps` 고리 머리 | `행동 N 앞` |
| 필수 걸음 반복의 **안전한 경계** | `_settle` 고리 머리 | `행동 N 의 필수 걸음` |
| 각 행동 **뒤** | `rerun_steps` 고리 끝 | `행동 N 뒤` |
| 최종 검증·자원 요약 **뒤** | `rerun_steps` 마지막 | `최종 검증 · 자원 요약 뒤` |
| 재생이 **돌아온 자리** | `_rerun_one` | `재생 호출 뒤` |
| 다음 결과를 **시작하기 전** | `rerun_results` 고리 머리 | (시작하지 않음) |

**협력적 시간 제한의 정확한 의미와 한계.**

- 🔴 **안전한 경계에서 멈춘다** — 다음 행동이나 다음 필수 걸음, 다음 결과를
  **시작하지 않는 것**으로 멈춘다.
- 🔴 **돌고 있는 단일 엔진 호출을 강제로 끊지 않는다.** 그러려면 프로세스나
  스레드 구조가 필요하고, 이번 범위가 아니다.
- 🔴 그래서 **마감 시각을 넘겨서 반환할 수 있다.** "정확히 지정한 초 안에
  강제 종료된다" 고 주장하지 않는다.
- 🔴 **그 호출이 반환하면 즉시 초과를 감지하고 성공 처리를 막는다**
  (`_rerun_one` 의 `재생 호출 뒤` 검사). 위 재현이 그 자리를 센다
  (`test_a06`).
- 🔴 **먼저 본 판정을 지우지 않는다.** 성공만 막고, 실제로 본 **불일치와
  예외**는 시간 초과로 덮어쓰지 않는다(`test_a07`) — 덮으면 "재현되지 않는
  경로" 가 "시간이 없었다" 로 바뀐다.
- 🔴 **단일 경로 재생의 기본 동작은 그대로다.** `rerun_path` · `rerun_steps`
  · `_settle` 의 `deadline` 은 **맨 뒤의 선택 인자**이고 기본값이 `None`
  이므로, 주지 않으면 6-AI 와 한 글자도 다르지 않다(`test_a10`).

### 9.3 B — 결과별 예외 격리

재현 (수집 결과 2개 · 첫 `rerun_steps` 에서 `RuntimeError`):

```
(기준 95d18e9)                                  (이번 보완)
🔴 호출자까지 전파됨: RuntimeError               전파되지 않았다 — 결과 2개
재생된 결과 수 = 1 / 2                           재생 시도 수 = 2 / 2
두 번째 결과   = 재생되지 않았다                 [결과 1] ERRORED · 'RuntimeError' · verified False
                                                 [결과 2] VERIFIED · '' · verified True
```

**구현.** 결과 하나의 **재생 · 최종 검증 · 자원 요약 비교**를
`BoundedSearch._rerun_one` 하나로 감쌌다.

- `BoundedSearchError` 와 그 밖의 `Exception` 을 각각 받아 **그 결과의
  실패**로 적는다. 형 이름(`RerunResult.error_type`)과 단계
  (`RerunResult.stage`)를 함께 남기므로 진단할 수 있다.
- 🔴 **남은 예산이 있으면 다음 결과를 새 초기 상태에서 계속 검증한다.**
  `rerun_steps` 는 받은 `duel` 에서 `Simulator` 사본을 새로 뜨므로, 실패한
  재생의 중간 상태가 다음 결과로 흘러가지 않는다(`test_b05` 가 초기 해시로
  센다).
- 🔴 **실패·성공·미검증 결과를 모두 보존한다.** 찾은 경로는 하나도 사라지지
  않는다(`test_b08`: `found` 가 줄지 않고 `reached` 가 참이다).
- 🔴 **오류를 "탐색 미발견" · UNKNOWN · 정상 무효과 해결로 바꾸지 않는다.**
  탐색 쪽 `errors` 칸에 섞어 넣지도 않는다 — 거기는 탐색의 오류다.
- 🔴 **예외를 조용히 삼키거나 성공 기본값으로 대체하지 않는다.**
  `rerun_notes` 에도 남는다.
- 🔴 **`BaseException` 전체를 잡는 방식을 쓰지 않는다.** `except Exception`
  이므로 `KeyboardInterrupt` · `SystemExit` · `GeneratorExit` ·
  `asyncio.CancelledError` (모두 `BaseException` 직계)는 그대로 올라간다
  (`test_b06`). `agent/bounded_search.py` 에 벌거벗은 `except:` 도,
  `except BaseException` 도 없다(`test_b07` 이 AST 로 센다).
- 🔴 **범위를 넓히지 않았다.** `except Exception` 을 쓰는 함수는 셋뿐이고
  시험이 이름을 고정한다 — `_rerun_one`(이번에 더한 것), 그리고 6-AH 부터
  있던 `rerun_steps` · `_apply_once` 의 **한 수 적용** 자리다.

### 9.4 결과 상태와 집계

`RerunState` 여섯 가지를 가른다. 🔴 **한 칸으로 뭉치면 왜 검증되지 않았는지가
사라진다.**

| 상태 | 뜻 | `rerun` |
|------|-----|---------|
| `VERIFIED` | 같은 판에 닿고 자원 요약까지 같다 | 있음 |
| `MISMATCHED` | 행동·선택·최종 판·자원 요약 중 하나가 어긋났다 | 있음 |
| `ERRORED` | 일반 실행 예외로 멈췄다 (`error_type`) | 있음 |

> 🔴 **정정 (§10).** 6-AJ 시점의 구현은 이 분류를 **행동 실행**
> (`fork.apply`) 예외에는 적용하지 못했다 — 그 분기가 `error_type` ·
> `stage` 를 비워 두어 `MISMATCHED` 로 집계됐다. §10 이 그 한 곳을
> 고치고 회귀 테스트를 더한다. 아래 표 자체는 그대로 맞다.
| `TIMED_OUT` | **시작했는데** 공유 마감을 넘겼다 | 있음 |
| `NOT_STARTED` | 시간이 남지 않아 **시작조차 못 했다** | 없음 |
| `DISABLED` | `rerun=False` 로 **끄고** 돌렸다 | 없음 |

- `MultiSearchOutcome.tally` 가 `ResultTally` 를 내놓고, 🔴 **`tally.total`
  이 모은 결과 수와 같다**(`test_c01`). 하나라도 어느 칸에도 들어가지 않으면
  결과가 조용히 사라진 것이다.
- 🔴 **검증된 비교에는 `VERIFIED` 만 넣는다.** 하나가 실패해도 정상 검증된
  다른 결과의 비교표는 유지된다(`test_c03`).
- 🔴 **경로를 찾았다는 사실과 재생 검증을 마쳤다는 사실을 가른다.** `found`
  는 재생 결과에 따라 줄지 않고, 요약이 그 사실을 한 줄로 밝힌다.
- 🔴 **탐색 예산과 재생 예산의 사유를 섞지 않는다** — `budget_hit` 과
  `rerun_budget_hit` 이고, 보고도 두 줄로 따로 적는다(`test_c07`).
- Discord 기본 응답은 **상태 한 줄**까지만 적고, 예외 형 이름과 단계 같은
  결과별 상세 사유는 **기존 첨부 기록**에 적는다(`test_c05`). 🔴 실제
  Discord 메시지는 보내지 않았다.


```
282 passed, 1 warning in 620.79s (0:10:20)
```

🔴 **기존 가짜 구현 넷이 처음에 실패했고, 기대값을 낮추지 않고 고쳤다.**
`tests/test_bounded_search_multi_results.py` 의 `rerun_steps` 스텁이
production 서명에 새로 붙은 `deadline` 을 받지 못해 `TypeError` 가 났다 —
그리고 §9.3 의 결과별 예외 격리가 그 `TypeError` 를 **"그 결과의 실패"** 로
적으므로, 한 시험(`test_c02`)은 **조용히 통과하는 쪽**이 될 수도 있었다.
그래서 스텁이 인자를 받기만 하는 것이 아니라 **마감이 실제로 전달되는지**를
함께 세게 했다. 단언을 지우거나 기대값을 느슨하게 바꾼 칸은 없다.

| 실패 | 무엇이 어긋났나 | 어떻게 고쳤나 |
|------|-----------------|---------------|
| `test_c01` · `test_c03` · `test_c05` | 스텁 서명에 `deadline` 이 없어 `TypeError` → 재생이 돌지 않았다 | 스텁도 `deadline` 을 받고, `RerunDeadline` 이 실제로 전달됐는지 단정한다 |
| `test_c04` | 재생 예산 사유를 `budget_hit` 에서 찾았다 | `rerun_budget_hit` 에서 찾고, `budget_hit` 에는 **섞이지 않는지**와 그 결과가 `NOT_STARTED` 인지까지 좁혀서 센다 |

**검증을 확대한 부분과 이유.** 공용 계층(`engine` · `core`)은 건드리지
않았으므로 전체 회귀를 다시 돌리지 않았다. 대신 **직접 영향받는 묶음**을
함께 돌렸다 — 재생을 쓰는 곳(복수 결과 · 단일 경로 첫 구현), 탐색 수치를
읽는 곳(깊이·선택), 출력과 어댑터(`/combo` 요약·첨부 · Discord · 선공 실행
통합).

## 10. 후속 보완 2 — 행동 실행(`apply`) 예외의 상태 분류 누락

🔴 **§9 의 테스트가 모두 통과한 뒤에도 남아 있던 결함이다.** 독립 검토에서
관련 테스트 167개가 통과했고 공유 재생 마감과 결과별 예외 격리도 구현돼
있었지만, 그 분류가 **실제 행동 실행 예외를 놓치고** 있었다.

### 10.1 무엇이 어긋나 있었나

`rerun_steps()` 안의 **행동 실행** 분기는 6-AH 부터 있던 그대로였다 —
`fork.apply()` 가 터지면 `ok=False` 인 `RerunResult` 를 만들면서
`reason` 과 `steps` 만 적고, 6-AJ 가 더한 `error_type` · `stage` 는
**비워 두었다.** 그래서:

1. `apply()` 에서 `RuntimeError` 가 난다.
2. `rerun_steps()` 가 `ok=False` 인 결과를 **반환**한다 (예외가 밖으로
   나가지 않는다).
3. 결과별 경계 `_rerun_one()` 에는 **예외가 전파되지 않는다.**
4. `error_type` 이 비어 있으므로 `PathResult.rerun_state` 가
   `ERRORED` 가 아니라 **`MISMATCHED`** 를 돌려준다.
5. 상태별 집계와 보고가 **실행 예외를 재생 불일치로** 표시한다.

🔴 **성공으로 잘못 인정하는 문제는 아니었다** — `verified` 는 두 경우 모두
거짓이다. 어긋난 것은 **왜 검증되지 않았는가**이고, 그것이 §9.4 가 가르려고
만든 바로 그 구분이다.

수정 전 격리 재현(`tests/test_bounded_search_rerun_apply_errors.py` 를
수정 전 코드에서 돌린 것):

```
assert rerun.error_type == "RuntimeError"
  AssertionError: assert '' == 'RuntimeError'

assert only.rerun_state is RerunState.ERRORED
  AssertionError: assert <RerunState.MISMATCHED: 'mismatched'>
                      is <RerunState.ERRORED: 'errored'>
  … RerunResult(ok=False, …, error_type='', stage='')
```

### 10.2 최소 수정

`agent/bounded_search.py` 의 그 분기 **하나**에 두 칸을 채웠다.

| 칸 | 값 |
|----|-----|
| `error_type` | `type(error).__name__` — 실제 예외 클래스 이름 |
| `stage` | `f"행동 {recorded.order} 실행"` — **몇 번째 행동의 실행 중**인지 |

🔴 **그 밖에는 아무것도 바꾸지 않았다.**

- `reason` 의 문구(`"N번째 행동에서 예외가 났습니다: …"`)와 `steps`(그때까지
  **완료한 걸음 수**)의 뜻은 그대로다.
- 공유 마감 · 시간 초과 처리 · 단일 경로 재생 API(`rerun_path` ·
  `rerun_steps` 의 서명과 기본값)는 **건드리지 않았다.**
- 예외를 성공 · 정상 무효과 · UNKNOWN · 재생 불일치로 바꾸지 않는다.
- `except Exception` 이므로 `apply()` 에서 난 `KeyboardInterrupt` ·
  `SystemExit` 같은 `BaseException` 직계는 **그대로 올라간다**(이 분기도,
  바깥 `_rerun_one` 도 마찬가지다).

### 10.3 수정 전/후 상태 분류

| | 수정 전 | 수정 후 |
|---|---|---|
| `rerun.error_type` | `""` | `"RuntimeError"` |
| `rerun.stage` | `""` | `"행동 1 실행"` |
| `rerun.reason` | `"1번째 행동에서 예외가 났습니다: RuntimeError: …"` | **같다** |
| `rerun.steps` | 완료한 걸음 수 | **같다** |
| `PathResult.rerun_state` | `MISMATCHED` | **`ERRORED`** |
| `verified` | `False` | `False` (같다) |
| `tally` | 불일치 1 · 예외 0 | **불일치 0 · 예외 1** |
| 상세 보고 | "재생이 어긋났습니다" | "재생이 **일반 실행 예외**로 멈췄습니다 … 🔴 예외 RuntimeError · 단계 행동 1 실행" |

### 10.4 회귀 테스트 — 실제 행동 실행 지점을 지난다

새 파일 `tests/test_bounded_search_rerun_apply_errors.py` (7건).

🔴 **`rerun_steps()` 를 가짜로 바꾸지 않는다.** 바꿔 끼우는 것은
`Duel.apply` 하나이고, 그것도 **기록된 그 행동의 열쇠일 때만** 터지게 한다 —
필수 걸음이 적용하는 패스에는 손대지 않으므로 예외가 **행동 실행 지점**에만
들어간다. 재생 반복문 · 허용 후보 재조회 · 필수 걸음 처리 · 결과별 경계
(`_rerun_one`) · 집계(`_many_outcome`) · 두 렌더러는 **production 그대로**
돈다.

🔴 **실제 카드를 쓰지만 탐색을 돌리지 않는다.** 선공 판에서 엔진이 내놓은
허용 후보로 짧은 경로 둘을 만든다 — `일반 소환 → 패스`(목표 `[69811710]` 에
**닿는다**)와 `마·함 세트 → 일반 소환`(두 번째 걸음에서 터뜨려 **완료 걸음
수 1**을 만든다). 열쇠가 틀렸다면 픅스처가 production `rerun_steps` 로
실제로 밟아 보는 자리에서 깨진다. 30초짜리 탐색을 반복할 이유가 없다.

| 시험 | 고정하는 사실 |
|------|---------------|
| `test_a01` | `ok=False` · `error_type="RuntimeError"` · `stage` 에 `행동 1` · `steps=0` · `reason` 문구 유지 · 시간 초과도 목표 도달도 아님 |
| `test_a02` | 두 번째 행동에서 터지면 `stage` 가 `행동 2`, `steps=1` (완료 걸음 수의 뜻 유지) |
| `test_a03` | 결과별 경계를 지나도 `ERRORED` 이고 `MISMATCHED` 가 아니다 · `verified=False` · 경로 보존 · 진단이 `rerun_notes` 에 남음 |
| `test_b01` | 첫 결과의 `apply` 만 터지면 두 번째는 **검증 성공** · 모은 결과 수와 경로 보존 · 두 재생이 **같은 초기 해시**에서 시작 · 원본 판 불변 |
| `test_c01` | 예외 수 1 · 불일치 수 0 · 검증 수 1 · `tally.total == found` · 상세에 예외 종류와 발생 단계 · 요약은 간결(단계는 상세에만) |
| `test_d01` (×2) | `apply` 에서 난 `KeyboardInterrupt` · `SystemExit` 이 `rerun_steps` 와 `rerun_results` 양쪽에서 **상위로 전파** |
