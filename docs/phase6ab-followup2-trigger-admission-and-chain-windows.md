## 2. 리뷰 A~E 재현 결과와 원인

🔴 **먼저 재현했다.** 지적을 재현된 결함으로 단정하지 않고 하나씩 실측했다.

| | 지적 | 재현 | 실제 원인 |
|---|---|---|---|
| **A** | `is not True` 가 `None` 을 허가로 바꾼다 | **재현됨** | 그대로. 단 **내부 판정 불일치**이고 실행 우회는 아니다 (아래) |
| **B** | 포기가 `_apply_board` 뒤에만 걸려 있다 | **재현됨** | 행동 종류마다 포기 코드를 붙이는 **구조** 자체 |
| **C** | `chain.is_empty` 가 모든 유발을 막는다 | **재현됨** | 체인 **구성**과 체인 **도중**을 가를 수단이 없었다 |
| **D** | 전·후 조회를 결합해 기회를 식별한다 | **미재현** (잘못 포기시키지 않았다) · **구조적으로 취약** | `(개체, 효과)` 일치는 **사건을 식별하지 못한다** |
| **E** | 실패가 있어도 종료 코드 0 | **재현됨** | 🔴 **내 임시 셸 패턴이었다.** 프로젝트 러너는 없다 |

### 2.1 A — 실측, 그리고 **과장하지 않은 서술**

포기가 끼지 않는 자리(상대 제안)에서 어휘를 모르는 제안을 물었다.

```
포기 기록에 있는가        = False
_missed_timing            = None
🔴 _window_admits         = True
🔴 _offer_is_activatable  = True
🔴 event_backed 에 포함    = True
legal_actions 후보인가     = False     ← 여기서만 막혔다
직접 apply                = 거절 (RULE_NOT_IMPLEMENTED,
                            "activate_effect 는 지금 허가된 행위가 아닙니다")
```

🔴 **읽는 법을 분명히 한다.** `_window_admits` 가 `None` 을 `is not True`
로 받아 **``True``** 로 바꿨고, 그래서 내부 관문(`event_backed`)이 열렸다.
막는 것은 후보 목록의 보류 **하나뿐**이었다 — 그것이 **내부 판정
불일치**이고, 이 Phase 들이 금지해 온 구조다.

**그러나 직접 `Duel.apply` 는 그때도 거절됐다** (후보 검사에서). 그래서
*"UNKNOWN 이 직접 실행된다"* 는 **재현되지 않았다.** 그 구별을
`_window_admits` 의 docstring 에도 적어 두었다.

### 2.2 B — 실측

기르수 소환으로 유발 기회를 연 뒤, 그 유발을 쓰지 않고 **다른 효과**
(어리석은 매장)를 발동해 체인 해결까지 갔다.

```
소환 직후 유발 후보   = True
별개 효과 발동 수락   = True   (체인 열림)
체인 해결 뒤 체인 빔  = True
🔴 과거 유발이 다시 후보인가 = True
   포기 기록 = 0 | 제안 = 1
```

포기는 `_apply_board` 수락 뒤에만 기록됐으므로 **효과 발동과 `PASS` 는
기회를 닫지 않았다.** 공식 Fast Effect Timing 도표에서 그 자리는 이미
지나간 창이다.

### 2.3 C — 실측

같은 사건이 유발 둘을 여는 합성에서 (제안 2건), 첫 발동 뒤:

```
후보 = ['…:e[0]']  →  발동 뒤 후보 = []
보류 = ['체인이 처리 중입니다 — …']
```

둘째 유발이 **같은 체인에 쌓일 수 없었다.** 룰북은 그 둘을 **같은 특수
체인**에 쌓는다고 적는다 (§*When multiple cards are activated
simultaneously*).

### 2.4 D — 미재현, 그러나 식별 방식이 취약

```
소환 전 유발 후보 = 0
소환 수락        = True
🔴 소환 뒤 포기 기록 = 0   ← 새 사건을 잘못 포기시키지 않았다
   유발 후보 = True
```

잘못 닫지는 않았다 — 행동 **전** 후보가 0건이면 일찍 돌아가기 때문이다.
🔴 **그래도 방식이 틀렸다**: 행동 전 `(개체, 효과)` 와 행동 뒤 제안을 맞춰
보는 것은 **사건을 식별하지 못한다.** 같은 개체 · 같은 효과의 **다른 사건**
제안이 끼면 잘못 닫힌다. §4 의 교체가 이 축을 없앴다.

### 2.5 E — 🔴 내 보고서가 거짓을 적은 자리

```
직접 실행 (선행 실패가 있는 묶음)  → 종료 코드 1
`nohup … &` 뒤의 $?               → 0
```

6-AB 보완 보고서 §7.6a 는 *"종료 코드는 네 묶음 모두 0 이다 (pytest 가
실패를 요약으로 보고하고 wrapper 가 0 으로 끝낸다)"* 라고 적었다.
**pytest 는 실패하면 1 을 돌려준다.** 내가 본 0 은 pytest 의 것이 아니라
**백그라운드 전환 결과**였고, 종료 코드를 한 번도 받아 보지 않은 채 0 이라고
적고 **그 이유를 지어냈다.**

🔴 **프로젝트에 테스트 wrapper 는 없다** (`scripts/` 에 `*.sh` 가 없다).
그 패턴은 내 임시 셸 호출이었다. 고친 방식은 §7.1 에 있다. 통과·실패·skip
수는 로그에서 읽은 값이므로 그대로 유효하고, 틀린 것은 그 문장 하나다 —
그 자리에 정정 안내를 넣었다 (`d81a494`).

## 3. 공통 판정의 True / False / UNKNOWN 계약

```
_missed_timing(offer)          타이밍을 놓쳤는가
   True   놓쳤다               False  놓치지 않았다      None  판정 근거 없음
        │                            │                        │
        ▼                            ▼                        ▼
_window_admits(offer, seat)    지금 이 자리에서 발동할 수 있는가
   False                        True                     None
        │                            │                        │
        ▼                            ▼                        ▼
_offer_is_activatable(offer, seat)   ``is True`` 만 통과시킨다
   False                        True                     False
        │                            │                        │
        ▼                            ▼                        ▼
activation_validator(seat).event_backed    열린 것만 들어간다
        │                            │                        │
   ┌────┴────────────┬───────────────┴──────┬─────────────────┘
   ▼                 ▼                      ▼
legal_actions   _apply_activation      deck/opening.py
(후보 생성)      (직접 apply 재검증)      (보고 계층 _gate_code)
```

🔴 **극성을 뒤집어서 넘긴다.** `_missed_timing` 의 `True` 는 "놓쳤다" 이고
`_window_admits` 의 `True` 는 "발동할 수 있다" 다. 이 보완을 쓰다가 그대로
돌려주었고, **소환 직후의 유발이 후보에서 사라지는 것**으로 바로 드러났다
(실측). 그 사실을 코드 주석에 적었다.

🔴 **`None` 은 어디서도 접지 않는다.** `_window_admits` 가 `None` 을
그대로 돌려주고, `_offer_is_activatable` 이 `is True` 만 통과시키므로
모름은 **내부 관문도, 후보 목록도, 직접 `apply` 도** 열지 않는다. 그래서
"후보 목록에서만 추가로 차단" 하는 구조가 사라졌다 (§5.1 이 센다).

> 🔴 **정정 (Phase 6-AB 최종 보완).** 바로 위 문장과 이 절의 다이어그램은
> **체인이 닫힌 경로에 대해서만 참이었다.** 이 커밋의 `_window_admits` 는
> 체인이 열리면 `return sequence < self.chain_floor` 로 끝나고, 그 분기는
> `_missed_timing` 을 **부르지 않으므로** `None` 을 낼 수 없다 — 즉
> 다이어그램이 그리는 흐름을 **밟지 않는 경로가 있었다.**
>
> 막는 효과 자체는 그대로였다 (그 분기의 답은 `True` / `False` 중
> 하나이고 `_offer_is_activatable` 이 `is True` 만 통과시킨다). 그래서
> 이것은 **설명의 결함**이다. 다만 그 분기는 자격을 묻지 않으므로
> `floor ≤ sequence ≤ chain_floor - 2` 구간에서는 판정되지 않은 제안에
> `True` 를 줄 수 있었다 — 그 구간이 지금 데이터에서 **비어 있어**
> 실행 경로에서는 재현되지 않았다.
>
> 고친 자리와 측정값: `docs/phase6ab-followup3-trigger-window-completion.md`
> §2.1 · §11.1.

🔴 **"판정할 수 없다" 와 "규칙이 금지한다" 를 가른다.** 전자는 `missing` 을
채우고 후자는 비운다 — 자리마다의 표는
`tests/engine/test_legal_action_candidate_consistency.py::test_i03` 에 있다.

## 4. 행동별 기회 종료 · 보존과 체인 단계 전이

### 4.1 `declined_events` → `window_floor` · `chain_floor`

🔴 **행동 종류마다 포기 코드를 붙이는 구조를 버렸다.** 대신 **"지금 창이
어디서 시작했는가"** 하나를 들고 있는다.

근거는 공식 Fast Effect Timing 도표다 — 유발을 확인하는 자리가 **둘**이고
(체인을 시작하지 않는 행위 뒤 · 체인이 해결된 뒤), 그 자리에서 양쪽이
패스하면 판은 **open state** 로 돌아간다. 그래서 **행동 종류를 열거할 필요가
없다.**

```
window_floor  지금 창이 덮는 첫 기록 번호
chain_floor   지금 쌓이는 체인이 시작된 기록 번호 (없으면 -1)
```

| 자리 | 창이 어떻게 움직이는가 |
|---|---|
| 판을 바꾸는 행위 (`_apply_board`) **수락** | `window_floor = 행위 **전**의 기록 길이` — 그 행위가 낳는 사건부터가 새 창 |
| 효과 발동으로 체인이 **시작** | `chain_floor = 지금 기록 길이`. 🔴 `window_floor` 는 **그대로** — 같은 기회의 다른 유발이 아직 쌓일 수 있다 |
| 체인이 **완전히 해결** (`_resolve_chain`) | `window_floor = max(window_floor, chain_floor)` · `chain_floor = -1` |
| 페이즈 전환 (`_apply_end_phase`) | `timing_floor` 와 `window_floor` 둘 다 올린다 |
| 행동 **거절** · 반복 조회 | **아무것도 움직이지 않는다** |

### 4.2 요구별 대응

| 요구 | 어떻게 지켰는가 |
|---|---|
| 행동 종류마다 포기 코드를 붙이지 않는다 | 창은 "open state 로 돌아갔는가" 하나로 움직인다. 행동 종류를 보지 않는다 |
| 기회를 계속 구성하는 행동 / 종료하는 행동을 구분 | `chain_floor` 가 그 구분이다 — 체인이 쌓이는 동안 `window_floor` 는 멈춰 있다 |
| `PASS` 를 문맥으로 판단 | **`PASS` 를 특별히 다루지 않는다.** 체인 응답의 패스는 창을 움직이지 않고, 양쪽이 패스해 체인이 해결되면 그때 창이 옮겨간다 |
| 같은 기회의 다른 유발을 자동으로 포기시키지 않는다 | 첫 발동은 `consumed_events` 에 **그 하나**만 넣고 창은 그대로다 (`test_b05`) |
| 종료된 기회가 체인 해결 후에도 다시 나오지 않는다 | `window_floor = chain_floor` (`test_b05b`) |
| 체인 도중 새 사건의 후속 기회는 보존 | 그 사건의 번호는 `chain_floor` **이상**이므로 새 창에 들어간다 (`test_b05b`) |
| 양측의 선택 기회와 종료 | 강제는 `to_act` · `_enforce_mandatory` 가 양쪽을 본다 (6-AB 보완). 🔴 **임의는 한계가 있다** — §8 BLOCKER-F2-1 |
| 전후 조회의 우연한 일치로 식별하지 않는다 | 조회를 맞춰 보는 코드가 **없어졌다.** 창은 기록 번호 하나다 |
| 반복 조회 · 거절된 불법 행동이 소비하지 않는다 | 창은 `accepted` 뒤에만 움직인다 (`test_b06` · `test_b07`) |

### 4.3 체인 단계 전이

```
① 기회 개시          사건이 기록된다 (번호 >= window_floor)
      │
      ▼
② 체인 구성·응답      chain_floor = 체인 시작 번호
      │              · 번호 <  chain_floor → 같은 기회 → **같은 체인에 쌓는다**
      │              · 번호 >= chain_floor → 체인 도중 → **보존하고 기다린다**
      ▼
③ 체인 해결          _resolve_chain 안에서 **한 번에** 일어난다
      │              🔴 그 사이에 legal_actions 가 불리지 않으므로
      │                 "해결 중의 판정" 이라는 것은 이 엔진에 없다
      ▼
④ 새 기회 개시        window_floor = chain_floor · chain_floor = -1
                     · 체인을 연 기회의 사건 → **끝났다**
                     · 체인 도중에 생긴 사건 → **살아 있다**
```

🔴 **`chain.is_empty` 하나로 이 단계들을 대신 판정하지 않는다** — 그것이
리뷰 C 가 가리킨 결함이다. 🔴 **그리고 체인 구성 중과 체인 해결 중을 같은
뜻으로 쓰지 않는다**: 위 ②와 ③은 다른 단계이고, ③에는 판정 자리가 없다는
사실을 그대로 적었다.

### 4.4 미지원 결과를 전파한다 (조용한 `continue` 셋)

`_trigger_actions` 가 후보도 보류도 남기지 않고 넘어가던 자리 셋을 보류로
바꿨다. 그 전에는 **"유발이 없다" 와 "유발이 있는데 처리할 수 없다" 가 같은
침묵**으로 나왔다.

| 자리 | `missing` | 실측으로 밟았는가 |
|---|---|---|
| 실행 구현이 없다 | `TRIGGER_IMPLEMENTATION_MISSING` | **예** — 한 사건이 유발 둘을 여는 합성에서 둘째 효과의 정의가 등재되어 있지 않았다 |
| 대상 환전이 안 된다 | 같음 | 아니다 (같은 결의 자리로 함께 고쳤다) |
| 관문이 거절했다 | 🔴 **관문의 답을 따른다** — `UNKNOWN` 이면 그 `missing_rule`, 규칙상 금지면 `None` | 아니다 |

## 8. 미지원 범위와 남은 BLOCKER

> 🔴 **후속 (Phase 6-AB 최종 보완).** 아래 BLOCKER 다섯 가운데 F2-1 은
> **상대 자리에 대해 해소**되었고 (양쪽이 같은 사건에 기회를 들 때는
> 남았다 → BLOCKER-F3-1), F2-2 는 **엔진 통합 경로가 합성 효과로
> 해소**되었다 (실제 카드 지원은 남았다 → BLOCKER-F3-2). F2-3 · F2-4 ·
> F2-5 는 그대로다. 측정값은
> `docs/phase6ab-followup3-trigger-window-completion.md` §9 · §11.2 에
> 있다.

### BLOCKER-F2-1 — 창이 **자리별로** 나뉘지 않는다

`window_floor` 는 값 **하나**이고 자리를 가르지 않는다. 그래서 내가 판을
바꾸는 행위를 고르면 **상대의 임의 유발 기회도 함께 닫힌다** — 공식 도표에
따르면 그 창에서 상대도 한 번은 선택할 수 있어야 한다.

실측으로 이 자리를 밟았다 (`test_b04` 를 쓰다가 상대 제안이 창 밖으로
나갔다). 🔴 **강제 유발은 막혀 있다** — `to_act` 와 `_enforce_mandatory` 가
양쪽을 보므로 (6-AB 보완) 상대의 **의무**는 내 행동으로 사라지지 않는다.
남은 것은 **임의** 쪽이다.

고치려면 창을 `(자리, 바닥)` 둘로 들고 "양쪽이 다 지나가면 닫는다" 를
구현해야 하고, 그것은 우선권을 자리 사이에서 넘기는 절차 (``_flow_actions``
가 *"우선권을 여는 규칙 (Phase 2-F)"* 로 적어 둔 미구현) 와 함께 가야 한다.

### BLOCKER-F2-2 — 같은 체인에 유발 둘을 **끝까지** 등록할 수 없다

`_window_admits` 가 같은 기회의 둘째 유발에 ``True`` 를 돌려주는 것은
쟀다 (`test_b05`). 🔴 **그러나 끝까지 등록하려면 두 번째 유발 효과의 실행
구현이 필요하고 이 저장소에 없다** — 실행 등재된 유발 효과는 하나다.

지금 그 자리는 **조용히 사라지지 않는다**: §4.4 가 `TRIGGER_IMPLEMENTATION_
MISSING` 으로 적게 만들었다. 그래서 "순서는 미지원" 이라는 주석만 남기고
임의로 진행한 결과를 합법 실행으로 표시하지 않는다.

### BLOCKER-F2-3 — 창에 사건이 둘 이상 들어가지 않아 **어휘 판정이 쓰이지 않는다**

듀얼 한 판에서 `legal_actions` 호출 142회 전수를 재어 보니
`(기록의 마지막 번호) − (창의 바닥)` 의 분포가 ``{-1, 0}`` 이었다 —
**1 이상이 한 번도 없다.**

뜻: 창이 열릴 때마다 그 안의 사건은 **하나**이므로 "사건이 창 안에 있지만
마지막은 아니다" 라는 자리에 도달하지 않는다. 「때 / 경우」 가 답을 가르는
자리가 바로 그곳이므로, 어휘 판정은 **지금 실제 실행 경로에서 쓰이지
않는다.** 사건을 여럿 낳는 효과나 여러 걸음으로 해결되는 효과가 들어오면
`test_b04b` 가 **먼저 깨지고**, 그때 어휘 판정이 쓰이기 시작한다.

### BLOCKER-F2-4 — SEGOC 의 순서는 **의무 우선순위까지만**

`to_act` 가 턴 플레이어의 강제 → 상대의 강제를 지킨다 (룰북 §*When multiple
cards are activated simultaneously*). 🔴 그 뒤(임의 효과들의 순서, 한 자리의
여러 효과 중 어느 것을 먼저)는 **구현하지 않았고 임의 순서로 실행하지도
않는다** — 여러 유발이 한 자리에 열리면 후보가 여럿 오르고 **고르는 쪽이
고른다.** 그것이 규칙상 정해진 순서인지 이 엔진은 주장하지 않는다
(`UNRESOLVED_ORDER_RULES` 가 그대로다).

### BLOCKER-F2-5 — 보류의 `missing` 출처가 **다섯 종류**다

`test_09` 가 세는 느슨함이 이번에 하나 늘었다 (§2 · `9ddd197`). 다만
다섯째는 성질이 다르다 — 앞의 넷은 그 자리가 **값을 고르는** 것이고 이것은
판정한 계층의 답을 **그대로 옮기는** 것이다. 느슨함을 줄이려면 나머지 넷을
이 모양으로 모으는 쪽이 방향이지만, **경계 재설계는 이 Phase 의 범위가
아니다.**

### 범위 밖 (손대지 않았다)

신규 카드 기능 · 특수·엑스트라 소환 · 전략 평가 · 학습 · EDOPro·리플레이
연동 · 검색 · 카드·금제 업데이트 · 광범위한 최적화.
`engine/timing.py` · `engine/trigger_order.py` 는 **한 줄도 바뀌지 않았다.**

🔴 **`engine/timing.py` 를 이번에도 쓰지 않았다.** 6-AB 보완 §4.1 의 이유가
그대로다 — `TimingCoordinator` 가 `TriggerChainIntegrator` 로 체인을 **직접
구성**하므로 `Duel` 과 같은 역할의 두 번째 경로가 생긴다. 🔴 **휴면 감사가
있다는 사실만으로 밀어 둔 것이 아니다**: 이번에 필요한 것은 "창이 어디서
시작했는가" 라는 **값 두 개**였고, 그것은 `TimingWindow` 가 들고 있지 않다
(그 클래스는 사건 · 관측자 · 우선권 · 체인의 **스냅숏**이다). 동일 역할의
두 번째 규칙 엔진을 만들지 않으려고 `Duel` 의 칸으로 더했다.
