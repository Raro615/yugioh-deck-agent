# Phase 3-F-44 — 한국어 오버레이 미적용 항목의 사용자 표시 경계 감사

**결론부터:**

* 미적용 7개는 **CLI 의 정상적인 카드 분석 흐름에 passcode 로 들어올 수
  없다.** 네 개 명령(`card` · `analyze` · `related` · `relations`) 전부
  `카드를 찾을 수 없습니다: …` 로 끝나고 **exit code 1** 이다.
* 막히는 지점은 오버레이가 아니라 **그보다 앞단인 카드 조회**다.
  `repo.get(passcode)` 가 7개 모두 `None` 이므로 오버레이·provenance 판정
  코드는 **실행 자체가 되지 않는다.**
* 7개는 한 덩어리가 아니다. **3개는 같은 공식 CID 아래 적용된 형제
  passcode 가 있고 한국어 이름·텍스트가 바이트 단위로 같다**(사용자 기준
  데이터 손실 0, 한국어 이름으로 조회 가능). **4개는 형제도 카드도 없다.**
* 진단 정보는 **생성되고 있으나 호출 지점에서 버려진다.**
  `korean_source.apply(cards)` 는 적용 건수 **13,892** 를 돌려주지만
  `core/card_repository.py:222` 가 반환값을 받지 않는다. 전체 코드베이스에서
  **반환값이 버려지는 유일한 `*.apply(...)` 호출**이다.
* **production 을 한 줄도 바꾸지 않았다** (audit-only).

## 2. 핵심 질문 1 — 미적용 7개는 CLI 의 정상 흐름에 들어올 수 있는가?

### 2.1 실제 CLI 호출 결과

`python3 -m app.main <명령> <passcode>` 를 7개 × 4개 명령 = 28회 실제
실행했다. 결과가 28/28 동일하다.

| 명령 | 출력 | exit code |
|---|---|---|
| `card 662853` | `카드를 찾을 수 없습니다: 662853` | **1** |
| `analyze 662853` | `카드를 찾을 수 없습니다: 662853` | **1** |
| `related 662853` | `카드를 찾을 수 없습니다: 662853` | **1** |
| `relations 662853` | `카드를 찾을 수 없습니다: 662853` | **1** |

**정상적인 카드 분석 흐름에 들어오지 못한다.** 분석이 시작되기 전에 끝난다.

### 2.2 막히는 경계의 위치

| 검사 | 7개 전부 |
|---|---|
| `repo.get(passcode)` | **`None`** |
| `passcode in repo._cards` | **`False`** |

경계는 **카드 조회**다. 오버레이 적용 여부, `korean_available`,

즉 "오버레이가 적용되지 않아서 한국어가 안 보이는 카드" 가 아니라
**"저장소에 없는 카드"** 다. 두 상태를 섞어서 말하면 안 된다.

## 4. 핵심 질문 2 — 표시할 실익이 있는가?

카드가 repository 에 없으면 분석 자체가 불가능하다. 그 상태에서
"한국어 데이터 없음" 류의 메시지를 덧붙이면 **틀린 정보**가 된다.
`data/ko` 에는 입력이 있다(§3.3 상태 3 = 0개). 없는 것은 카드다.

현재 출력이 이미 정확하다: `카드를 찾을 수 없습니다: 662853`. 한국어
관련 문구를 한 글자도 쓰지 않는다. **이것이 맞는 출력이다.**

### 4.1 서로 다른 세 상태가 실제로 다르게 보이는지 확인

실제 CLI 로 세 경우를 비교했다.

| 경우 | 예시 | 실제 출력 |
|---|---|---|
| 오버레이 적용됨 | `483` | `한국어` 행 + `카드 텍스트(한국어)` |
| 카드가 없음 | `662853` | `카드를 찾을 수 없습니다` — 한국어 관련 문구 **없음** |
| 카드는 있고 한국어가 없음 | `212652` | `카드 텍스트` — 언어 수식어 **없음** |

세 출력이 서로 구별된다. **"한국어 데이터 없음" 하나로 합쳐진 사례는
재현되지 않았다.** 지시가 금지한 병합은 현재 코드에서 일어나지 않는다.

## 5. 핵심 질문 3 — 진단 정보는 어느 경계에서 사라지는가

### 5.1 버려지는 반환값

`sources/korean_names.py` 의 `apply()` 는 docstring 에 "적용된 카드 수를
돌려준다" 고 적혀 있고 실제로 **13,892** 를 돌려준다.

호출 지점은 하나다.

| 위치 | 코드 | 반환값 |
|---|---|---|
| `core/card_repository.py:222` | `korean_source.apply(cards)` | **버려짐** |

AST 로 코드베이스 전체의 `*.apply(...)` 호출 12곳을 세었다. **11곳은
반환값을 쓴다. 반환값을 버리는 것은 이 한 곳뿐이다.**

따라서 경계는 이렇다.

```
data/ko (13,899)
  → apply() 가 13,892 를 집계하고 돌려준다        ← 정보가 존재한다
  → card_repository.py:222 가 반환값을 버린다      ← 🔴 여기서 사라진다
  → CardRepository 는 적용 건수를 모른다
  → CLI 는 출력할 값이 없다
```

7개 미적용에 대한 집계는 **생성되지만 저장되지 않는다.**

### 5.2 그래도 사용자 표시 문제는 아니다

§2 에서 본 대로 7개는 조회 단계에서 막힌다. 이 반환값이 보존되어도
`card 662853` 의 출력은 바뀌지 않는다. 이것은 **사용자 출력 결함이 아니라
빌드 단계의 관측 가능성(observability) 공백**이다. 두 개를 섞지 않는다.
