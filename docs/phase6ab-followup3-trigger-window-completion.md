## 2. 검토 항목 A~D 재현 결과

구분을 지킨다 — **재현됨 / 미재현 / 제한된 조건에서 발생**.

### 2.1 A — `_window_admits` 가 체인이 열리면 `_missed_timing` 을 건너뛴다

**제한된 조건에서 발생 (구조적 결함, 실행 경로 미재현).**

검토 기준 커밋의 코드:

```python
if self.chain_floor >= 0 and not self.chain.is_empty:
    return sequence < self.chain_floor      # ← 여기서 끝난다
missed = self._missed_timing(offer)
```

그 식은 "이 창의 사건인가" 만 묻고 **자격을 묻지 않는다.** 따라서 잘못된
`True` 가 나오는 입력 구간은

```
floor ≤ sequence ≤ chain_floor - 2      (그래야 is_last 가 거짓이 되어
                                         _missed_timing 이 None 을 낼 수 있다)
```

🔴 **그 구간이 지금 데이터로는 비어 있다.** 창은 사건 **하나**만 들고
(`test_b04b`, 추가 보완 BLOCKER-F2-3 의 실측: 듀얼 한 판 142회 전수에서
`(기록의 마지막 번호) − (창의 바닥)` 분포가 `{-1, 0}`), `chain_floor` 는
언제나 그 사건 번호 + 1 이므로 `chain_floor - 2 < floor` 다. 실측:

```
체인 없음      floor=0 horizon=0 chain_floor=-1
합성 발동 뒤    floor=0 horizon=0 chain_floor=1
→ 구간 [0, -1] = 비어 있다
```

즉 **내부 판정과 후보 목록이 갈라질 수 있는 구조**였고, 실행 우회가
재현된 것은 아니다. 고친 이유는 그 구조가 창이 사건 둘을 들게 되는 날
작동해야 하기 때문이다.

🔴 **고치는 방향을 한 번 틀렸고, 그것이 다른 사실을 드러냈다.** 처음에는
자격 검사를 체인 분기보다 **앞**에 두었다. 그러면 체인 도중에 생긴 「때」
사건이 *"타이밍을 놓쳤다"* 로 판정되는데, 그것은 `_trigger_actions` 가
적는 보존 이유(*"기회는 남아 있지만 발동은 그 체인이 모두 해결된 뒤"*,
聖鳥クレイン 재정)와 **어긋난다.** 체인 도중의 사건에 대해 "마지막에
일어난 일인가" 를 지금 묻는 것 자체가 틀린 질문이다. 그래서 최종 순서는

```
① sequence < floor                      → False (지나간 창)
② 체인 열림 · sequence >= chain_floor    → False (보존, 다음 창)
③ seat in window_passed                 → False (그 자리가 포기했다)
④ 그 밖                                  → _missed_timing 에 맡긴다
```

이고, 이제 `_window_admits` 와 `_trigger_actions` 가 **판정과 이유를 둘 다**
같게 답한다 (`test_a02` 가 그 일치를 센다).

### 2.2 B — `window_floor` 단일 값이 상대의 임의 창을 닫는다 (BLOCKER-F2-1)

**재현됨.** 실측 (상대 자리에만 임의 유발 제안 하나를 두고):

```
상대 제안 1 · 창 판정 True
내 세트 수락 True
🔴 상대 제안 1 · 창 판정 False · 상대 후보 False
🔴 END_PHASE 수락 True
```

규칙이 보장해야 하는 처리 기회가 **확인되기 전에** 사라졌다. 강제는
추가 보완의 `_duty_seat` 가 막고 있었으므로 (6-AB C), 남아 있던 구멍은
**임의**였다.

### 2.3 C — "같은 체인에 유발 둘" 이 내부 `True` 확인에서 끝났다 (BLOCKER-F2-2)

**재현됨** — 추가 보완 보고서가 스스로 그렇게 적어 두었다 (§5.3 ·
§8 BLOCKER-F2-2). 이 Phase 가 끝까지 통과시켰다 (§5 · §6).

### 2.4 D — `deck/opening.py` 가 보류를 보지 않고 정상 종료를 적는다

**재현됨.** 사용자가 본 그 전개를 그대로 돌려 실측했다:

```
stopped_kind = unsupported
남은 후보 ['end_phase']
🔴 같은 자리의 미지원 보류 1건:
   activate_card [activation-timing (Phase 2-C/2-F)]:
   activate_card 의 남은 적법성을 판정할 규칙 계층이 아직 없습니다.
```

즉 *"이 저장소의 현재 지원 범위에서 더 고를 것이 없다"* 는 문장은
**같은 자리에 지원하지 않아 오르지 못한 후보가 있다는 사실을 보지 않고**
쓰여 있었다. `Simulator` 도 그 사실을 밖으로 내보내지 않았다 — 사본은
버려지므로 그 자리에서 읽지 않으면 영영 나가지 않는다.

🔴 **"후보가 흐름뿐" 이라는 사실만으로 정상 전개 종료라고 결론 내리지
않는다** 는 요구가 바로 이 자리다.

## 4. 구현한 판정과 상태 전이

### 4.1 기회의 수명 — 네 칸

```
timing_floor    페이즈가 바뀔 때 올라간다           (6-AA)
window_floor    지금 기회가 시작된 기록 번호          (추가 보완)
chain_floor     지금 쌓이는 체인이 시작된 기록 번호    (추가 보완)
window_passed   이 창에서 선택을 마친 자리들 ← 최종 보완이 더한 칸
```

`window_passed` 는 `frozenset` 이므로 `dataclasses.replace` 가 값으로
가져간다 — 한 분기의 포기가 다른 분기의 기회를 닫지 않는다 (§7 E 군).
창이 옮겨 가는 세 자리에서 비워진다: `apply` (판을 바꾸는 행동 수락) ·
`_resolve_chain` · `_apply_end_phase`.

### 4.2 `PASS` 의 세 가지 뜻 — 단계가 가른다

같은 행위가 단계마다 다른 일을 한다. 단계는 `priority` 가 열려 있는지와
창에 고를 것이 있는지로 갈린다.

| 단계 | `PASS` 가 하는 일 | 적는 곳 |
|---|---|---|
| 우선권이 열려 있다 | 체인 응답 · 빠른 효과 응답의 포기 | `priority.passed()` |
| 우선권이 닫혀 있고 내 창에 처리할 것이 있다 | **유발 처리 기회의 포기** | `window_passed` |
| 둘 다 아니다 | 통상 우선권 넘김 | `priority.passed()` |

`test_b04` 가 셋을 가르는 것을 센다 — 유발 포기의 이유는 *"이 유발 처리
기회에서 발동하지 않기로 했습니다"* 이고, 체인 응답의 포기는 그 문장을
쓰지 않으며 `window_passed` 를 건드리지 않는다.

🔴 **포기가 후보를 실제로 닫는다.** `_window_admits` 가 `seat in
self.window_passed` 를 보도록 했다. 그러지 않으면 `PASS` 는 아무 일도
하지 않은 것이고 "상대의 기회를 물었다" 고 말할 수 없다. 실측: 포기 뒤
그 자리의 claims 1 → 0, 후보 0건.

### 4.3 제어권 전달 — `window_floor` 를 자리별로 나누는 것으로 끝내지 않았다

```
to_act          _duty_seat() → _window_actor() → 통상 우선권 보유자
_window_actor() 턴 플레이어 먼저, 그 다음 상대 (룰북 §동시 발동 순서)
_flow_actions   그 자리에 발동 후보와 PASS 를 함께 올린다
_enforce_mandatory  다른 자리의 창이 열려 있으면 내 진행을 막는다
```

실측 — 상대 자리에만 임의 유발 제안 하나:

```
to_act=1 · 상대 claims=1 · 내 허가=[] (세트 후보도 없다)
내 END_PHASE 수락=False · 상대 claims=1  ← 지나칠 수 없다
상대 PASS 수락=True "이 유발 처리 기회에서 발동하지 않기로 했습니다."
window_passed=[1] · 포기 뒤 상대 claims=0 · 상대 후보=[]
to_act=0 · 내 허가=['set_spell_trap' ×3, 'end_phase']  ← 제어권 복귀
내 END_PHASE 수락=True · 페이즈=BATTLE
```

🔴 **영구 대기가 아니다.** 가리켜진 자리에는 발동 후보와 `PASS` 가 함께
오르므로 고를 것이 반드시 있다. 듀얼 한 판이 그대로 끝난다 (§7).

🔴 **내 창이 내 행동을 좁히지는 않는다 — 한 번 그렇게 썼고 틀렸다.**
처음 구현은 창을 쥔 자리의 허가를 "발동 + 포기" 로 좁혔다. 공식 도표만
보면 그쪽이 더 엄격하지만, 그것은 **임의 유발이 그 controller 를
강제하지 않는다**는 6-AA 의 구분을 지운다. 실측으로
`test_b01_an_optional_trigger_can_be_taken_or_given_up` 이
*"임의 유발은 페이즈 전환을 막지 않는다"* 로 깨졌고 (`END_PHASE` 가
임의 유발에 막혔다), 같은 변경이 `test_b02` 계열 열 건을 함께 깼다 —
그 자리에서 다른 일을 고르는 것이 **그 자리의 포기**라는 것이 6-AB
보완이 공식 도표에서 끌어낸 해석이다. 되돌렸고, 막는 것은 **다른
자리의** 창뿐이다.

### 4.4 동시 발동 — 스펠 스피드 관문이 막던 자리

같은 기회의 둘째 유발을 체인에 쌓으려 하면 관문이
*"스펠 스피드를 판정할 수 없습니다 (몬스터 효과)"* 로 멈췄다.
`ActivationTiming.simultaneous` 를 더해 "같은 기회에서 동시에 쌓이는
묶음의 하나인가" 를 **판을 든 쪽이 값으로** 넘긴다 (`Duel._is_simultaneous`
가 `chain_floor` 와 제안의 사건 번호로 답한다). `ActivationTimingChecker`
가 그 경우를 통과시키는 근거는 룰북 §동시 발동이다.

🔴 **관측에 없는 사실이므로 값으로 넘어온다** — 창에 사건이 몇 건인지,
체인이 어느 사건에서 시작했는지는 `Duel` 의 수명 상태이고
`GameStateView` 에 없다. 체인 · 우선권 · `set_this_turn` 과 같은 이유다
(`test_activation_timing::test_f`).

### 4.5 미지원 사유의 전파 경로 (④)

```
WithheldAction.missing            빠진 규칙의 이름 (엔진이 정한다)
        │
        ▼
LegalActions.unsupported()        missing 이 붙은 보류만 고른다 ← 새 접근자
        │
        ├──► deck/opening.py  unsupported_reasons()
        │       ExecutedStep.unsupported   걸음별
        │       OpeningRun.unsupported     전체, 처음 본 순서대로
        │       OpeningRun.stopped_kind    멈춘 종류 한 낱말
        │               │
        │               ├──► deck/report.py  render_opening_run
        │               └──► app/discord_bot.py  /combo 요약 줄
        │
        └──► agent/simulation.py  SimulationResult.unsupported
                     fully_supported = 미래가 있고 경계가 없다
                     │
                     └──► agent/search.py  SearchCandidate.unsupported
                              (이름만 · ordering_key 는 보지 않는다)
```

🔴 **"규칙이 막았다" 와 "이 저장소에 그 규칙이 없다" 를 가른다.**
`missing` 이 붙은 보류만 미지원이다. 섞으면 규칙의 답이 결함으로 읽히거나
그 반대가 된다.

🔴 **`stopped_kind` 가 "흐름뿐" 과 "미지원" 을 가른다.** 여덟 낱말:
`not_run` · `duel_over` · `no_candidates` · `unsupported` · `flow_only` ·
`not_chosen` · `rejected` · `limit`. 추가 보완까지 앞의 둘이 **같은
문장**으로 나왔다.

🔴 **미지원이 하나 있다는 이유로 모든 진행을 막지 않는다.** `unsupported`
는 **기록**이고 허가를 바꾸지 않는다. 실측: 같은 전개가 그대로 5걸음
실행되고 효과 1걸음이 해결된다 (§8 보존). `SearchCandidate.ordering_key`
도 이 칸을 보지 않는다 — 미지원을 벌점으로 바꾸면 "모른다" 가 "나쁘다"
가 된다.

🔴 **`SUPPORTED` 와 "그 뒤를 다 안다" 를 가른다.** `SimulationResult.
fully_supported` 가 그것이고, 미래가 없는 결과에 경계를 적으면
`SimulationError` 다 — 없는 미래의 경계를 적지 않는다 (`test_d02`).

## 5. 실제 카드 / 합성 검증의 구분

### 5.1 조사 — 실제 카드로 ③ 을 구성할 수 있는가

**없다.** 순서대로 확인했다.

1. 실행 구현이 등재된 유발 효과는 **기르수 ① 하나**다 (6-Z `test_c09`).
2. **같은 지원 효과의 서로 다른 카드 개체**를 먼저 조사했다. 기르수를
   2장 이상 넣고 둘을 같은 기회에 소환할 수 있으면 실제 카드로 ③ 이
   된다. 그러나 **일반 소환은 턴에 한 번**이고, 특수 소환은 이 Phase 의
   범위 밖이며 (범위: 신규 카드 기능 · 특수 · 엑스트라 소환 제외) 이
   저장소에 실행 구현이 없다. 즉 **같은 사건이 두 개체의 기회를 함께
   열 수 없다.**
3. 카드명별 횟수 제한은 지켰다 — 기르수는 금제상 3장까지이고
   `_board(girsu_copies=…)` 로 2장 판도 만들어 보았으나 위 이유로 같은
   기회가 열리지 않는다.
4. 사건 하나가 두 효과의 기회를 여는 실제 카드(한 카드에 유발 둘)는
   등재된 효과가 하나이므로 없다.

### 5.2 그래서 ③ 은 합성 검증이다 — 무엇을 합성했는가

| 항목 | 값 |
|---|---|
| 합성한 것 | `EffectDefinition` 하나 — 기르수의 **둘째 효과 칸**(`EffectRef(69811710, 1)`)에 공통 연산 `DrawOperation(count=1)` 을 붙였다 |
| 왜 드로우인가 | 대상 선택이 없고 판의 다른 카드를 보지 않으므로 **역순 해결이 실제로 일어났는지**를 가리는 것이 없다. 묘지로 보내는 효과를 둘 쌓으면 둘째 해결이 `BoardRuling._interference` 에서 `UNKNOWN` 이 된다 — 먼저 풀린 링크가 묘지에 넣은 카드에 대해 "그것이 막는지" 확인된 것이 없기 때문이고(실측), 그것은 엔진의 **올바른 보수적 답**이므로 우회하지 않았다 |
| 주입하지 **않은** 것 | 허가 · 체인 링크 · 소비 기록 · 최종 상태. 전부 엔진이 만든다 |
| 지난 경로 | 실제 사건(일반 소환) → `TriggerSource` 제안 → `legal_actions` → `_activation_gate` → `Duel.apply` ×2 → 상대 응답(우선권) → `ChainResolver` 역순 해결 → `GameState` · `EventJournal` |
| 배선 | 그 판의 `_activator` · `_resolver` · `triggers` 와 `PolicyChooser.definitions` 에만 꽂는다. **프로덕션 등록부를 건드리지 않는다** |
| provenance | `EffectProvenance.hand_written(verified=True, note=…)` — note 에 "합성이며 기르수의 둘째 효과가 아니고 어떤 실제 카드의 효과도 주장하지 않는다" 를 적었다 |

🔴 **실제 카드 지원이 완료되었다고 보고하지 않는다.** ③ 이 증명한 것은
**엔진 통합 경로가 같은 기회의 유발 둘을 한 체인에 쌓고 역순으로 풀 수
있다**는 것이고, 그렇게 할 **실제 카드가 이 저장소에 등재되어 있다**는
것이 아니다.

### 5.3 합성인 시험의 목록

| 시험 | 바꿔 끼운 값 | 왜 합성인가 |
|---|---|---|
| `test_a01` · `test_a02` | `wording` · `event_sequence` | 어휘가 답을 가르는 자리에 실제 실행 경로가 도달하지 않는다 (`test_b04b`) |
| `test_b01`~`test_b05` | `requirement` · `controller` | 상대 자리의 유발이 실제로 등재되어 있지 않다 |
| `test_c01`~`test_c04` | 둘째 효과 정의 (§5.2) | 같은 기회에 유발 둘을 올릴 실제 카드가 없다 (§5.1) |
| `test_c02` 의 "체인 도중 사건" | `event_sequence` | 체인 도중에 실제로 유발을 낳는 사건이 아직 없다 |
| `test_e04` | 없음 — 사본의 등록부를 그대로 관찰한다 | 합성 효과가 사본에서 사라지는 **방식**을 센다 |

### 5.4 실제 카드 경로는 그대로다

`test_f01` — 합성을 꽂지 않은 판에서 제안은 **하나**이고, 발동 → 상대
응답 → 해결 → 묘지 +1 · 덱 −1 · 해결 시점 선택 1건 · 기회 종료가
예전 그대로다.

| 열거 감사 (칸 수 · 이름 · 호출 수) | 6 | **시험을 기준으로 정정** (§8) |

🔴 **열 건이 한 번에 깨진 것이 설계 판단을 되돌리게 했다.** 공식 도표만
보면 "창을 쥔 자리는 발동 아니면 포기" 가 더 엄격하지만, 그것은 6-AA 가
세운 **강제 · 임의의 구분**을 지운다. 시험 열 건이 그 구분을 지키고
있었고, 그 가운데 `test_b01` 은 *"임의 유발은 페이즈 전환을 막지 않는다"*
를 문장으로 들고 있었다. **시험을 고치지 않고 코드를 되돌렸다.**

## 8. 정정한 기존 시험 — 여섯, 전부 **열거에서 기준으로**

🔴 **삭제 · skip 추가 · assertion 완화는 하지 않았다.** 여섯 건 모두
"칸이 N개다 / 호출이 N번이다" 라는 **열거**를 그 시험 자신이 docstring 에
적어 둔 **주장**으로 되돌린 것이고, 주장은 전부 그대로이거나 **더
좁아졌다** (추가 단정을 붙였다).

| 시험 | 전 | 후 | 그 시험이 지키려는 주장 |
|---|---|---|---|
| `test_activation_timing::test_f` | `fields == {네 이름}` | 관측의 이름이 **없음** + 허용 집합 + `{chain, priority}` 포함 | *"관측에 이미 있는 것을 다시 담지 않는다"* (그 docstring 이 이미 적어 둔 문장) |
| `test_search_ai::test_18b` | `names == {여섯 이름}` | 판을 담는 이름 여섯이 **없음** + `future` 있음 + 형 주석 확인 | *"판을 담는 칸이 없다"* |
| `test_opponent_resource_weighting_audit::test_15` | `len(fields(SearchCandidate)) == 4` | 관측 이름 없음 + 정확한 다섯 이름 + `ordering_key` 가 새 칸을 **보지 않음** | 3-E-42 *"후보는 관측을 들고 있지 않다"* |
| `test_opponent_resource_feature::test_18` | 같음 | 같음 | 같음 |
| `test_legal_action_candidate_consistency::test_a03` | `simulation` 호출 **3회** | `agent/simulation.py` 안에서 부르는 **함수 집합** | *"사설 보조 함수를 직접 부르는 외부 호출자가 없다"* |
| `test_legal_action_candidate_consistency::test_i03` | `len(forced) == 4` | `forced.count(True) == 1` · 나머지는 모두 `False` | *"`missing` 은 근거가 생겨야 풀리는 자리에만 찬다"* (기준 자체는 손대지 않았다) |

### 8.1 변경 전 기대값이 왜 틀렸는가

- `test_f` · `test_18b` · `test_15` · `test_18` — 네 시험 모두
  docstring 이 *"이 시험이 지키는 주장은 'N개다' 가 아니다"* 를 **이미
  적어 두었다** (`test_f` 는 3-E-15 에서 한 번 같은 이유로 깨진 기록까지
  남겨 두었다). 열거는 그 주장보다 **좁지 않고 다르다** — 관측에 없는
  사실이 하나 늘 때마다 깨지면서, 정작 지켜야 할 "관측과 겹치지 않는가" 는
  세지 않는다.
- `test_a03` — 주장은 **어디서 부르는가**이고 호출 횟수는 그 주장의
  대리값이었다. 같은 공개 함수를 한 번 더 부르는 것은 주장을 위반하지
  않는다.
- `test_i03` — 기준은 옳고 그대로다. 틀린 것은 자리 **개수**를 함께
  고정한 부분이고, 추가 보완이 이미 "수에서 기준으로 옮겼다" 고 적어 둔
  시험에서 `_enforce_mandatory` 의 개수만 남아 있었다.

### 8.2 내가 쓴 시험의 기대값 하나도 틀렸다

`test_b05` 는 강제와 임의가 섞인 자리에서 막는 이유를 **임의 창** 쪽
문장으로 기대했다. 실측은 **강제** 쪽이다 — `_enforce_mandatory` 가 의무를
먼저 보기 때문이고, 그 순서를 뒤집으면 강제 의무가 임의 창의 이유로
가려진다 (`test_c06` 이 그 문장을 센다). 기대값을 고쳤고 왜 그 순서인지를
시험에 적었다.

## 9. 미지원 범위와 남은 BLOCKER

### BLOCKER-F3-1 — 두 자리가 **같은 사건**에 기회를 들면 턴 플레이어가 둘 다 닫을 수 있다

막는 것은 **다른 자리의** 창이다 (`_enforce_mandatory` 의 창 블록). 내 창은
내 행동을 좁히지 않는다 — 임의 유발은 controller 를 강제하지 않는다는
6-AA 의 구분이고, 그 자리에서 다른 일을 고르는 것이 **그 자리의 포기**다
(6-AB 보완이 공식 도표에서 끌어낸 해석, `test_b02`).

그래서 남는 구멍은 하나다: `_window_actor()` 가 턴 플레이어를 먼저
가리키므로, **양쪽이 같은 사건에 기회를 들고 있으면** 턴 플레이어가 다른
일을 골라 창을 옮기고 상대의 기회까지 함께 닫을 수 있다.

🔴 **실제 데이터로는 밟을 수 없다** — 실행 등재된 유발은 한 카드의 효과
하나이므로 두 자리가 같은 사건에 기회를 드는 일이 없다. 합성으로만
만들 수 있고, 닫으려면 공식 도표의 "양쪽이 다 지나가야 닫힌다" 를
**내 창에도** 적용해야 하는데 그것은 위의 6-AA 해석과 충돌한다. 두 근거의
우선순위를 정하는 것은 이 Phase 의 범위가 아니다 — **부분 완료**로 적는다.

### BLOCKER-F3-2 — ③ 은 **합성 효과**로만 통과한다

§5.1 의 조사 결과다. 실제 카드로 같은 기회에 유발 둘을 올리려면 특수
소환이나 둘째 유발 효과의 실행 구현이 필요하고, 둘 다 이 Phase 의 범위
밖이다. **엔진 통합 경로는 완료, 실제 카드 지원은 미달성.**

### BLOCKER-F3-3 — SEGOC 의 네 단계 가운데 **한 단계**만 구현했다

룰북 §When multiple cards are activated simultaneously 는 특수 체인을
**턴 플레이어 강제 → 상대 강제 → 턴 플레이어 임의 → 상대 임의** 로
쌓는다. 이 엔진이 구현한 것은 **강제가 임의보다 먼저**라는 한 단계이고
(`_duty_seat` → `_window_actor` 순서), 자리끼리의 순서는 `turn_player`
먼저로만 처리한다. 또 둘을 **한 번에 쌓지 않고** 플레이어가 차례로
올리게 한다.

🔴 **`Journal` 순번을 규칙상의 동시성과 같다고 적지 않았다.** 역순 해결의
근거는 `chain.links` 의 `sequence` 와 기록 순서이고, 그것이 "두 사건이
규칙상 동시였다" 를 뜻한다고 말하지 않는다.

### BLOCKER-F3-4 — 창에 사건이 둘 이상 들어가지 않아 **어휘 판정이 쓰이지 않는다**

추가 보완의 BLOCKER-F2-3 이 그대로다 (`test_b04b` 가 그 사실을 고정한다).
①의 결함이 **실행 경로에서 재현되지 않는 이유**도 이것이다 (§2.1).
사건을 여럿 낳는 효과나 여러 걸음으로 해결되는 효과가 들어오면
`test_b04b` 가 먼저 깨지고, 그때 어휘 판정과 ①의 보호가 쓰이기 시작한다.

### BLOCKER-F3-5 — `_window_claims` 는 **발동 관문을 돌리지 않는다**

`_offer_is_activatable` 은 창과 강제 · 임의만 본다. 그래서 관문이 거절할
제안(예: 그 카드를 쥐고 있지 않다)도 claim 으로 세어지고, 그 자리의
허가가 `PASS` 하나만 남을 수 있다. **멈추지는 않는다** — `PASS` 가 항상
함께 오르므로 고를 것이 있다. 관문을 창 판정 안에서 돌리면 같은 관문을
두 번 돌리게 되므로(`_trigger_actions` 가 이미 돌린다) 손대지 않았다.

### BLOCKER-F3-6 — 같은 체인에서 묘지로 보내는 효과 둘은 **둘째가 `UNKNOWN`** 이다

실측: 첫 링크가 묘지에 넣은 카드에 대해 `BoardRuling._facts_of` 가
확인된 사실을 못 찾으면 `_interference` 가 멈추고, 둘째 해결의 후보가
전부 `UNKNOWN` 이 되어 `TOO_FEW_SELECTED` 로 불발한다.

🔴 **이것은 엔진의 올바른 보수적 답이다** — "아무도 안 막는다" 는 판
전체를 다 읽었을 때만 할 수 있는 말이고, 묘지 카드의 `restricts_others`
에 대한 검증된 사실이 없다. 우회하지 않았고, ③ 의 합성 효과를
드로우로 고른 이유가 이것이다 (§5.2).

### 이 Phase 가 손대지 않은 기존 실패 둘

`b098987` 에서 같은 두 건이 이미 실패했다 (같은 묶음을 pristine HEAD 로
돌려 확인했다 — 2 failed, 255 passed):

| 시험 | 왜 |

| `tests/agent/test_opponent_resource_weighting_audit.py::test_07_a_whole_duel_never_offers_a_choice_about_opponent_resources` | 이 Phase 의 변경 **전에도** 실패했다. 네 파일(`agent/search.py` · `agent/simulation.py` · `engine/duel.py` · `engine/activation_timing.py`)을 하나씩 되돌려도 실패가 남는 것으로 확인했다 |

## 11. 이전 보고서의 정정

### 11.1 `phase6ab-followup2-…` §3 의 다이어그램이 **체인이 열린 경로를 설명하지 않았다**

그 절은 *"`None` 은 어디서도 접지 않는다. `_window_admits` 가 `None` 을
그대로 돌려주고…"* 라고 적었다. 🔴 **그 문장은 체인이 닫힌 경로에
대해서만 참이었다.** 같은 커밋의 `_window_admits` 는 체인이 열리면
`return sequence < self.chain_floor` 로 끝났고, 그 분기는
`_missed_timing` 을 **부르지 않으므로** `None` 을 낼 수 없다 — 즉
다이어그램이 그리는 흐름을 **밟지 않는 경로가 있었다.**

막는 효과 자체는 그대로였다 (`_offer_is_activatable` 이 `is True` 만
통과시키고, 그 분기의 답은 `True`/`False` 중 하나였다). 그래서 이것은
**설명의 결함**이고, 고친 것은 코드와 설명 둘 다다 (§2.1).

### 11.2 두 BLOCKER 의 현재 상태

| 추가 보완의 BLOCKER | 현재 |
|---|---|
| F2-1 — 창이 자리별로 나뉘지 않는다 | **상대 자리에 대해 해소.** 양쪽이 같은 사건에 기회를 들 때는 남았다 → BLOCKER-F3-1 |
| F2-2 — 같은 체인에 유발 둘을 끝까지 등록할 수 없다 | **엔진 통합 경로 해소 (합성).** 실제 카드 지원은 남았다 → BLOCKER-F3-2 |
| F2-3 — 창에 사건이 하나뿐이어서 어휘 판정이 쓰이지 않는다 | **그대로** → BLOCKER-F3-4 |
| F2-4 — SEGOC 의 순서는 의무 우선순위까지만 | **그대로** → BLOCKER-F3-3 |
| F2-5 — 보류의 `missing` 출처가 다섯 종류다 | **그대로.** 이 Phase 는 `missing` 의 **출처를 통일하지 않았다** — 한 것은 그 이름이 붙은 보류를 밖으로 내보내는 것이고 (④), 이름 자체의 어휘를 정리하는 일은 범위 밖이다 |

### 11.3 과장하지 않은 것 — 이번 보고서가 지킨 구분

- ① 은 **구조적 결함**이고 실행 우회가 재현된 것이 아니다 (§2.1 · §10).
- ③ 은 **합성 검증**이고 실제 카드 지원 완료가 아니다 (§5 · §10).
- "현재 한 시나리오에서 관측되지 않았다" 를 "실행 경로 전체에서
  불가능하다" 로 일반화하지 않았다 — ①의 미재현은 **입력 구간이 비어
  있다는 측정**(`test_b04b` 가 고정한 사실)에 근거한다.
- 통과한 시험 수가 많다는 이유로 미달성 기준을 완료로 바꾸지 않았다 —
  §10 에 **부분 완료 · 미달성**을 그대로 남겼다.
- Discord 검사는 **토큰 없는 응답 생성 검사**이고 실제 접속 검증이 아니다.
- `Journal` 순번을 규칙상 사건의 동시성 · 처리 순서와 같다고 가정하지
  않았다 (§6 · BLOCKER-F3-3).
