# 제한된 전개 탐색 첫 구현 (Phase 6-AH)

기준 HEAD: `79ce531a56a13b0e1555b10dadfbc36114d01c64`
선행 보고서: `docs/orcust-girsu-token-line.md` · `docs/orcust-first-executable-combo.md`

## 0. 이번 단계의 완료 기준

> **"정해진 카드 순서를 호출하지 않고, 엔진이 허용한 분기를 탐색하여 목표
> 경로를 찾고 재생까지 성공했다"**

🔴 **"더 강한 집을 만들었다" 가 아니다.** 이 Phase 에는 평가 함수가 없고,
전개 강도도 승률도 재지 않는다. 찾는 것은 **목표에 닿는 한 경로**다.

목표는 하나다 —

> 자신 필드에 「오르페골 갈라테아」 [30741503] 가 **앞면으로** 있고,
> 진행 중인 체인과 필수 처리가 **정리된** 상태다. 성공 여부는 실제
> `GameState` 에서 판정한다.

## 1. 고정 정책과 이번 탐색의 차이

| | 고정 정책 (`deck.combo_policy`, 6-AC·6-AF) | 제한 탐색 (`agent.bounded_search`, 6-AH) |
| --- | --- | --- |
| 무엇을 고르는가 | 사람이 적어 둔 **네 단계**를 순서대로 찾아 고른다 | **엔진이 그 자리에서 허가한 후보** 전부를 펼친다 |
| 적혀 있지 않은 판 | 아무것도 고르지 못하고 `None` 을 돌려준다 | 그 판의 후보를 똑같이 펼친다 |
| 해결 중 선택 | 경로가 적어 둔 카드 ID 를 먼저 집는다 (`PreferredCardChoice`) | 그 자리의 **허용 후보 안에서 다른 답을 해 본다** |
| 멈추는 기준 | 적어 둔 단계가 끝나거나 다음 단계를 못 찾을 때 | **목표 판정** · 예산 · 범위 소진 |
| 카드 ID 가 쓰이는 자리 | 단계마다 (`kind` · `card_id` · `effect_ref` · 소재 · 해결 선택) | **목표 지정 하나** (`FieldGoal.card_id`) |

🔴 **구조로 지킨다.** `agent/bounded_search.py` 는

* `ORCUST_GIRSU_LINE` · `ORCUST_GIRSU_TOKEN_LINE` · `ComboLine` ·
  `VerificationLinePolicy` 를 **코드로 한 번도 쓰지 않고**,
* `deck` 도 `integration` 도 `core` 도 **import 하지 않으며**
  (`agent` → `engine` 만, ADR-007 의 경계 그대로),
* **카드 ID 리터럴이 하나도 없다** (10,000 이상의 정수 상수 0건).

세 가지를 AST 로 세는 시험이
`tests/test_bounced_search_first_pass.py::test_a03` 이다.

🔴 **찾은 경로가 적어 둔 경로와 같을 필요가 없다.** 실제로 토큰 입력에서
탐색이 찾은 경로는 기르수 ① 을 **발동한다** — 적어 둔 토큰 경로는 그 기회를
`declines` 로 지나간다. 엔진이 허가하고 목표에 닿으면 그것으로 충분하다.

## 2. 실제로 지원하는 행동·선택 범위

### 2.1 행동

탐색이 펼치는 것은 `duel.legal_actions(seat).allowed` 의 원소뿐이다. 이
모듈에는 `PlayerAction` 을 **만드는 코드가 없다**.

| | 다루는 방식 |
| --- | --- |
| 일반 소환 · 세트 · 링크 소환 · 효과 발동 · 패스 | 후보로 올라온 그대로 펼친다 |
| `end_phase` | **펼치지 않는다** — 이 턴을 벗어나는 유일한 수다 (§4.3) |
| 상대 자리의 수 | **탐색하지 않는다.** 명시적인 무방해 정책이 패스한다 (§2.3) |
| 미지원으로 보류된 수 | 후보가 아니므로 펼치지 않고, **사유를 따로 보존한다** (§4.4) |

🔴 **`UNKNOWN` 을 합법으로 바꾸지 않는다.** 보류된 수는 `legal.allowed` 에
없으므로 구조적으로 펼칠 수 없다.

### 2.2 해결 중 선택

행동 순서만 바꾸고 카드 선택을 `first-permitted` 로 고정하면, 다른 해결
선택으로 열리는 경로를 찾을 수 없다. 그래서 선택도 분기한다.

```
빈 각본으로 한 번 돌린다
      ↓  ScriptedChoice.log 에 그 걸음의 물음 전부가 남는다
그 기록의 실제 답을 앞부분으로 고정하고 한 자리만 다른 답으로 바꾼다
      ↓  부모의 판에서 처음부터 다시 (사본은 각본마다 하나)
다른 미래
```

지키는 것 —

1. **후보는 엔진이 낸 것뿐이다** — `offer.permitted` 를 그대로 옮긴
   `ChoiceAsk.offered` 가 분기의 재료다.
2. **장수 조건을 지킨다** — `selection_options` 가 `minimum`~`maximum`
   안의 조합만 만든다.
3. **후보 밖을 지정하지 않는다** — 각본의 번호가 그 자리의 허용 후보에
   없으면 쓰지 않고 `ChoiceAsk.plan_missing` 에 적는다.
4. **원본을 고치지 않고 효과를 두 번 적용하지 않는다** — 각본마다 부모의
   판에서 **처음부터** 다시 한다.
5. **잘린 분기를 적는다** — 상한에 걸리면
   `SearchOutcome.out_of_scope` 에 남는다.

🔴 **기존 인터페이스를 최소로 늘렸다.** 새로 만든 것은 두 군데뿐이다.

| 자리 | 늘린 것 |
| --- | --- |
| `agent/choice.py` | `ScriptedChoice` · `ChoiceAsk` — **새 클래스 둘**, 기존 정책은 한 글자도 바뀌지 않았다 |
| `agent/simulation.py` | `Simulator.fork(selector=…)` — 기존 `_fork` 를 **그대로 부르는** 공개 메서드 |
| `integration/autonomy.py` | `PolicyChooser.forked(selector=None)` — 인수 하나를 더했고, 주지 않으면 6-AB 와 **같다** |

### 2.3 상대는 명시적인 정책이다

"상대의 방해가 없다" 를 조용히 가정하지 않는다.

```
NO_INTERFERENCE = "no-interference (상대는 언제나 패스한다)"
```

* 상대 자리가 오면 **패스를 고른다.** 패스도 `legal_actions` 를 지나
  `apply` 로 들어간다 — 손으로 우선권을 돌리지 않는다.
* 그 자리에 **패스 말고 다른 수가 있었으면** 그 사실을
  `SearchOutcome.opponent_declined` 에 적는다.
* 상대 자리에 **고를 것이 남아 패스할 수 없으면** 더 펼치지 않고
  `SearchOutcome.opponent_blocked` 에 적는다 — 아무 수나 골라 주지 않는다.

### 2.4 필수 처리를 생략하지 않는다

한 걸음은 "고른 행동 하나 + 그 뒤의 **고르는 일이 아닌 걸음들**" 이다.

| 지나가는 것 | 왜 고르는 일이 아닌가 |
| --- | --- |
| `duel.advance()` | 고르지 않아도 일어난다 (드로우) |
| 자기 자리에 **패스뿐**인 걸음 | 고를 것이 하나면 고르는 일이 아니다 (`Simulator._settle_forced_passes` 와 같은 근거) |
| 상대 자리 | §2.3 의 명시적 정책 |

🔴 **고를 것이 있으면 즉시 멈춘다.** 그 자리가 진짜 결정 지점이다.

🔴 **목표에 일찍 닿아도 남은 필수 처리를 건너뛰지 않는다.** 목표 판정이
"판이 정리되었는가" 를 함께 묻기 때문이다 (§4.2).

## 3. 상태 복제와 중복 제거

### 3.1 이미 있는 fork 를 재사용했다

새 복제 기계를 만들지 않았다. `Simulator._fork` 가 하는 일을 그대로 쓴다 —
`GameState.clone()` (난수원까지 복제, `project()` 는 쓰지 않는다) · 사본의
**새 기록** (부모의 사건을 씨앗으로) · 부모의 효과 정의와 실행 계약 ·
사본용 고르는 사람.

그래서 분기마다 독립적으로 보존되는 것 —

| | 어디서 오는가 |
| --- | --- |
| 카드 위치와 개체 식별 | `GameState.clone()` |
| 토큰과 토큰 소멸 | 같음 (토큰도 인스턴스다) |
| 턴 · 페이즈 · 우선권 | `dataclasses.replace` 가 값으로 가져간다 (`PriorityState` 는 frozen) |
| 체인과 보류된 유발 처리 | 같음 (`chain` · `consumed_events` · `window_passed` · 세 바닥) |
| 일반 소환권 · 효과·소환 사용 제한 | `GameState.clone()` (`uses` · `rule_uses` · `summon_uses`) |
| 선택 상태와 실행 기록 | 사본의 **새** 기록 + 사본의 `ScriptedChoice` |

🔴 **원본은 건드리지 않는다.** `BoundedSearch.run` 이 시작과 끝의
`state_hash` 와 난수 좌표를 직접 비교하고, 어긋나면 **던진다**.
`test_c01` 이 받은 듀얼의 필드 · 패 · 턴 번호와 **고르는 사람의 기록이
비어 있음**을 센다.

### 3.2 기존 `state_hash` 는 탐색에 **모자란다**

`GameState.canonical_state` 는 체인 · 우선권 · 기록을 **일부러 뺀다** —
"같은 판" 의 뜻을 도달 경로와 무관하게 두려고 그렇게 두었다. 탐색에는
그 빠진 것이 미래를 바꾼다.

그래서 열쇠(`node_key`)는 다섯 칸이다.

| 칸 | 무엇을 막는가 |
| --- | --- |
| `state.state_hash()` | 판의 모양 + **사용 제한** + 턴당 소환 기록 + 턴 |
| `to_act` | 지금 고를 사람이 다른 자리를 합치지 않는다 |
| `step` · 응답 창 | 흐름 위의 자리가 다르면 할 수 있는 일이 다르다 |
| **허용 후보 집합** | 엔진이 "지금 무엇을 할 수 있는가" 에 준 답 그대로 |

그리고 **합치지 않는 자리**가 있다.

* **체인이 진행 중이면 열쇠가 `None`** 이다 — 체인 도중의 두 자리를 같다고
  볼 안전한 기준이 없으므로 합치지 않는다. 중복 제거를 못 하는 것이 틀린
  병합보다 낫다.
* **기록 전체를 열쇠에 넣지 않는다** — 넣으면 모든 노드가 영원히 달라지고
  중복 제거가 사실상 꺼진다. 지나간 사건 중 아직 쓸 수 있는 것이
  무엇인지는 **허용 후보 집합**에 이미 나타난다 (유발 후보가 그렇게
  오른다).

🔴 **미래 동치의 증명이 아니다.** "지금 할 수 있는 일과 사용 제한이 같은 두
자리를 같다고 본다" 는 **보수적인 기준**이고, 그 한계는 §6.3 에 적었다.
`test_c04` 가 세 가지를 센다 — 체인 중에는 열쇠가 없다 · 소환권을 쓰면 다른
열쇠다 · 허용 후보가 달라지면 다른 열쇠다.

## 4. 예산과 종료 상태

### 4.1 예산 네 칸

| 칸 | 기본값 | 뜻 |
| --- | --- | --- |
| `max_depth` | 8 | 한 경로의 최대 걸음 수 |
| `max_nodes` | 300 | **펼친 노드** 상한 (사본에 행동을 적용한 횟수) |
| `max_seconds` | 300 | **안전장치** — 기계가 느리면 먼저 걸린다 |
| `max_choice_branches` | 8 | **한 행동**에서 만들 해결 중 선택 분기 상한 |

🔴 **같은 입력 · 같은 노드·깊이 예산이면 결과가 재현된다.** 후보를 줄
세우는 열쇠가 `(kind, repr(canonical_state()))` 로 결정론적이고, 선택 조합도
번호로 정렬한 뒤 만든다. 시간 제한은 안전장치이므로 시험은 **실행 속도에
의존한 단언을 쓰지 않는다**.

### 4.2 목표 판정 — 다섯 조건

```
reached  ⟺  present  그리고  settled
```

`settled` 는 다섯을 함께 본다 — 듀얼이 끝나지 않았다 · 체인이 비었다 ·
응답 창이 닫혔다 · 지금 고를 사람이 자신이다 · **엔진이 그 자리에서
`end_phase` 를 허가한다.**

🔴 **마지막 조건은 실측한 결함을 고친 것이다.** 앞의 넷만 보면 일반 소환
**직후**가 "정리된 자리" 로 읽혔다 — 체인은 비어 있고 응답 창도 `none`
이지만, 그 자리에는 **유발 처리 기회**가 열려 있어 엔진이 `end_phase` 를
*"유발 처리 기회가 열려 있습니다 — 판이 열린 상태가 아니므로 그 기회를
처리한 뒤에 진행합니다"* 로 보류했다. 그 자리를 목표로 읽으면 **남은 필수
처리를 생략**하게 된다. 그래서 "판이 열렸는가" 를 **엔진의 답으로** 묻고,
이 계층이 그 조건을 다시 짜지 않는다. `test_a04` 가 그 자리를 고정한다.

### 4.3 이 턴을 벗어나지 않는다

`end_phase` 는 전개하지 않고, 그 사실을 `out_of_scope` 에 적는다.

```
OUT_OF_TURN_SCOPE = "end_phase: 이 턴을 벗어나는 수이므로 이번 범위에서
전개하지 않았습니다 — 다음 턴의 자원으로 목표에 닿는 경로는 찾지 않습니다."
```

턴을 넘기는 유일한 수가 그것이므로, 고르지 않는 것이 **구조적인 보장**이다
(`advance()` 는 드로우 페이즈의 드로우만 한다). `test_d04` 가 턴 번호가
그대로임과 경로에 `end_phase` 가 없음을 센다.

### 4.4 종료 사유 네 가지

| `Termination` | 뜻 |
| --- | --- |
| `goal_reached` | 목표에 닿는 경로를 찾았다 |
| `exhausted` | 지정된 범위를 모두 펼쳤고 **그 안에** 목표가 없었다 |
| `budget_exceeded` | 예산에 걸려 멈췄다 — 🔴 **못 찾았다는 뜻이 아니다** |
| `error` | 실행 중 예외가 났다 |

🔴 **예산에 걸린 채로 "범위를 다 펼쳤다" 고 적지 않는다.** 깊이 상한에 걸려
더 내려가지 못한 가지가 하나라도 있으면 `budget_exceeded` 다 — 그 둘은 다른
사실이다.

🔴 **미지원은 종료 사유와 별개 칸이다.**

| 칸 | 무엇 |
| --- | --- |
| `unsupported` | 그 자리에서 **지원하지 않아 후보가 되지 못한** 수들 |
| `out_of_scope` | 이번 범위에서 **일부러** 펼치지 않은 분기 |
| `opponent_declined` / `opponent_blocked` | 상대 자리에서 일어난 일 |
| `errors` | 예외 |

🔴 **경로를 못 찾았다는 이유로 "실제 듀얼에서 불가능하다" 고 결론 내리지
않는다.** 요약과 상세 모두 그 문장을 적지 않고, 종료 사유의 뜻을 한국어로
적는다 (`deck.report._TERMINATION_KO`).

### 5.1 실제 카드 입력별 경로 · 노드 수 · 소요 시간

🔴 **무엇으로 쟀는가.** 아래 수치는 `app.main.bounded_search_opening` 을
입력마다 **한 번씩** 부르는 스크립트의 결과다 (`pytest` 묶음의 fixture 와
**같은 입력 · 같은 예산**). CLI 의 `--search galatea` 와 Discord 의
`search:galatea` 도 **같은 함수**를 부르므로 (§7) 같은 수치가 나온다 —
다만 그 두 경로는 출력 렌더링과 `[실제 엔진 실행]` 절을 함께 돌리므로
**전체 소요는 더 길다.**

## 6. 미지원과 한계

### 6.1 해결 중 선택이 목표를 가르는 **실제 카드** 사례를 만들 수 없다

기르수 ① 의 허용 후보가 되려면 `MAY_BE_SENT_TO_GRAVE` 가 `TRUE` 여야 하고,
그 답은 (1) 손으로 등록한 재정이나 (2) **자기 묘지행을 전제한 텍스트
증거**(`self_grave_text_evidence`)에서만 나온다 (ADR-006).

🔴 **실측**: 저장소의 카드 **14,759장 전수**에서 「오르페골」(`0x11b`) ·
「성유물」(`0xfe`) setcode 를 가지고 그 둘 중 하나를 만족하는 카드는
**93920420 하나뿐**이다. 그래서 그 선택의 허용 후보는 실제 카드로는 언제나
**같은 카드의 사본들**이고, 선택이 목표 도달을 가르는 판을 실제 카드만으로는
만들 수 없다.

그래서 `test_b02` 는 **확인된 재정 한 건만** 격리해 끼운다 —
「오르페골 클리막스」(703897) 의 `MAY_BE_SENT_TO_GRAVE` 를 `TRUE` 로. 카드 ·
효과 · 체인 · 목표는 전부 실제이고, production 의 `OPERATION_RULINGS` 는
`monkeypatch` 가 되돌린다 (`test_b04` 가 되돌아왔는지 센다).

🔴 **그 사례를 실제 카드 전개 성공의 근거로 쓰지 않는다.** 실제 카드 전개가
성공한다는 주장은 §5.1 의 두 입력(`test_a01` · `test_a02`)이 혼자 들고 있다.

### 6.2 상대의 선택은 탐색하지 않는다

명시적인 무방해 정책이 패스하고, 상대 자리에 고를 것이 남으면 그 노드에서
멈춘다. 상대 방해 탐색은 이번 범위가 아니다.

### 6.3 중복 제거 기준은 미래 동치의 증명이 아니다

§3.2 의 열쇠는 "지금 할 수 있는 일과 사용 제한이 같으면 같다고 본다" 는
보수적인 기준이다. 지나간 사건 중 **지금은 후보로 오르지 않지만 나중에
오를 수 있는** 것이 있다면 그 두 자리는 미래가 다를 수 있다. 그 경우를
배제하는 증명은 하지 않았고, 체인 중에는 **아예 합치지 않는다**.

### 6.4 그 밖에 이번에 열지 않은 것

| | |
| --- | --- |
| 전개 강도 · 승률 평가 | **없다.** 노드 순서는 `canonical_state` 의 결정론적 순서이고 좋음의 척도가 아니다 |
| 새 카드 효과 · 소환법 | 더하지 않았다 |
| 자동 레시피 생성 · LLM · 인터넷 검색 · 외부 시뮬레이터 | 연결하지 않았다 |
| 다음 턴 | `end_phase` 를 펼치지 않으므로 구조적으로 닿지 않는다 (§4.3) |
| 유발즉시 발동 | 여전히 `UNKNOWN` 이다 (6-AG §7.7 그대로) |
| 「링크 소재로 할 수 없다」 류 지속 제약 | 여전히 못 본다 (6-AG §7.7 그대로) |

## 7. 사용자 실행 진입점

기존 `/combo` 동작과 검증용 정책(`line:`)은 **그대로 유지**한다. 탐색은
**명시적으로 골라야** 돌아간다.

| 어댑터 | 인터페이스 |
| --- | --- |
| Discord | `/combo … search:galatea` (`search` 옵션 하나를 더했다) |
| CLI | `python3 -m app.main combo … --search galatea` |

🔴 **주지 않으면 돌리지 않는다.** `search:` 없는 요청의 출력은 6-AG 와 한
글자도 다르지 않다 (`test_e06` 이 센다).

🔴 **모르는 목표 이름은 비슷한 것으로 고쳐 주지 않는다** — 있는 목표를
적고 돌리지 않는다. `line:` 과 같은 규율이다.

🔴 **핵심 탐색은 Discord 코드에 없다.** 세 계층을 잇는 자리가
`app.main.bounded_search_opening` 하나이고 (CLI 와 Discord 가 같은 것을
쓴다 — `opening_wiring` 과 같은 규율), 요약과 상세는 공용 보고 함수
(`deck.report.render_bounded_search_brief` · `render_bounded_search`)가
만든다. 어댑터는 `agent` 도 `integration` 도 직접 import 하지 않는다.

🔴 **엔진을 두 번 돌린다 — 그리고 그 둘은 다른 것이다.** `search:` 를 주면
기존 `[실제 엔진 실행]` 절(고정 경로 또는 `first_meaningful`)과 `[제한 전개
탐색]` 절이 **각자 한 번씩** 돌린다. 6-AE 의 "엔진을 한 번만 돌린다" 는
*같은 실행의* 요약과 상세를 두 번 계산하지 않는다는 규율이고, 여기서는
사용자가 **다른 실행 방식 둘**을 명시적으로 고른 것이므로 섞지 않는다 —
섞으면 "적어 둔 경로를 따라간 것" 과 "엔진이 허가한 분기를 펼친 것" 을
구별할 수 없다.

🔴 **봇의 비동기 응답을 막지 않는다.** 기존 `/combo` 와 같은 구조다 —
`interaction.response.defer()` 로 3초 제한을 먼저 넘기고 실제 탐색은
`asyncio.to_thread` 로 보낸다 (탐색은 실측 20~180초다 — §5.1).

### 7.1 복사 가능한 실행 예시

레시피는 저장소의 **검증용** 레시피다 (`deck.combo_policy.
ORCUST_VERIFICATION_RECIPE`). 🔴 **자동 생성한 실전 덱이 아니다** — 이
Phase 의 실행을 재현하기 위한 명시적 분석 조건이다.

**CLI** (레시피를 `.ydk` 파일로 저장해 두고):

```
python3 -m app.main combo "69811710,703897,2930675,12989604,93920420" \
    --recipe <ORCUST_VERIFICATION_RECIPE 를 적은 .ydk> \
    --search galatea
```

패에 『성장』 이 **없는** 입력 (토큰 입력):

```
python3 -m app.main combo "69811710,703897,2930675,12989604,55051920" \
    --recipe <같은 .ydk> \
    --search galatea
```

**Discord**:

```
/combo hand:69811710,703897,2930675,12989604,93920420 recipe:<위 레시피> search:galatea
```

적어 둔 경로와 **함께** 볼 수도 있다 (두 절이 따로 나온다):

```
/combo hand:69811710,703897,2930675,12989604,93920420 recipe:<위 레시피> \
       line:orcust-girsu search:galatea
```

### 7.2 요약에 적는 것

§6 이 요구한 다섯 가지를 요약이 전부 적는다 (`test_e05` 가 센다).

1. 실행 방식이 **제한 탐색**이라는 것
2. 목표 도달 여부 (`✔ 도달` / `✗ 미도달` + 종료 사유의 뜻)
3. **행동 수와 탐색 노드 수** (그리고 해결 중 선택 횟수 · 최대 깊이 · 소요)
4. **예산 종료 여부** (걸린 칸의 이름까지)
5. **전체 규칙 지원을 뜻하지 않는다**는 설명 + 최선 전개·승률 평가가
   아니라는 설명

상세 행동과 선택 · 미지원 내역은 **기존 상세 기록 첨부**를 그대로 쓴다 —
첨부에 「제한 전개 탐색」 절이 따로 붙고, 고정 경로 실행 절과 섞지 않는다.

### 7.3 어댑터 경로 실측

`combo_response` 를 **실제로 한 번씩** 불러 쟀다 (🔴 Discord 로 메시지를
보내지는 않는다 — 이 함수는 메시지와 첨부를 값으로 돌려준다).

| | 기본 메시지 | 첨부 | 소요 |
| --- | --- | --- | --- |
| `search:` **없이** | 1개 | 1개 (`combo-detail.txt`) | 15.9초 |
| `search:galatea` | **2개** | 1개 · **21,752바이트** | 48.7초 |

* `search:` 없이 돌린 응답에는 「제한 전개 탐색」 이 **한 글자도 없다.**
* `search:galatea` 응답에는 `✔ 도달` · `경로 재생` 이 요약에 있고, 첨부에
  **탐색 절 · 입력 조건 · 그 자리의 허용 후보**가 들어 있다.
* 🔴 **기존 요약의 줄이 하나도 사라지지 않았다** (실측: `search:` 없는
  응답의 모든 줄이 `search:` 있는 응답에도 있다). 더해진 것은 21줄이다.
* 메시지가 1개 → 2개로 늘지만 상한(`COMBO_MESSAGE_LIMIT = 4`) 안이므로
  **잘리는 줄이 없다.**

## 8. 재생 (§5)

🔴 **탐색이 만든 최종 상태를 그대로 내보내는 것으로 끝내지 않는다.**

```
build_opening(...)  ← 같은 입력으로 만든 새 초기 상태
      ↓  걸음마다
legal_actions 에서 canonical_state 가 같은 후보를 다시 찾는다
      ↓  없으면 🔴 재생 실패
ScriptedChoice(기록된 선택) 로 적용
      ↓  기록된 선택이 그 자리의 허용 후보가 아니면 🔴 재생 실패
최종 판의 해시와 자신 필드를 탐색 결과와 비교
```

| 재생이 확인하는 것 | 어긋나면 |
| --- | --- |
| 기록된 행동이 **지금 허용 후보**인가 | `ok=False` + 몇 번째 걸음인지 |
| 기록된 선택이 **그 자리의 허용 후보**인가 | `ok=False` + 어느 물음인지 |
| 물음 수와 고른 것이 기록과 같은가 | `ok=False` + 기록과 실제 |
| 목표에 닿았는가 | `ok=False` + 목표 판정의 이유 |
| 최종 해시와 자신 필드가 **같은가** | `ok=False` + 두 해시 |

🔴 **재생 실패를 성공 결과로 출력하지 않는다.** 요약이 `🔴 실패` 와
*"재생이 실패했으므로 성공 결과로 읽지 마십시오"* 를 적는다.
`test_e02` · `test_e03` · `test_e04` 가 기록을 일부러 어긋나게 해서 그
실패를 고정한다.
