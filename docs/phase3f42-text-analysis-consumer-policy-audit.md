## 3. 기존 데이터 모델로 구별 가능한 상태

여섯 상태를 **직접 구성해서** 확인했다 (`test_06`~`test_13`).

| 상태 | 구별 가능? | 어떻게 |
|---|---|---|
| ① 텍스트 분석을 시도하지 않음 | ✔ (모델 밖) | `TextAnalysis` 객체가 **생기지 않는다**. production 전체가 이 상태다 |
| ② 시도했으나 결과 없음 | ✔ | `has_text=True · skipped_reason=None · effect 있음 · actions=[]` |
| ③ 결과를 생성함 | ✔ | `is_empty=False` |
| ④ 분석할 텍스트가 없음 | ✔ | `has_text=False · effect=None` |
| ⑤ 시도했으나 일부러 건너뜀 | ✔ | `skipped_reason is not None` (설정 문구 보호) |
| ⑥ 분석 실행 중 오류 | ✘ | 전용 칸 없음, `try/except` 없음 |

🔴 **편의 속성 하나로는 셋이 뭉친다.** ②④⑤ 모두 `is_empty=True` 다. 그러나
세 칸(`has_text`·`skipped_reason`·`effect`)을 보면 세 상태가 전부 다르다
(`test_11` 이 세 서명이 서로 다름을 확인한다). **정보가 없는 것이 아니라 한
속성만 보면 사라진다** — 이것이 N49 의 정확한 모습이다.

🔴 **⑥ 의 트리거도 재현되지 않는다.** `analyze(None)` 은 예외 대신
`TextAnalysis(card_id=0)` 을 돌려주고, `desc`·`desc_en` 이 비어도 예외가 나지
않는다 (`" ".join(... if t)` 가 걸러낸다). 즉 **담을 칸이 없는 상태의 발생
경로도 없다**. §3 이 "현재 구조로 구별할 수 없다면 어느 소비자가 이 구분을
필요로 하는지 입증하라" 고 했고, **소비자가 0개**이므로 칸을 만들지 않았다.

🟢 **결과 생성이 의미 검증을 뜻하지 않는다.** `TextAnalysis` 에 검증을
뜻하는 칸이 아예 없어 그렇게 주장할 수단 자체가 없다 (`test_13`).

### 4.1 🟠 범위 밖에서 찾은 잠재 위험 — 텍스트 라벨이 **이름**으로 결정된다

`app/main.py` `print_card_detail`:

```python
label = "카드 텍스트(한국어)" if card.name_ko else "카드 텍스트"
```

텍스트의 라벨을 **텍스트**가 아니라 **이름**(`name_ko`)으로 고른다. 그리고
`KoreanTextSource.apply` 는 이름과 텍스트를 **서로 독립된 조건**으로 채운다:

```python
name = entry.get("name", "").strip()
if name: card.name_ko = name; card.name = name
desc = entry.get("desc", "").strip()
if desc: ...; card.desc = desc
```

이름만 있고 텍스트가 없는 항목이 들어오면 **영어 텍스트에 "한국어" 라벨이
붙는다.** 그 사례를 구성해 실제로 재현했다 (`test_22`).

🟢 **그러나 실제 코퍼스에는 0장이다** (`test_23`: 이름 한국어 + 텍스트 원문
그대로 = 0장, 이름·텍스트 모두 한국어 13,728장, 이름이 한국어 아님 393장).
§4 가 "표시 정책을 바꾸려면 **재현 사례**가 있어야 한다" 고 했고, 실제
소비자가 잘못된 정보를 보는 사례가 없으므로 **고치지 않았다.** 위험으로만
기록한다 (N51).

* **`print_card_detail` 라벨을 고치지 않았다** — 재현 사례 0장 (§4.1).
* **상태 승격·강등 없음** — `TEXT_DERIVED` 를 오류로 바꾸지 않았고,
  `MATCHED` 를 의미 검증으로 취급하지 않았다 (`test_25`, `test_13`).
