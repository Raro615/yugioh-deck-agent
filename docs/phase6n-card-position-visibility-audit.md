## 1. 현재 카드 표시 형식 모델의 실제 구조

### 1-1. 값은 **하나의 칸**에 여덟 개

`engine/vocabulary.py` 의 `Position` 이 앞뒷면과 공격·수비를 **한 값에
함께** 담는다. `CardInstance.position` 이 그 칸이고, 그것 하나뿐이다.

| 값 | `is_faceup` | 뜻 |
|---|---|---|
| `FACEUP_ATTACK` | **True** | 앞면 공격 표시 |
| `FACEUP_DEFENSE` | **True** | 앞면 수비 표시 |
| `FACEUP` | **True** | 앞면 (마법·함정) |
| `FACEDOWN_ATTACK` | False | 뒷면 공격 — **필드에서는 불법** |
| `FACEDOWN_DEFENSE` | False | 뒷면 수비 표시 |
| `FACEDOWN` | False | 뒷면 (세트된 마법·함정 · 덱 · 패) |
| `ATTACK` | False | 🔴 **앞뒷면을 말하지 않는다** |
| `DEFENSE` | False | 🔴 **앞뒷면을 말하지 않는다** |

### 1-2. 표시 형식을 정하는 production 상수는 **넷**

| 자리 | 상수 | 값 |
|---|---|---|
| `engine/normal_summon.py` | `SUMMON_POSITION` | `FACEUP_ATTACK` |
| `engine/set_card.py` | `SET_MONSTER_POSITION` | `FACEDOWN_DEFENSE` |
| `engine/special_summon.py` | `SPECIAL_SUMMON_POSITION` | `FACEUP_ATTACK` |
| `engine/spell_activation.py` | `ACTIVATION_POSITION` | `FACEUP` |

넷 다 앞뒷면을 말하는 값이다. 그래서 §1-1 의 두 공백(`ATTACK` ·
`DEFENSE`)은 **production 이 만들지 않는다** (AST 로 센다).

### 1-3. 직전 상태가 **따로 남는다**

`CardInstance.previous` (`PreviousState`) 가 자리 · 표시 형식 · 컨트롤러
셋을 들고 있다. 그래서 §4-A 6 ("카드가 필드를 벗어난 이후에도 이전 표시
상태가 필요한 사건")은 **표현할 수 있다.**

## 2. 앞면·뒷면 및 공격·수비 상태 지원 범위

§4-A 의 여섯 질문에 코드로 답한다.

| 질문 | 답 |
|---|---|
| 1. 표시 형식 필드가 있는가 | 🟢 있다 (`CardInstance.position`) |
| 2. 앞뒷면과 공격·수비를 독립적으로 표현하는가 | 🟡 **독립 칸이 아니다** — 한 값이 둘을 함께 말한다. 그런데 조합 여섯이 모두 값으로 있으므로 **표현 능력은 충분하다** |
| 3. 앞면 공격 · 앞면 수비 · 뒷면 수비를 구분하는가 | 🟢 구분한다 |
| 4. 뒷면 공격 표시가 불법으로 처리되는가 | 🔴 **아니다.** `battle.ATTACK_POSITIONS` 가 `FACEDOWN_ATTACK` 을 **포함한다.** 다만 production 이 그 값을 필드에 만들지 않는다 (§17-2) |
| 5. 카드가 이동하면 표시 형식이 어떻게 되는가 | 🟡 **그대로 남는다.** `GameState.move` 가 건드리지 않는다 (§11) |
| 6. 필드를 떠난 뒤에도 이전 표시 형식이 필요한 사건을 표현할 수 있는가 | 🟢 `PreviousState.position` 이 있다 |

공격·수비 쪽은 **조건이 하나도 없다** — `CardIsAttackPosition` 류가 0건이다
(§10). §9 에 따라 만들지 않았다.

## 3. 표시 상태 관련 실제 차단 사례

### 🔴 선정한 사례 — **같은 판이 두 답을 냈다**

`BoardRuling._interference` 가 판을 훑으며 "막을 수 있는 것이 있는가" 를
본다. 그 훑기가 **자리를 보지 않고 앞뒷면만** 보고 "세트된 카드는 효과를
적용하지 않는다" 며 건너뛰었다.

**묘지에는 뒷면이 없다.** 그런데 `move` 가 표시 형식을 건드리지 않으므로,
패에서 버려진 카드는 `position=FACEDOWN` 을 들고 묘지에 있다.

구현 전 실측 — 묘지에 **미등록 카드**(사파이어 드래곤, 판정 지식에 없다)가
있는 **같은 판**:

| 그 카드가 묘지에 간 경로 | `position` | 관측 `face_up` | `BoardRuling` | 어니스트 ① |
|---|---|---|---|---|
| 필드에서 앞면으로 | `FACEUP_ATTACK` | `True` | `UNKNOWN` | **막혔다** (`UNCHECKED_RULES`, MZONE) |
| 패에서 버려졌다 | `FACEDOWN` | `False` | **`TRUE`** | **해결됐다** (HAND) |

🔴 그리고 관측은 **그 카드의 정체를 보여 준다** (`card_id=11091375`) —
묘지는 공개 존이므로 당연하다. 즉 엔진은 **무엇인지 아는 카드를** 뜻 없는
`position` 값 때문에 건너뛰었다.

### §9 의 일곱 기준 대조

| 기준 | 판정 |
|---|---|
| 1. 기존 카드·행동 데이터가 존재한다 | 🟢 등재·실행 가능한 효과 **다섯**이 묘지에 카드를 보낸다 (육신보살 · 의적의 입문서 · 무정한 말살 · 어리석은 매장 · 벌금) |
| 2. 표시 상태가 실제 판정에 필요하다 | 🟢 `_interference` 가 `face_up` 을 읽는다 |
| 3. 현재 엔진에서 해당 상태를 확인할 수 없다 | 🔴 **아니다 — 정직하게 적는다.** 상태는 있다. 누락은 "그 질문을 **물어도 되는 자리인가**" 였다 |
| 4. UNKNOWN · RULE_NOT_IMPLEMENTED 또는 잘못된 판정이 발생한다 | 🟢 **잘못된 판정** — 같은 판, 두 답 |
| 5. 기존 모델에 대한 최소 수정으로 해결 가능하다 | 🟢 한 함수의 조건 한 줄 |
| 6. 카드별 예외가 필요하지 않다 | 🟢 카드 ID 분기 0건 |
| 7. 실제 GameState 에서 전후 차이를 검증할 수 있다 | 🟢 §11 |

기준 3이 어긋나므로 **"표시 상태 모델이 없어서 막혔다" 는 주장은
철회한다.** 모델은 있었다. 막힌 것은 **그 모델을 읽는 규율**이었다.

### 🔴 선정하지 **않은** 사례 — 주장을 철회한다

| 후보 | 왜 아닌가 |
|---|---|
| 후보 생성의 앞면 필터 | **쓸 카드가 0건이다.** 등재 17건 중 앞면 조건을 쓰는 것이 하나도 없다. 그리고 `CandidateSource.require` 가 이미 `Condition` 을 받아 **모델 변경 없이** 표현된다 (실측: 후보 2장 → 1장) |
| 공격·수비 조건 | 술어가 0건이고 **요구하는 등재 카드도 0건**이다 |
| 어니스트 ① 의 「앞면 표시의」 | 6-M §16-1 이 남긴 것이고 **실제로는 닿지 않는다** — Phase 6-K 가 뒷면 몬스터의 효과 발동을 막는다 (실측: 후보 0, `apply` 거절). §17-1 에 남겼다 |
| 비공개 정보 노출 | **0건.** 패·덱은 자리로 가려지므로 표시 형식 이월이 누출을 만들지 않는다 (§9) |

## 4. 확인된 근본 원인

**한 사실을 두 곳이 묻는데, 한쪽만 자리를 봤다.**

"이 자리에서 앞뒷면이 뜻을 갖는가" 를 묻는 곳이 둘이다.

1. `engine/game_state_view._card_view` — 그 카드의 **정체가 보이는가.**
2. `engine/effect/ruling.BoardRuling._interference` — 그 카드가 **효과를
   적용하는가.**

1번은 그 사실을 `_FACE_SENSITIVE_ZONES` 로 **적어 두고 있었고**, 심지어 그
docstring 이 이 함정을 정확히 경고하고 있었다.

> "그런데 ``move_card`` 는 표시 형식을 건드리지 않으므로, 덱에서 묘지로 간
> 카드는 ``position`` 이 ``FACEDOWN`` 인 채로 남는다 — 앞뒷면만 보고
> 판단하면 **상대 묘지가 통째로 가려진다.** 존을 먼저 봐야 하는 이유다."

2번이 **그 경고를 읽지 않았다.** 같은 함정을 같은 저장소 안에서 두 번째로
밟은 것이고, 원인은 그 사실에 **공개 이름이 없어서** 복사할 수도, 읽을
수도 없었던 것이다.

## 5. 채택한 최소 수정 방식과 대안 비교

§10 의 다섯 선택지를 전부 재 보았다.

| 대안 | 채택 | 이유 |
|---|---|---|
| **A** `CardInstance` 표시 상태 필드 재사용 | ✅ | 새 칸을 하나도 더하지 않았다 |
| **B** `GameState` 의 전달 경로 보완 | ❌ | 전달은 이미 된다 — `CardView.face_up` · `position` 둘 다 실린다 |
| **C** `ActionValidator` 에 표시 판정 연결 | ❌ | 이미 연결돼 있다 (`action_validation.py` 세 자리) |
| **D** `CandidateResolver` 의 표시 조건 평가 보완 | ❌ | 이미 `require` 로 된다 (실측). 쓸 카드가 0건이므로 **더하지 않았다** |
| **E** 카드 이동과 표시 변경의 일관성 개선 | 🟡 **부분** — 값을 바꾸지 않고, **뜻이 없는 자리에서 묻는 쪽**을 고쳤다 |

### 왜 "이동 시 표시 형식을 초기화" 를 하지 않았는가

그렇게 하면 **제외 구역이 깨진다.** 거기서는 그 값이 **일을 한다** —
앞면 제외와 뒷면 제외를 구분하는 유일한 값이고, `_card_view` 가 그것으로
정체를 가린다 (실측: 앞면 제외 `card_id` 보임 / 뒷면 제외 `None`).

즉 표시 형식 이월은 **결함이 아니다.** 결함은 그 값을 **묘지에서 물은
것**이다. 그래서 값을 건드리지 않고 질문하는 쪽을 고쳤다.

## 10. 표시 상태 조건 AST 및 평가 결과

§4-D 의 다섯 질문.

| 질문 | 답 |
|---|---|
| 1. 앞뒷면을 검사할 수 있는가 | 🟢 `CardIsFaceUp` 이 **이미 있다** (6-N 이 만들지 않았다) |
| 2. 공격·수비를 검사할 수 있는가 | 🔴 **없다** (0건). 요구하는 등재 카드도 0건이므로 만들지 않았다 (§9) |
| 3. 조회할 수 없으면 무엇을 돌려주는가 | 🟢 `UNKNOWN` + 이유 문자열 ("가려진 존"). 실측 확인 |

## 17. 남아 있는 구조적 차단 요인

### 17-1. 「앞면 표시의」 를 해결 시점에 묻는 길이 없다

6-M §16-1 이 남긴 것이고 6-N 도 옮기지 못했다. `CardOperation` 에 표시

  `engine/effect/executor.py` (`_plan_card_operation`)
- **영향**: **닿지 않는다.** Phase 6-K 가 뒷면 몬스터의 효과 발동을
  막는다 (실측: 후보 0건, `apply` 거절, 판 그대로). 발동과 해결 사이에
  카드를 뒤집는 길이 이 엔진에 없다 (표시 변경 · 리버스 소환 둘 다

- **최소 수정안**: 6-M 의 `origin_zones` 와 **같은 모양**의 칸 하나

### 17-2. 뒷면 공격 표시가 불법으로 처리되지 않는다

- **사실**: `battle.ATTACK_POSITIONS` 가 `FACEDOWN_ATTACK` 을 포함한다.
  `CardInstance.position` 의 **기본값**도 그 값이다.
- **영향**: **닿지 않는다.** 필드에 카드를 놓는 production 자리 넷이

  없다 (AST 로 센다).
- **최소 수정안**: `ATTACKING_POSITIONS`(공격 선언 가능)는 이미
  `{FACEUP_ATTACK}` 하나다. `ATTACK_POSITIONS`(공격 표시인가)에서
  `FACEDOWN_ATTACK` 을 빼면 "뒷면 공격 표시" 가 어휘에서 사라지는데, 그
  값을 **기본값**으로 쓰는 자리가 있으므로 함께 바꿔야 한다. 기본값을
  고치는 것은 모든 `CardInstance` 생성 자리의 계약이다 (§3-2) → **승인 대기.**

- **사실**: `Position.ATTACK` · `DEFENSE` 는 앞뒷면을 말하지 않는데

- **영향**: **닿지 않는다.** production 이 그 두 값을 만들지 않는다.
- **최소 수정안**: 반환형을 `ConditionResult` 삼값으로 넓히고, 읽는 자리
  여덟 곳이 `UNKNOWN` 을 각자 처리한다. 공유 속성의 계약 변경이므로
  (§3-1) **승인 대기.**
