## 1. 먼저 — STRUCTURAL-94 의 원인은 요청서의 진단과 달랐다

요청서는 이렇게 보았다.

> 조건이 앞선 Operation 의 결과를 필요로 하는데, 현재 Plan 시점에는 그
> 결과가 아직 존재하지 않는다.

**이 엔진에서는 사실이 아니다.** 앞선 조작의 결과는 계획 시점에 **이미
있다** — Phase 2-AD 가 그렇게 만들었고 코드가 그대로다.

```python
steps.append(step)
values = values.with_result(step.result(index))   # 계획 루프 안이다
```

계획이 무엇을 할지 **확정**하고 적용은 확정된 것만 하므로, 뒤의 일이
읽는 수와 실제로 일어날 일이 어긋나지 않는다. 그래서 `ResultRef` 는
계획 중에 곧바로 풀린다.

없던 것은 결과가 아니라 **판**이었다. 2-AG 가 남긴 TODO 의 원문이
그것이다.

> 판을 읽는 조건이 앞선 일의 결과를 보지 못한다. **계획 시점의 판을 보기
> 때문이다.**

내 문장이 모호해서 "결과가 없다" 로 읽힌 것으로 보인다. 정확히 적으면
**계획이 읽는 판이 효과 시작 시점에 멈춰 있었다.**

네 장일 때도 뒤의 선택이 **남은 세 장**에서 고른다.

## 3. 고친 방법 — 계획이 내다보는 판 (§2 · §6 · §7 · §21)

`GameState.project()` 를 더했다. `clone()` 과 **한 가지만** 다르다.

| | 판의 모양 | 난수원 |
|---|---|---|
| `clone()` | 복제 | **복제** (사본에서 꺼내도 원본은 그대로) |
| `project()` | 복제 | **공유** (같은 것을 함께 쓴다) |

난수원만 함께 쓰는 이유가 이 설계의 핵심이다. 난수는 **계획 단계에서**
꺼내고(2-Z) 꺼낸 횟수는 재현의 좌표다. 투영이 제 난수원을 가지면 그
좌표가 진짜 판에 남지 않아 **같은 seed 로 다시 돌렸을 때 다른 판**이
된다.

> 판의 *모양*은 복제되고 흐름의 *위치*는 공유된다 — 해시에서 난수원을 뺀
> 것과 같은 가름이다.

그리고 계획은 조작을 하나 확정할 때마다 **투영에** 반영한다. 진짜 판은
계획이 전부 끝난 뒤에야 바뀌므로 §21("plan 단계에서 GameState mutation
금지")도 그대로다 — 바뀌는 것은 투영이지 판이 아니다.

### 덤으로 안전해진 것

적용 도중의 예외가 이제 **계획 단계에서** 잡힌다. 예전에는 두 번째
조작의 적용이 터지면 첫 번째는 이미 적용된 채로 남고
`EXECUTION_ERROR` 가 "판이 반쯤 바뀌어 있을 수 있습니다" 라고 말했다.
이제 투영에서 먼저 터지므로 진짜 판을 건드리기 전에 깨끗하게 거절한다.

### 2-AG 의 한계도 함께 풀렸다

"판을 읽는 조건은 계획 시점의 판을 본다" 던 제약이 사라졌다. 조건도
투영을 보므로 **앞의 일이 끝난 판**을 본다.

## 4. Deferred 와 UNKNOWN 을 가른다 (§4 · §5 · §19)

결과가 계획 중에 풀리므로 "아직 값이 없는 참조" 를 위한 Promise/Future
계층은 **만들지 않았다** (§3 이 금지한 것). 대신 **없는 이유**를 나눴다.

| | 뜻 | 무엇을 고쳐야 하나 |
|---|---|---|
| `NOT_YET` | 아직 그 일에 닿지 않았다 | 순서 |
| `NOT_APPLIED` | 그 일을 **하지 않았다** (2-AG 건너뜀) | 정의가 그 경우를 적어야 한다 |
| `NO_FIELD` | 그 일에는 **그 칸이 없다** | 정의가 틀렸다 |
| `AVAILABLE` | 있다 | — |

셋 다 "수가 없다" 로 끝나지만 **고쳐야 할 것이 다르고**, 셋 다
`UNKNOWN`("규칙을 판정할 수 없다")과 다르다. 합치면 "규칙을 더 옮기면
풀린다" 와 "정의를 고쳐야 한다" 가 같은 말이 된다.

`ExecutionValues.look_up(ref) -> ResultLookup` 이 이유까지 답하고,
기존 `result()` 는 그 위에 서서 `ExecutionLookupError.availability` 로
이유를 들고 나간다 — **기존 호출자를 깨지 않는다.**

그리고 `SelectionCount.resolve` 가 이유별로 다르게 답한다.

```
NOT_APPLIED → UNKNOWN + missing="rule for reading a skipped operation's count"
NOT_YET     → UNKNOWN + missing=그 참조
NO_FIELD    → INVALID           (규칙이 모자란 것이 아니라 정의가 틀렸다)
```

### 막는 자리를 앞당겼다

`NO_FIELD` 는 **정의를 적는 순간** 알 수 있다 — 어느 종류가 장수를
내는지는 고정이다 (`COUNTING_KINDS`). 그래서 라이프 증감이나 셔플의
장수를 읽는 정의는 **만들어지지 않는다.**

실행해 봐야 아는 거짓말이 아니라 적는 순간 아는 거짓말이므로, 실행
때까지 들고 다니지 않는다.

## 5. 고리는 만들어질 수 없다 (§17 · §18)

참조가 언제나 **앞**을 가리켜야 하므로 조작 순서가 이미 위상 정렬이다.
A→B, B→A 는 정의를 만들 때 거부된다.

그래서 **고리를 푸는 장치를 만들지 않았다** (§18). 무한 대기가 생길
자리가 없다는 것을 테스트가 확인한다 (`engine/effect/*.py` 에
`topological` · `cycle_solver` · `while True` 가 없다).

## 6. 나머지 경계 (§10 · §14 · §15 · §16 · §20 · §23 ~ §27)

| 경계 | 어떻게 지키는가 |
|---|---|
| Plan-time ≠ Execution-time | 계획은 투영을 보고, 진짜 판은 계획이 끝난 뒤에 바뀐다 |
| Unresolved ≠ UNKNOWN | `ResultAvailability` 넷으로 갈린다 |
| UNKNOWN ≠ FALSE | 조건이 수를 모르면 건너뛰지 않고 **전체 거절** (2-AG 그대로) |
| FALSE ≠ FAILED | 건너뛴 일은 `NOT_APPLIED`, 효과는 해결된다 |
| 선택 의존 | 선언이 없으면 조건도 정하지 않는다 — 임의의 수를 넣지 않는다 |
| 무작위 의존 | 조건을 보는 코드에 `randomness`·`choose`·`shuffle` 이 없다 (AST) |
| 부분 결과 의존 | 부분 적용을 조건으로 만들지 않고 `ResultRef` 로 수를 가져온다 |
| 실행값 lifetime | `execute()` 한 번. 투영도 그 안에서만 산다 (§22 "가장 작은 lifetime") |
| 복제 독립 | 복제본에서 돌려도 원본의 난수원·판·결과가 그대로 |
| 정보 경계 | 투영은 **엔진이 보는 판**이고 관측은 그대로다 |
| 저널 · 해시 | 한 줄도 바뀌지 않았다 |
