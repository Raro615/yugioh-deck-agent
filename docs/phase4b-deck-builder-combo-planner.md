## 4. 실제 구현한 기능

### 4.1 요청 구조화

```
$ python3 -m app.main deck "오르페골 + K9으로 덱을 짜 줘. 초동 안정성을 우선하고, 패트랩도 충분히"
요청 해석
테마: 오르페골 + K9
목표: 초동 안정성 우선 · 패에서 발동하는 카드 비중 우선
```

🔴 **못 해석한 것을 채우지 않는다.** 목표를 못 찾으면
`목표: 지정되지 않았습니다` 로 적고 기본 목표를 끼우지 않는다 — 사용자가
지정하지 않은 기준으로 덱이 짜이면 안 되기 때문이다.

### 4.2 덱 구성 — 후보 선정과 최종 구성을 나눴다

`candidates()` 는 **조회**(카드군 소속 전부), `build()` 는 **결정**(역할·매수·
자르기)이다. 한 함수에 두면 "왜 이 카드인가" 와 "왜 2장인가" 가 섞여 어느
쪽이 틀렸는지 가릴 수 없다.

역할 분류는 **측정 가능한 신호만** 쓴다:

| 역할 | 신호 |
|---|---|
| 엑스트라 덱 | `card.is_extra_deck` |
| 패에서 자체 특수 소환 | `can_self_special_summon_from_hand` (EFFECT_SPSUMMON_PROC) |
| 패에서 발동 (패트랩 계열) | `has_effect_from('HAND')` |
| 테마 카드 | 카드군 소속 + 카드 종류 |
| 분류 근거 없음 | 🔴 **추측해서 붙이지 않는다** |

실행 예 (오르페골, 초동 안정성 우선):

```
  메인 40장 (종류 20) · 엑스트라 6장 (종류 6)
  해석된 카드군: ORCUST
    2x  오르페골 디베르  [57835716]
         역할: 테마 카드
         근거: ORCUST 카드군의 몬스터입니다
  [구성 기록]
    - 테마 카드만으로 메인 40장에 16장 부족해 보강했습니다 — 기준은
      '패에서 발동 가능한 효과를 가진 몬스터' 하나이고 카드 ID 순서입니다.
      🔴 메타 평가가 아닙니다
    - 테마 '오르페골' → 카드군 ORCUST (소속 카드 18장 확인)
```

🔴 **보강 기준을 숨기지 않는다.** 테마만으로 40장이 안 될 때 채우지만,
"이 카드가 좋다" 는 판단의 근거가 이 저장소에 없으므로 기준은 관측 가능한
신호 하나이고, 결정론적 순서(카드 ID)를 쓴다. 같은 요청이 다른 덱을 내지
않는다.

### 4.3 덱 검증 — 🔴 **확인된 규칙만** 검사한다

룰북 구조화 데이터를 실제로 조사해 **무엇이 데이터로 확인되는지** 가렸다.

| 규칙 | 데이터 | 처리 |
|---|---|---|
| 메인 덱 40~60장 | ✅ `zones[Deck].notes` = "The Deck must be 40 to 60 cards." + `capacity=60` | **검사한다.** 근거 규칙 `RULE-DECK-002` 를 함께 출력 |
| 엑스트라 덱 15장 이하 | ✅ `zones[Extra Deck].capacity=15` | **검사한다.** `RULE-DECK-003` |
| 동일명 3장 제한 | ❌ 룰북 데이터에 없다 | 🔴 **검증 불가** |
| 금지·제한 | ❌ 저장소에 데이터 자체가 없다 | 🔴 **검증 불가** |
| 칸별 매수 ≥1 · 카드 ID 중복 · 엑스트라 카드의 위치 | — (자체 일관성 / 카드 데이터) | 검사한다 |

출력:

```
  ✔ 메인 덱 장수: 충족
      40장 (40~60 범위 안)
      근거 규칙: RULE-ZONE-001, RULE-DECK-002, RULE-MISC-002
  ? 동일명 카드 매수 상한: 검증 불가 (데이터 없음)
      룰북 데이터에 매수 상한 규칙이 없습니다. 이 초안의 최대 매수는
      2장입니다 — 사람이 확인해야 합니다
  ? 금지·제한 (리미트 레귤레이션): 검증 불가 (데이터 없음)
      이 저장소에 금지·제한 데이터가 없습니다. 금지·제한 위반 여부를
      전혀 판정하지 못했습니다

  요약: 위반 0건 · 검증 불가 2건 · 전체 7건
  🔴 검증 불가 항목은 **통과가 아닙니다.** 사람이 확인해야 합니다
```

🔴 **"위반 0건" 뒤에 "검증 불가 2건" 이 숨지 않는다.** 숫자를 따로 세고
경고를 따로 적는다. 3장 제한을 '상식' 으로 검사하면 근거 없는 판정이
근거 있는 판정과 같은 표에 올라간다.

룰북 파일이 없으면 장수 검사도 **검증 불가**가 된다 — 기본값으로 때우지
않는다 (`test_13`).

### 4.4 전개 계획 — 초기 패는 **입력이 정한다**

```
$ python3 -m app.main combo "오르페골 디베르,오르페골 스켈레촌,55144522,212652"

  초기 패 4장 · 초기 필드·묘지 0장
  (초기 패는 사용자가 지정한 것입니다 — 무작위 패 생성은 구현되어 있지 않습니다)

  1. ✔ '오르페골 디베르' 을 일반 소환합니다
      상태: 확정  ·  근거: 엔진이 이 행위를 허가함
      필요: 이번 턴 일반 소환권이 남아 있어야 합니다
      필요: 메인 몬스터 존에 빈 자리가 있어야 합니다
      기대: 앞면 공격 표시로 몬스터 존에 놓입니다
  2. ~ '오르페골 스켈레촌' 을 일반 소환합니다
      상태: 조건부  ·  근거: 엔진이 이 행위를 허가함
      필요: 🔴 이번 턴 일반 소환권을 이미 썼습니다 — 추가 소환 수단이 필요합니다
  3. ✔ '욕망의 항아리' 의 효과를 발동합니다
      상태: 확정  ·  근거: 엔진에 효과 실행 구현 있음
  4. ? 'Trap of the Poisonous Scorpion' 을 발동합니다
      상태: 미확인  ·  근거: 카드 종류상 효과만 확인
      비고: Lua 스크립트가 없어 효과를 구조적으로 알지 못합니다

  요약: 4걸음 (확정 2 · 조건부 1 · 미확인 1)
  🔴 중단: 근거가 없는 카드 1장이 있어 그 뒤의 전개는 계획하지 않았습니다
```

#### 🔴 초기 패 장수를 강제하지 않는 **근거**

룰북 데이터 `zones[Hand]` 를 직접 읽었다.

```
capacity = 6
notes = "capacity 6 은 엔드 페이즈 종료 시점의 상한이다 —
         그 외 시점의 상한은 룰북에 없다. …"
```

즉 **패 6장은 엔드 페이즈 상한**이고 그 외 시점의 상한은 룰북에 없다.
그래서 0장·1장·7장·9장 전부 그대로 받는다 (`test_14` 가 다섯 장수를
돌린다). 확인되지 않은 제약을 검사하거나 거부 이유로 쓰지 않는다 —
`test_15` 가 그 근거 문장을 데이터에서 확인한다.

#### 근거의 층과 상태

| 근거 (`StepBasis`) | 뜻 | 상태 |
|---|---|---|
| `ENGINE_ACTION` | 엔진이 **이 행위를 허가**한다 (일반 소환) | 확정 |
| `ENGINE_EXECUTABLE` | 그 **카드 효과의 실행 구현**이 엔진에 있다 (13장) | 확정 |
| `LUA_PARSED` | Lua 효과 블록이 파싱돼 있다. 실행 구현은 없다 | 조건부 |
| `PRINTED_TYPE_ONLY` | 카드 종류상 효과가 있다는 것만 안다 | 미확인 |
| `NONE` | 근거 없음 | 미확인 |

🔴 **작업 중 과대 진술을 한 번 저질렀고 고쳤다.** 처음에는 일반 소환에도
`ENGINE_EXECUTABLE`("엔진 실행 구현 있음")을 붙이고 있었다. 그러면 효과
구현이 등록되지 않은 몬스터를 두고 "엔진에 구현이 있다" 고 적게 된다.
근거 값을 `ENGINE_ACTION` 과 `ENGINE_EXECUTABLE` 둘로 갈랐고 `test_30` 이
그 분리를 못 박는다.

#### 미지원 절차는 **계획에 넣지 않고 따로 적는다**

```
  [엔진이 지원하지 않아 계획에 넣지 않은 절차]
    - 특수 소환 (조건 판정 계층이 없어 ActionValidator 가 언제나 UNKNOWN)
    - 융합 소환 (재료 선택 절차 없음)
    - 싱크로 소환 (재료 선택 절차 없음)
    - 엑시즈 소환 (재료 선택 절차 없음)
    - 링크 소환 (재료 선택 절차 없음)
```

🔴 **효과가 무엇을 하는지 서술하지 않는다.** 서술하려면 효과를 해석해야
하고 이 저장소는 그 해석을 보증하지 않는다. "발동한다" 와 "근거가 어디
까지인가" 만 적고, 효과 내용은 카드 텍스트를 보라고 한다.

### 4.5 초기 패 입력과 패 생성의 분리

`deck/hand.py` 가 경계다.

```python
@runtime_checkable
class HandProvider(Protocol):
    def hand(self) -> list[int]: ...

@dataclass(frozen=True, slots=True)
class FixedHand:          # 🔴 이번 단계의 유일한 구현
    card_ids: tuple[int, ...] = ()
    def hand(self) -> list[int]: return list(self.card_ids)
```

* `ComboPlanner` 는 패를 **받기만** 한다. 만들지 않는다.
* 🔴 **플래너에 난수원이 없다.** `test_26` 이 AST 로 확인한다 — `random`
  import 없음, `shuffle`/`sample`/`choice`/`randint` 호출 없음.
* 경계는 **하나**다. 구현체가 하나뿐인 인터페이스를 여러 겹으로 쌓지
  않았다.

### 5.1 후속 단계에서 패 생성을 끼울 자리

`deck/hand.py` 에 `HandProvider` 를 만족하는 구현을 **하나 더** 추가하면
된다. `ComboPlanner` 도 `deck/model.py` 도 고치지 않는다.

그때 지켜야 할 것 (그 모듈 docstring 에 적어 두었다): **난수원을 스스로
들고 다녀야 한다.** `engine.randomness.RandomPurpose` 는 `AI_*` 를 일부러
넣지 않았고("탐색·정책의 무작위는 규칙의 무작위와 다른 계층이고, 한
열거형에 섞으면 같은 난수원을 쓰게 된다"), `agent.policy.RandomPolicy` 가
그 결정에 따라 제 `random.Random` 을 들고 다닌다. 패 생성도 **같은 쪽**
이다 — 덱 셔플의 난수원을 빌려 쓰면 패를 한 번 더 뽑았다는 이유로 듀얼의
셔플 결과가 달라진다.

**통과했다** — 빈 덱에는 제외한 카드도 없으니까. 정확히 일치하는 것만
걷어내도록 고치고, `test_07` 에 "테마가 살아 있어야 한다 · 덱이 비면 안

## 10. 다음 단계에서 수행할 단 하나의 작업

> **초동 확률 계산 기능 추가** — 덱 초안과 "초동으로 보는 카드 집합" 을
> 받아, 지정한 패 장수에서 그 집합이 1장 이상 잡힐 확률을 조합으로
> 계산한다.

왜 이것 하나인가:

* **엔진에 의존하지 않는다.** 초과기하분포 계산이고 카드 효과 해석이
  필요 없다. S3(효과 컴파일러)가 막혀 있어도 진행된다.
* **지금 만든 것 위에 바로 올라간다.** `DeckDraft` 가 이미 카드별 매수를
  들고 있고, 패 장수를 입력으로 받는 규율도 이미 세웠다.
* **"초동 안정성 우선" 목표를 처음으로 수치로 뒷받침한다.** 지금은 그
  목표가 매수와 자르는 순서만 바꾸고, 결과가 실제로 안정적인지는 아무도
  모른다.
* 무작위 패 생성과 **다른 작업**이다 — 확률은 계산이고, 무작위 패는
  표본 추출이다. 확률을 먼저 하면 나중에 표본 결과를 검산할 기준이 생긴다.
