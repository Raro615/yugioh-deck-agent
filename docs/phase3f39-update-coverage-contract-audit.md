## 2. N30 — `--changed-only` 의 실제 기본값과 실행 경로

### 2.1 측정 (코드와 실행으로)

`argparse` 선언을 소스에서 그대로 꺼내 확인했다.

```
[1] --changed-only 생략: False
[1] --changed-only 명시: True
[2] 실제 선언 action/help: ('store_true', '변경된 카드만 다시 분석한다 (기본 동작)')
[3] 소비 지점: if args.changed_only and affected:
[4] 모듈 docstring 흐름 줄: ['수집 -> 변경 감지 -> 병합 -> 분석 -> 인덱스 -> 검증']
[4] docstring 에 --changed-only 가 있는가: False
```

§2 의 일곱 질문에 대한 답:

| # | 질문 | 실측 답 |
|---|---|---|
| ① | 실제 기본값 | **`False`** (`action="store_true"`) |
| ② | 생략 / 명시 시 동작 | 생략 → **분석 단계가 통째로 빠진다.** 명시 → 변경된 카드만 분석하고 결합 요약을 낸다 |
| ③ | `store_true` 가 의도와 맞는가 | **맞지 않는다.** 끄는 쪽("전부 다시 분석")이 코드에 **존재하지 않는다.** `False` 에는 가리킬 동작이 없고, 실제로는 "분석 안 함" 이 된다 |
| ④ | help 의 기본 동작 설명 | **거짓이었다.** help 는 "(기본 동작)" 이라 적고 기본에서는 분석을 건너뛰었다. 모듈 docstring 의 흐름(`… -> 분석 -> …`)과도 어긋났고, **README** 와도 어긋났다 (§2.2) |
| ⑤ | 영향 범위 | **분석 실행과 요약 출력에만** 영향. 갱신 대상 선정(`plan`/`commit`)·저장(`CardRepository.build()`)·`validate()`·`summarise()` 는 flag 와 무관하다 |
| ⑥ | 기존 호출자·자동화 의존 | **없다.** `changed_only` 를 참조하는 곳은 `scripts/update_cards.py` 안의 선언 1곳·소비 1곳뿐이고, 테스트·CI·다른 스크립트·README 어디에도 없다 (전수 grep) |
| ⑦ | 수정 시 기존 사용자 동작 변화 | `--update` 가 **분석을 더 돌린다**. 저장되는 것은 **하나도 바뀌지 않는다** — `EffectAnalyzer` 는 파일을 쓰지 않고 `Card` 를 변형하지 않는다(AST·실행 양쪽으로 확인). 비용은 출력과 실행시간뿐이고, 최악(전수 14,127장)이 **실측 약 34~54초**다 |

### 2.2 의도는 저장소 안에 적혀 있었다

기본값을 바꾸는 것이 "사용자 계약 변경" 인지 판단하기 위해, 의도를 코드
밖에서 추측하지 않고 **저장소가 스스로 적어 둔 것**만 모았다.

| 출처 | 적혀 있는 것 |
|---|---|
| flag 의 help | `변경된 카드만 다시 분석한다 (기본 동작)` |
| `scripts/update_cards.py` 모듈 docstring | `수집 -> 변경 감지 -> 병합 -> 분석 -> 인덱스 -> 검증` |
| `README.md` (수정 금지 대상) | `python -m scripts.update_cards --update   # 변경을 반영한다` 바로 아래 `흐름: 수집 → 변경 감지 → 병합 → 분석 → 인덱스 → 검증`. **`--changed-only` 는 README 에 아예 없다** |

세 군데가 모두 "`--update` 는 분석을 포함한 파이프라인이다" 라고 말한다.
`--changed-only` 는 사용자 문서에 존재하지 않는 flag 이므로, 사용자가
문서를 따라 `--update` 를 쓰면 **문서에 적힌 단계 하나가 조용히 빠졌다.**
즉 세 서술과 실행 중에서 **틀린 쪽은 실행**이고, 이것은 내 추론이 아니라
저장소에 기록된 계약이다.

### 2.3 재현 (실제 `main()`)

상태 파일을 건드리지 않도록 `build_manager` 만 바꿔 끼우고 **실제 `main()`** 을
양쪽으로 돌렸다. 수정 전:

```
argv=['--update']
  '다시 분석했습니다' 포함 : False      ← 분석이 돌지 않았다
  '효과 블록 결합 상태' 포함: False      ← 3-F-38 이 만든 요약이 도달하지 않는다
argv=['--update', '--changed-only']
  '다시 분석했습니다' 포함 : True
  '효과 블록 결합 상태' 포함: True
```

즉 Phase 3-F-38 이 갱신 경로에 붙여 둔 결합 요약은, **문서가 기본이라고 적은
호출 방식에서는 한 번도 나오지 않았다.**

### 2.4 판정과 수정: **`CONFIRMED_BUG`**

세 개의 서술이 서로 모순이고(help "기본 동작" / 모듈 docstring "분석" 포함 /
실제 "분석 안 함"), 그중 **실행이 틀린 쪽**이다. 그래서 실행을 고쳤다.

* 고친 것: `if args.changed_only and affected:` → `if affected:`
  — 변경된 카드 분석이 **항상** 돈다.
* 고치지 **않은** 것: flag 의 `action`/기본값. `store_true` 를 그대로 뒀다.
  기본값을 `True` 로 바꾸면 끌 수 없는 flag 가 되고, 끄는 쪽의 동작이
  코드에 없으므로 그 선택은 의미를 만들어내는 것이 된다.
* `--changed-only` 는 **같은 것을 명시적으로 적는 수단**으로 남는다. 기존
  호출자의 출력이 글자 단위로 동일하다 (`test_03`).
* 문구만 고치고 실행을 두는 선택(= `CONFIRMED_CONTRACT_GAP` 처리)은 하지
  않았다. 그러면 모듈 docstring 이 적은 파이프라인이 계속 거짓이 된다.

## 3. N31 — Coverage 의 분자·분모

### 3.1 분모가 실제로 무엇인가

`CardAnalysis.coverage()` 는 17칸 dict 를 돌려준다. 비율은 셋이고 분모는
전부 **`self.effects`(= 증명된 **등록** 효과)의 부분집합**이다.

| 비율 | 분자 | 분모 | 코퍼스 전수 |
|---|---|---|---|
| `condition_ratio` | `condition_structured` | `has_condition` (등록 효과 중 condition 함수를 가진 것) | 5,130 / 11,626 |
| `cost_ratio` | `cost_structured` | `with_costs` (등록 효과 중 비용이 있는 것) | 4,736 / 4,982 |
| `action_ratio` | `with_actions` | `total = len(effects)` | 14,499 / 26,352 |

AST 로 확인했다: 이 함수에서 **순회하는 목록은 `self.effects` 하나뿐**이고,
`resolution_effects` 와 `unbound_effects` 는 `len()` 으로만 등장한다
(`test_13`, `test_38`).

§3 의 일곱 질문:

| # | 질문 | 실측 답 |
|---|---|---|
| ① | 현재 분모 | 위 표. 전부 **등록 효과** 기준 |
| ② | `effects` 만 쓰면 미인식 블록이 빠지는가 | **빠진다.** 미증명 블록은 `unbound_effects` 로 가므로 어떤 분모에도 들어가지 않는다 |
| ③ | 실제보다 높게 보이는 사례 재현 | **재현했다** (§3.2) |
| ④ | 빈 핸들러 블록과 미인식 블록 구분 | **구분된다.** 조건·비용·선택·처리가 모두 없는 블록이 **13,440개**(등록 6,218 / 해결 7,222) 있는데 **전부 `MATCHED`** 다. "비었다" 가 "증명되지 않았다" 를 뜻한 적이 없다 |
| ⑤ | 네 상태가 coverage 에 어떤 영향을 **미쳐야** 하는가 | **분모에 섞지 않고 따로 밝혀야 한다.** §3.4 참고 |
| ⑥ | 사용자는 coverage 가 무엇을 재는 값이라고 이해하는가 | CLI 문구가 `구조화 정도 : 효과 N개 \| 조건 a/b · 비용 c/d …` 였다. **N 이 "등록 효과만" 이라는 사실이 어디에도 없었다** — 해결 효과 8,283개(전체 블록의 **23.9%**)가 그 N 에 없다 |
| ⑦ | 분모를 바꾸면 | 정상 코퍼스의 수치가 **움직인다**. `action_ratio` 분모를 전체 블록으로 바꾸면 26,352 → 34,635 이 되어 비율이 통째로 내려간다. 비율을 읽는 production 호출자는 **하나도 없지만**(전수 확인), **README 가 이 분모로 계산된 수치를 공표하고 있다** — §3.1.1 |

#### 3.1.1 README 가 이미 이 분모로 계산된 수치를 공표한다

`README.md` 에 이렇게 적혀 있다 (수정 금지 대상).

```
- 액션이 없는 45% 중 실제 미구조화는 15.1% (나머지는 처리 함수가 없는 지속 효과)
```

실측으로 맞춰 보면 `1 - with_actions / effects = 1 - 14,499 / 26,352 =`
**`44.98%`** → 공표된 **45%** 와 같다. 즉 "**등록 효과 기준**" 은 내가
고른 해석이 아니라 **이미 공표된 계약**이다. 분모를 바꾸면 README 의
공표 수치가 거짓이 되고, README 는 §7 이 수정을 금지한 파일이다.

### 3.2 재현 — 분석이 나빠지는데 숫자는 좋아진다

블록 2개 카드에서, **지문은 맞고 블록 식별자 하나만 어긋난** 캐시를 만들면
(옛 parser 의 offset 규약이 남은 캐시가 실제로 이 모양이다) 부분 미증명이
된다. 이것이 부분 미증명을 만드는 유일한 경로다.

```
--- 정상 (전부 MATCHED)
    effects 2 · unbound 0 · action_ratio=0.500
--- 부분 미증명 (offset 1개만 어긋남)
    effects 1 · unbound 1 · action_ratio=1.000   ← 올라갔다
```

**0.500 → 1.000.** 증명된 블록이 절반으로 줄었는데 "처리 구조화율" 은
100% 가 된다. 세 실패 상태(`MISMATCHED`/`UNPROVABLE`/`SOURCE_MISSING`)에서
블록 **전부**가 미증명이면 분모가 0 이 되고 비율은 `0.0` 이다 — 0/0 을
1.0 으로 치지 않는다 (`test_17`).

### 3.3 그 조건은 이미 dict 안에 드러나 있다

`coverage()["unbound_effects"]` 는 Phase 3-F-37 이 넣어 둔 칸이고, 위
재현에서 `1` 이다. 세 목록의 합이 **파싱한 블록 수와 정확히 같다**
(`test_18`) — 그래서 호출자가 "분모에서 빠진 것" 을 직접 되살릴 수 있다.
빠진 정보가 아니라 **표시되지 않은 정보**였다.

### 3.4 판정과 수정: **`CONFIRMED_CONTRACT_GAP`**

계산은 그대로 두고 **범위 표기**만 고쳤다. 근거:

1. **미증명 블록을 분모에 넣으면 두 종류의 실패가 합쳐진다.** `coverage` 는
   "분석이 얼마나 구조화했는가" 를 재고, 결합 상태는 "블록과 핸들러의 대응을
   증명했는가" 를 잰다. 미증명 블록을 "구조화 못 한 효과" 로 세면, 결합
   실패가 구조화 실패로 보고된다. Phase 3-F-38 §2 가 금지한 바로 그 합치기다.
2. **분리 표현이 이미 존재한다.** `effects` / `resolution_effects` /
   `unbound_effects` 세 칸이 같은 dict 에 있고 합이 블록 수와 같다. 새 칸·새
   함수·새 프레임워크가 필요하지 않다 — 그래서 **공개 API 를 늘리지 않았다**
   (dict 칸 수 17개 그대로, `test_37`).
3. **정상 코퍼스의 수치를 흔들지 않는다.** 분모를 바꾸면 26,352 → 34,635 로
   움직인다. 근거 없이 흔드는 것은 §8 이 금지한다.

실제로 고친 것:

* `coverage()` docstring 이 **세 분모를 하나씩 명시**하고, 해결 효과와 미증명
  블록이 왜 빠져 있는지, 왜 섞지 않는지를 적는다. (코드 변경 0줄)
* 분석 CLI 의 문구가 `구조화 정도 : 등록 효과 N개 기준 \| …` 으로, **무엇을
  분모로 썼는지**를 항상 말한다.
* 미증명 블록이 있을 때만 제외된 수를 한 줄 더 적는다. 정상 카드의 출력에는
  붙지 않는다 (`test_24`).

## 4. 두 문제의 관계

§4 의 네 항목을 실제 출력으로 확인했다.

| 질문 | 실측 답 |
|---|---|
| 갱신하지 않은 카드가 coverage 집계에서 누락되는가 | **그런 집계가 존재하지 않는다.** `coverage()` 를 읽는 production 호출자는 `app/main.py` 한 곳이고 **카드 한 장**짜리다. 코퍼스 전체 coverage 집계는 production 에 없다 (`test_21`) |
| 갱신 대상만 분석한 결과가 전체 corpus 인 것처럼 표시되는가 | **표시된다.** `효과 블록 결합 상태 … 3장` 바로 아래에 `카드 데이터 현황 … 14,127장` 이 붙고, 두 표 어느 쪽도 자기 범위를 적지 않았다 |
| 범위가 다른 두 집계가 한 요약에 나오는가 | **나온다.** 위와 같은 자리 |
| 기본값을 바꾸지 않고도 범위를 명확히 할 수 있는가 | **할 수 있다.** 두 표의 머리글에 범위를 적었다 — `효과 블록 결합 상태 (다시 분석한 3장 기준)` / `카드 데이터 현황 (저장소 전체)` |

**인과관계는 없다.** 두 결함은 코드 경로를 공유하지 않는다 — N30 은
`main()` 의 실행 조건, N31 은 `CardAnalysis.coverage()` 의 분모 정의다.
같은 원인에서 갈라진 것이 아니다.

**같은 **종류**의 결함이다.** 둘 다 "집계·실행의 범위를 밝히지 않는다" 이고,
그래서 숫자가 조용히 다른 것을 가리킨다. 증명되지 않은 인과를 주장하지
않되, 한 가지 실제 상호작용은 기록한다: **N30 때문에 N31 의 조건이 드러날
자리가 막혀 있었다.** `--update` 만 주면 분석이 돌지 않으므로, 코퍼스에
미증명 블록이 생겨도 갱신 경로에서는 아무 신호도 나오지 않았다
(`validate()` 와 `summarise()` 는 결합 상태를 읽지 않는다).
