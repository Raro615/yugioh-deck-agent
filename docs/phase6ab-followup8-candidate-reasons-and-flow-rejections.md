## 3. 기존 결함과 재현 절차

### 3.1 결함 ① — 자동 PASS 가 중간 기회의 사유를 버린다

`agent/simulation.py` 의 `_settle_forced_passes()` 는 PASS 만 남은 응답
기회를 자동으로 지나간다. 그런데 `simulate()` 는 **그 반복이 끝난 뒤**의
`legal.unsupported()` 만 모았다.

재현 (실행 경로를 전부 지난다 — 결과 객체를 주입하지 않는다):

```
① 기존 staged 도구로 P0 에게 세트 가능한 몬스터를 둔다
② P1 의 마법·함정 존에 뒷면 욕망의 선물(5915629)을 둔다
③ 테스트 전용 정의에서 그 효과의 activation_waits_for_event=True 로 바꾼다
   🔴 카드 수정 제안이 아니다 — 기존 미지원 사건 관문을 밟기 위한 합성 조건
④ duel_components(definitions=…) 로 그 정의를 넘긴다
⑤ P0 의 SET_MONSTER 를 Simulator().simulate(...) 로 실행한다
```

실측한 흐름과 결과:

```
[1] P0 빠른 효과 기회 → activate_card [activation-timing (Phase 2-C/2-F)]
[2] P1 빠른 효과 기회 → 🔴 activate_effect [trap-activation-event]
최종 (판이 다시 열림)  → activate_card [activation-timing (Phase 2-C/2-F)]

전: SimulationResult.unsupported = (activate_card … ,)      ← [2] 가 없다
후: SimulationResult.unsupported = (…activate_card…,
                                     🔴 …trap-activation-event…,
                                     …activate_card…)
```

🔴 **그 재현에서 `fully_supported` 는 전후 모두 거짓이다** — 다른 사유
하나가 이미 있었다. 그래서 *"`fully_supported=True` 로 잘못 성공했다"* 가
아니고, 확인된 결함은 **"진행 도중의 구체적인 중요 사유가 결과에서
유실된다"** 다. `test_a02` 가 그 구분을 함께 센다
(`assert result.fully_supported is False`).

`deck/opening.py` 의 `_settle_chain()` 도 같은 모양이었다 — 조용히 패스만
하고, 부르는 쪽은 반복이 끝난 뒤의 자리만 읽었다.

### 3.2 결함 ② — `apply` 경계가 "무엇이 빠졌는가" 를 잃는다

`DuelStep` 에는 `missing` 칸이 없다. 그래서 판정 계층이 `missing_rule` 로
들고 있던 사실이 `apply` 결과에서 사라졌다. 실측:

```
ActionValidator.validate(special_summon)
→ UNKNOWN / RULE_NOT_IMPLEMENTED
  missing_rule = "special-summon-condition (카드마다 다르다)"

DuelStep (전) "아직 구현하지 않은 규칙이 걸려 있습니다."
DuelStep (후) "아직 구현하지 않은 규칙이 걸려 있습니다.
               [special-summon-condition (카드마다 다르다)]"
```

고친 자리는 `Duel._refusal_sentence` 하나다. **확정 거부에는 아무것도
붙지 않으므로** ("규칙이 막았다" 는 `missing is None`) 두 사실의 구분은
그대로다. 보류 목록은 `WithheldAction.line_ko` 로 같은 규약을 이미 쓰고
있었고, 그것을 `apply` 결과에도 쓴 것이다.

### 3.3 결함 ③ — 출력이 서로 다른 말을 한다

같은 응답 안에서:

- 위쪽 `[실제 엔진 실행]` 절이 `recipe:` 로 패 구성을 **검사했다**
- 아래쪽 정적 계획이 *"덱 초안을 주지 않아 그 검사를 하지 않았다"* 고 적고
- 다시 *"위쪽이 이미 검사했다"* 는 해명이 붙고
- 실행하지 않은 정적 계획의 걸음이 **"확정"** · **"엔진이 이 행위를 허가함"**

### 3.4 결함 ④ — 종료 판정이 **마지막 자리**만 본다 (남은 세 항목 ①)

`execute_opening()` 은 `note_unsupported()` 로 중간 사유를
`run.unsupported` 에 **모으고 있었다.** 그런데 종료 판정은 **그 자리**의
`missing_here` 만 보았다. 그래서 중간에 중요한 미지원을 지나왔어도 마지막
자리가 깨끗하면 `flow_only` 가 되고, 멈춘 설명이 그 한계를 한 글자도
말하지 않았다.

재현 (실행 경로를 전부 지난다):

```
① _board_with_facedown_gift(repository, definitions=_waiting_gift_registry())
② P0 의 패를 일반 소환 가능한 몬스터 1장만 남긴다 (나머지는 덱으로)
③ OpeningSetup(duel=duel, journal=duel.journal) 로 execute_opening 을 부른다
```

🔴 **합성 조건이다** — ②의 등록부는 테스트 전용 정의에서
`activation_waits_for_event` 만 참으로 바꾼 것이고, **실제 욕망의 선물이
사건을 기다리는 카드라는 뜻이 아니다.**

실측:

```
                     전                                후
걸음                  normal_summon 1걸음                 그대로
중간 P1 기회           trap-activation-event 미지원         그대로
run.unsupported       3건 (그 사유 포함)                   그대로
마지막 P0 패           비었다 → 그 자리의 미지원 없음        그대로
stopped_kind          "flow_only"                        "flow_only" (종료 원인은 그대로)
fully_supported       🔴 **그 질문이 없었다**              **False**
멈춘 설명              마지막 후보만 언급                   🔴 "… 앞선 자리의 사실입니다 ·
                                                          전개 전체를 지원 범위 안에서
                                                          검증한 것은 아닙니다"
ExecutedStep          unsupported=()                     unsupported=() · 🔴
                                                          unsupported_during=(그 사유,…)
```

## 5. 중간 사유 수집 · 중복 처리 · 관련성 판단 · 비공개 정보 보호

### 5.1 수집

```python
# agent/simulation.py
def _settle_forced_passes(self, fork) -> "tuple[int, tuple[tuple[int, WithheldAction], ...]]":
    #  각 기회에서 legal.unsupported() 를 (자리, 보류) 로 모은 뒤 PASS 한다
```

`simulate()` 가 그 중간 목록과 최종 자리의 목록을 **순서대로** 이어 붙인다.
`deck/opening.py` 는 같은 일을 `note` 콜백으로 한다 — `_settle_chain(duel,
note=None)` 이 반복마다 `note(legal, seat)` 를 부르고, `execute_opening` 이
`note_unsupported` 를 넘긴다.

### 5.2 중복

🔴 **완성된 한 줄을 열쇠로 묶는다.** 그 줄에 종류 · 규칙 이름 · (자기
자리면) 효과 이름이 들어 있으므로, **다른 효과의 사유가 합쳐지지 않는다.**

`WithheldAction.scope` 는 그 열쇠에서 **빠진다**. 그것이 이 작업에서 내가
만든 버그였다: 훑은 패의 장수를 `reason` 안에 넣었더니 문장이 걸음마다
달라져 `/combo` 의 미지원이 1줄 → 5줄(내용이 같은 다섯 줄)이 되었다.
그래서 `scope` 를 별도 칸으로 떼고 `line_ko(with_scope=False)` 를 누적
열쇠로 쓴다.

### 5.3 관련성

`Duel._refusal` 의 우선순위 — **행위 단위가 종류 단위보다 먼저다.**

| | 누가 | 무엇에 대해 |
|---|---|---|
| 1 | `_refusal_verdict` (발동 관문) | 그 **행위 하나** (발동에만 있다) |
| 2 | `_rule_verdict` (`ActionValidator`) | 그 행위 하나의 규칙 쪽 판정. 흐름 둘(`PASS`·`END_PHASE`)에는 묻지 않는다 |
| 3 | `_withheld_for` (보류 목록의 같은 종류) | 흐름 계층이 **종류 단위**로 낸 판정 |
| 4 | 예전 문장 | 남은 자리를 숨기지 않는다 |

같은 행위에 두 이유가 겹칠 때 (예: 빠른 효과 기회에 **가려진 카드**를
가리킨 소환) 더 좁은 쪽이 실제 이유다. 종류 단위의 단계 설명을 앞세우면
*"부수적으로 발견한 문제를 실제 제외 이유처럼"* 적는 일이 된다.

`_withheld_for` 가 **종류만 같은 다른 효과의 거절**을 가져오지 않는지는
`test_c02` 가 따로 센다 — 같은 종류에 줄이 여럿일 때 확정 거부를 먼저
고르고, 그 종류의 줄이 없으면 `None` 이다 (지어내지 않는다).

의 불변식(`test_26`)은 `WithheldAction` 에 `source`·`action`·`instance_id`
를 **금지**한다 — 후보별 식별자를 담으면 `HIDDEN_CARD` 처럼 **가려진 것을
가리키는 판정**에서 정체가 함께 새기 때문이다.

해결:

- 효과 참조는 **`reason` 문자열**에만 둔다 (이 저장소의 기존 규약이다).
- 데이터클래스에 더한 것은 `code` (**규칙의 이름**)와 `scope` (**개수**)
  뿐이다 — 둘 다 어느 카드인지 말하지 않는다. 소비자는 효과를 구별할
  필요 없이 `code` 로 "규칙 거절인가 모름인가" 를 읽는다.
- **자리를 넘어갈 때는 문장을 가린다.** `agent/simulation.py` 의
  `_encountered_line()` 과 `deck/opening.py` 의
  `unsupported_reasons_elsewhere()` 가 같은 일을 한다:

```
자기 자리   activate_effect [trap-activation-event]: 5915629:e[0] 를 지금 …
다른 자리   activate_effect [trap-activation-event]: P1 의 기회에서 만났고
                                어느 카드인지는 이 자리의 관측 밖입니다.
```

`test_a03` 이 그 경계를 양방향으로 센다: 카드 번호도 `EffectRef` 도 없고,
**그런데 사실은 남아 있고** ("누구의 기회였고 무엇이 없어서인지"), 지웠다는
것도 적는다 — "사유가 없다" 로 읽히지 않게. 그리고 같은 판에서 `viewer=P1`
로 보면 **자기 자리의 사유는 문장째로** 온다 (경계가 과하게 지우지 않는다).

## 6. 후보 제외 / 직접 `apply` / Simulator / `/combo` 사이의 계약

| 사실 | 후보 목록 | 직접 `apply` | Simulator | `/combo` |
|---|---|---|---|---|
| 지원 범위에서 진행 완료 | `allowed` 에 흐름만 남고 `unsupported()` 가 비었다 | `accepted=True` · `OK` | `SUPPORTED` + `fully_supported=True` | `stopped_kind="flow_only"` |
| 규칙상 불가능한 후보 | `withheld` · `code` 가 INVALID · `missing is None` | `accepted=False` · 그 코드 | `unsupported` 에 **들어가지 않는다** | 미지원 목록에 **없다** |
| 선택 정책이 고르지 않음 | `allowed` 에 있다 | — | 정책의 선택 기록 | `stopped_kind="not_chosen"` · 고른 방식을 `first_meaningful` 이라고 적는다 |
| 중요 미지원 때문에 검증 불가 | `withheld` · UNKNOWN · `missing` 에 규칙 이름 | `accepted=False` · 같은 코드 + `[빠진 규칙]` | `fully_supported=False` · `unsupported` 에 줄 | `stopped_kind="unsupported"` + 미지원 목록 |
| 실행 또는 해결 실패 | — | `accepted` 는 참일 수 있고 `code` 가 불발 사유 | 결과·기록이 말한다 | 걸음마다 `결과` 칸 |

### 6.1 🔴 **종료 원인**과 **전체 지원 상태**는 다른 질문이다 (남은 세 항목 ①)

`stopped_kind` 하나로 둘을 말할 수 없다. 그래서 **최소 계약으로 갈랐다** —
`OpeningRun.fully_supported` (이름은 `SimulationResult.fully_supported` 와
같다: 같은 질문이므로 같은 낱말을 쓴다).

| 상황 | `stopped_kind` | `fully_supported` |
|---|---|---|
| 미지원 없이 흐름만 남았다 | `flow_only` | 참 |
| **중간에** 미지원을 지나왔고 마지막 자리는 깨끗하다 | `flow_only` | **거짓** |
| 멈춘 자리에 미지원이 있다 | `unsupported` | 거짓 |
| 행동이 거절되었다 | `rejected` | 만난 것에 따른다 |
| 상한에 닿았다 | `limit` | 만난 것에 따른다 |

🔴 **누적 미지원이 실제 종료 원인을 덮지 않는다.** 거절 · 상한 · 정책
미선택의 `stopped_kind` 와 설명은 그대로다 (`test_g04`). 그리고
🔴 **시점을 섞지 않는다**: `flow_only` 로 멈췄는데 누적 미지원이 있으면 멈춘
설명이 *"지금 이 자리가 아니라 **앞선 자리**의 사실입니다"* 라고 적는다 —
과거 사유를 "현재 후보가 되지 못한 것" 으로 옮겨 적지 않는다.

걸음의 두 목록도 시점으로 갈렸다:

| | 무엇 | 어디서 읽는가 |
|---|---|---|
| `ExecutedStep.unsupported` | 이 걸음이 **끝난 뒤 그 자리** | 걸음 줄에 문장째로 |
| `ExecutedStep.unsupported_during` | 이 걸음의 **자동 처리 도중** 지나간 자리 | 걸음 줄에 **수와 자리만**, 문장은 누적 `미지원 사유` 목록 |

🔴 문장을 걸음마다 다시 적지 않는 이유는 실측이다 — 같은 문장을 두 번
적으면 긴 전개에서 Discord 메시지 상한에 걸려 **정적 계획 절이 잘렸다.**
그래서 요구 ①의 *"어디서 확인할 수 있는지 연결해라"* 를 **연결**로 지킨다.

핵심은 **같은 판정 하나를 네 자리가 읽는다**는 것이다. 보완8 이 새 규칙을
구현하지 않은 이유가 여기 있다 — 흐름 계층의 정확한 말은 이미
`legal.withheld` 에 있었고, `apply` 가 그것을 읽지 않았을 뿐이다.

`INVALID` 가 미지원으로 집계되지 않는다는 것은 `LegalActions.unsupported()`
가 `missing` 이 붙은 보류만 돌려주는 것으로 **구조적으로** 지켜진다. 그리고
`WithheldAction.__post_init__` 이 INVALID 코드에 `missing` 을 붙이면 예외를
던지므로, 그 규율을 어기는 자리는 만들 수 없다.

## 8. 혼합 대상 조합과 강제 유발 미지원 처리

> 🔴 **정정 (보완8 남은 세 항목 ②).** 이 절은 처음에 아래 네 줄만으로
> *"혼합 조합 요구를 충족했다"* 고 적었다. **근거가 부족했다.** `test_b02`
> 는 *모두 INVALID*, `test_b03` 은 *모두 VALID*, `test_b04` 는 *서로 다른
> 효과*이고 — 셋 중 어느 것도 **같은 효과 안에서 합법 · 거절 · 미확인
> 조합이 섞인 경우**가 아니다. 모두 VALID / 모두 INVALID 사례를 혼합 검증
> 이라고 부른 것이 그 과장이다. 아래 §8.1 이 그 혼합을 실제로 만든다.

### 8.0 기존 네 줄 (유지한다 — 각자 다른 사실을 잰다)

| 요구 | 시험 | 실제 카드 | 결과 |
|---|---|---|---|
| 조합이 **전부** VALID 면 전부 후보로 남는다 | `test_b03` | `94192409` | 네 조합 전부 허가 |
| 조합이 **전부** 거절이면 한 줄로 묶인다 | `test_b02` | `73148972` | 같은 `code`·`missing` 이므로 한 줄 |
| 합법 조합이 있다고 중요 미지원을 숨기지 않는다 | `test_b01` | `94192409` | 세트 전 발동 요청의 UNKNOWN 이 보류로 남는다 |
| 서로 다른 효과의 사유를 합치지 않는다 | `test_b04` | `5915629` + `94192409` | 같은 `code`·`missing` 이어도 **효과가 다르면 두 줄** |
| 강제 유발 미지원이 조용히 사라지지 않는다 | `test_a05` · `test_c01` | — | `_enforce_mandatory` 의 보류가 다른 합법 행동 때문에 지워지지 않는다 |

### 8.1 같은 효과의 **혼합** 조합 — 실제로 만들어 검증한다

🔴 **실제 등재 카드 하나로 세 가지가 함께 나온다.** 싸이크론
(`5318639:e[0]`) 의 대상 규칙은 *"필드(양쪽)의 마법 · 함정 1장"* 이므로 한
판에서:

```
내 앞면 마법 1장        → 조건 참      → VALID 조합이 된다
내 앞면 몬스터 1장      → 조건 거짓    → INVALID: 후보가 되지 않는다
상대 뒷면 마법·함정 1장  → 정체 모름    → UNKNOWN: 셀 수 없다
```

| 사례 | 시험 | 실제/합성 | 결과 |
|---|---|---|---|
| **A** VALID + INVALID | `test_f01` | 🔴 실제 (`5318639`) | 조합 1개만 후보 · 그 조합이 `apply` 에서 **수락**된다 · 거짓인 조합은 **미지원으로 집계되지 않는다** |
| **B** VALID + UNKNOWN | `test_f02` | 🔴 실제 (`5318639`) | 합법 조합은 **그대로 후보** · 모름은 보류 한 줄(`INFORMATION_UNAVAILABLE` · `missing` · `scope`)로 **남는다** |
| **C** 서로 다른 UNKNOWN 둘 | `test_f03` | **합성** (대상 규칙을 `{MZONE, HAND}`·양쪽으로 넓힌 테스트 전용 정의) | 사유가 **둘**이고 `missing` 이 서로 다르다 — 가려진 후보 / 들여다보지 못한 자리 |
| 직접 `apply` 가 다른 조합의 사유를 빌리지 않는다 | `test_f04` | 🔴 실제 | 거절될 조합을 직접 넣으면 **그 조합 자신의 코드**가 오고, 보류의 모름이 오지 않는다 |
| 사본·원본 일치 · 조회 순수성 | `test_f05` | 🔴 실제 | 후보 · 보류(코드 · `missing` · `scope` · 문장)가 같고, 조회와 거절이 13칸 지문을 바꾸지 않는다 |

> 🔴 이 다섯은 **발동이 가능한** 효과의 혼합이다. *발동 자체가 금지된* 효과의
> 대상 정보 부족은 이 표가 재지 못했고, 그것이 §8.4 의 결함이다.

### 8.2 고친 자리 — 못 센 대상 범위를 적는다

실측 (이 보완 전, `test_f02` 의 판):

```
eligible  = (내 앞면 마법,)        → 조합 1개 · 후보가 된다
undecided = (상대 뒷면 마법·함정,)  → 🔴 보류 0건 — 조용히 사라졌다
```

즉 *"합법인 대상이 하나 있다"* 가 *"대상 공간을 끝까지 검증했다"* 로
읽혔다 — 요구 ②의 *"VALID 대안이 있다고 중요한 UNKNOWN 선택지를 모두
숨기지 않는다"* 가 그 자리다.

고친 것은 **최소 구조 하나**다. `engine/target_bridge.py` 에
`target_enumeration_limits()` 와 `TargetEnumerationLimits` (수 셋만 담는
불변 묶음) 를 더하고, `Duel._note_target_limits` 가 그 범위를 보류로 적는다:

| | |
|---|---|
| `kind` | `ACTIVATE_EFFECT` |
| `code` | `INFORMATION_UNAVAILABLE` (UNKNOWN — "정보가 없다") |
| `missing` | `target-candidate-identity …` 또는 `target-candidate-zone …` — **서로 다른 모름을 다른 이름으로** |
| `scope` | `"대상 후보 2장 중 1장은 정체를 읽을 수 없음"` 처럼 **수로** |
| `reason` | 효과 참조 + *"합법인 조합은 그대로 후보로 남아 있습니다"* |

🔴 **허가 목록은 건드리지 않는다** — 합법 조합은 그대로 후보이고
`apply` 에서 수락된다. 🔴 **같은 규칙에서 나온다** —
`target_combinations` 과 이 함수가 같은 `_candidate_pool` 을 쓰므로 "셀 수
있는 것" 과 "못 센 것" 이 두 벌로 갈리지 않는다. 🔴 **식별자는 없다** —
조건 계층의 사유 문장은 인스턴스를 가리키므로(`#62 는 뒷면이라 정체를
모름`) 옮기지 않고 **수와 자리 이름**만 적는다.

🔴 **`scope` 를 대신 쓰지 않았다.** 보류의 `scope` 가 *패의 장수*를 적는
자리와 이 자리는 **다른 사실**이고, 그래서 각자 자기 범위를 적는다 —
패의 장수를 대상 범위의 근거로 쓰지 않는다 (요구 ②).

> 🔴 **그런데 이것을 묻는 순서가 틀렸다.** 이 보류를 조합 판정보다 **앞에서**
> 모았고, 그래서 발동 자체가 금지된 효과까지 걸렸다 — §8.4 가 그 정정이다.

### 8.3 구조적으로 불가능한 혼합과 그 이유

| 무엇 | 왜 |
|---|---|
| `legal_actions().allowed` 안에 **INVALID 조합이 섞이는 일** | 불가능하다. `target_combinations` 은 `found.eligible` 만 묶고, 조건이 거짓인 후보는 애초에 `eligible` 이 아니다 (`engine/target_bridge.py` 의 `_candidate_pool`). `test_f01` 이 그것을 실행으로 보인다 — 거짓인 대상을 가리킨 조합은 목록에 **없다** |
| `allowed` 안에 **UNKNOWN 조합이 섞이는 일** | 같은 이유로 불가능하다. 그리고 그것이 옳다 — 올리면 `UNKNOWN` 이 허가가 된다. 그래서 고친 방향은 "올린다" 가 아니라 **"못 올린 범위를 적는다"** 였다 (§8.2) |
| **발동 금지**와 **조합별 거절**이 한 코드로 뭉개지는 일 | 불가능하다. 둘은 서로 다른 질문을 서로 다른 자리에 묻는다 (§8.4 의 ①·②). `test_h06` 이 그 둘을 같은 효과에서 비교한다 — 대상 독립 거절과 조합별 관문이 **같은 코드**를 내고, 보류는 한 줄이다 |

### 8.4 🔴 **순서가 틀렸다** — 대상 정보 부족을 발동 금지보다 먼저 모았다

> 이 절은 §8.2 의 **정정**이다. 보완8 의 세 항목 ②는 옳은 사실을 적기
> 시작했지만 **묻는 순서**가 틀렸다.

`_activation_actions()` 는 `target_enumeration_limits()` 를 **조합 판정보다
앞에서** 불렀다. 그래서 *발동 자체가 규칙상 금지된* 효과도 상대의 뒷면 카드가
있으면 대상 미확인이 "진행에 영향을 주는 미지원" 으로 집계되었다.

재현 (실제 등재 카드 싸이크론 · **세트한 턴** · 세트와 기회 통과는 모두
`Duel.apply` 다. 앞면 욕망의 항아리를 묘지로 옮기는 것만 **초기 판 구성**이고,
그 카드의 별도 발동 미지원 사유가 섞이지 않게 하기 위한 것이다):

| | 상대 뒷면 카드 **없음** | 상대 뒷면 카드 **있음** |
|---|---|---|
| 전 | `flow_only` · `fully_supported=True` · `unsupported=[]` | 🔴 `unsupported` · `fully_supported=False` · `target-candidate-identity` 1건 |
| 후 | `flow_only` · `fully_supported=True` · `unsupported=[]` | **같다** |

두 판 모두 그 효과는 세트한 턴이라 **발동할 수 없다.** 상대의 뒷면 카드가
있다는 이유만으로 이번 진행을 미지원으로 분류해서는 안 된다.

그리고 보류 문장이 허가된 조합이 **0개**인데도 언제나 *"합법인 조합은 그대로
후보로 남아 있습니다"* 라고 적었다 — 거짓이었다.

#### 세 가지를 순서대로 가른다

| | 무엇 | 어떻게 답하는가 |
|---|---|---|
| ① | **특정 대상 조합만** INVALID | 조합별 관문이 그 조합만 거절한다. 다른 조합의 VALID · UNKNOWN 은 그대로다 (`test_h05`) |
| ② | **대상과 무관하게** 발동 전체가 INVALID | `Duel._target_free_verdict` 가 먼저 답한다. 그러면 대상 범위 보고를 **멈춘다**. 실제 거절 이유는 `SET_THIS_TURN` 등 기존 코드로 **그대로** 남는다 (`test_h01`) |
| ③ | 발동 가능성은 남았는데 대상 공간을 다 판정하지 못했다 | 대상 범위를 **보고한다** — VALID 조합이 하나도 없어도 그렇다 (`test_h03` · `test_h04`) |

#### `_target_free_verdict` — 같은 관문의 대상 독립 부분

`engine/activation.py` 의 `_check()` 에서 **대상 의존이 아닌 단계 전부**를
`_check_before_targets()` 로 빼고, `can_activate_ignoring_targets()` 가 같은
것을 쓴다. 다른 것은 **마지막 하나(`_check_targets`)를 지나지 않는다**는
것뿐이다.

| 단계 | 대상에 의존하지 않는 근거 |
|---|---|
| 1 `ActionValidator` | `ACTIVATE_EFFECT` 의 요구는 쥔 쪽 · 범위 · 차례 · 페이즈 · 빈 칸이고, `action.targets` 를 읽는 자리는 참조 무결성(`_first_unseen`) 하나다 — 대상이 없으면 통과한다 |
| 2 `ActivationTimingChecker` | `ActivationTiming` 에 대상이 **없다**. 세트 턴 · 스펠 스피드 · 단계가 여기서 나온다 |
| 3 `can_activate_ignoring_targets` | `_check_shape` · `_verdict` · 정의 등록 · `_check_authority` · `_check_condition`. 마지막은 **전부터** `self._condition_context(action, ())` 로 대상을 비운 채 조건을 평가해 왔다 |

🔴 **대상이 없는 행위로 묻는다.** 조합 하나를 골라 묻지 않는다 — 그러면
*"첫 번째 조합의 INVALID 를 효과 전체의 INVALID 로 간주"* 가 되고, 대상이
전부 가려진 판(조합 0개)에서는 물을 것조차 없다.

🔴 **`VALID` 를 돌려주지 않는다.** 부분 판정이므로 `None` 으로만 "막는 것이
없다" 를 말한다 — 허가로 읽힐 수 있는 값을 내보내지 않는다.

🔴 **`UNKNOWN` 은 멈추지 않는다.** 발동 가능성이 남아 있으므로 대상 범위를
계속 보고한다. 모름을 확정 INVALID 로 바꾸지 않는다.

🔴 **그 거절 이유를 잃지 않는다.** 조합이 하나도 만들어지지 않는 판에서는
조합 반복이 아무것도 적지 못하므로, 이 자리가 적는다 — 조합별 관문과 **같은
문장 · 같은 열쇠**(`_note_gate_refusal`)이므로 한 줄로 묶인다. 실측으로 그
덕에 **F2 벌금 · 후보 1장** 자리의 침묵이 드러났다 (아래 §8.5).

#### 쓰지 않은 방법 (금지된 것들)

카드 ID 전용 분기 없음 · 세트 턴 규칙을 후보 생성기에 복제하지 않음 · 거절
문장 파싱 없음 · 첫 조합의 INVALID 를 효과 전체로 간주하지 않음 · 허가 후보
0개로 UNKNOWN 을 지우지 않음 · 보고서에서만 숨기지 않음. 허가 목록과 `apply`
의 규칙 판단은 그대로이고, 새 허가를 만들거나 기존 규칙상 거절을 풀지 않았다.

#### 보류 문장의 조건 (요구 ③)

| 허가된 조합 | 문장 |
|---|---|
| 1개 이상 | *"… 합법인 조합은 그대로 후보로 남아 있습니다."* |
| 0개 | *"… 지금 허가된 조합은 없고, 가려진 쪽을 보지 못했으므로 합법인 조합이 있는지도 말할 수 없습니다."* |

🔴 0개일 때 **"합법인 조합이 없다" 고도 말하지 않는다** — 가려진 쪽을 보지
못했으므로 있는지 없는지를 모른다 (`test_h04`). 그리고 **발동 금지**는 애초에
이 문장에 닿지 않는다 (②에서 멈춘다) — 세 가지가 서로 다른 문장을 갖는다.

### 8.5 🔴 뜻밖의 수확 — 조합이 없어 침묵하던 자리가 드러났다

`_target_free_verdict` 는 조합 수와 무관하게 불리므로, **조합을 하나도 만들
수 없어 관문에게 물을 것조차 없던** 효과의 실제 이유가 처음으로 보고된다.

실측 (`test_i02`, 스물 자리 전수): 고를 수 있는 자리의 보류 줄이 **8 → 9**.
늘어난 줄은 **F2 벌금 · 후보 1장** 이고, 그 자리는 이 감사의 관문 집계에
**들어 있지도 않았다** (`gates={}`) — 벌금은 패 2장을 고르는데 후보가 1장뿐이라
조합이 0개였기 때문이다. 즉 그 효과는 *"후보도 없고 이유도 없다"* 로 조용히
사라지고 있었고, 지금은 실제 이유(`발동 조건이 거짓입니다: 자신 HAND 에 2장
이상`, `CANDIDATE_NOT_ELIGIBLE`)가 적힌다.

🔴 **별도 한계로 기록하는 범위** (요구 §3 의 마지막 줄):

- **정의가 없어 후보 자체를 만들지 못하는 범위.** `activatable_effects` 는
  `EFFECT_LIBRARY` 를 읽으므로, 등록되지 않은 효과 참조는 후보도 보류도
  되지 않는다. `test_b05` 가 그 사실을 그 자리에서 확인한다.
- **옮긴 조작이 없어 후보가 되지 못하는 범위** (`executable=False`).
  `test_i02` 의 실측: 스물 자리 전수에서 관문이 막은 발동 9건 중 보류 줄을
  받는 것이 **8건**이고, 남은 1건(G1 로스트)은 관문이 막은 것이 아니라
  후보 생성 전에 빠진다. 그 자리의 `withheld` 는 **비어 있다.**
- **세트된 카드는 보류 줄조차 받지 못한다.** `_withheld_board_actions` 는
  패만 훑는다. `test_06` (priority_response_audit) 이 `hand`·`set` 양쪽을
  비교해 그 비대칭을 고정한다.
- **비용 있는 효과는 관문을 지나지 않으므로** 거기서 적을 판정이 없다
  (등재된 효과 전부가 비용이 없어 지금은 아무것도 걸리지 않는다 —
  STRUCTURAL-120).

## 9. 사용자의 5장 입력 회귀 결과

입력 패 `69811710,703897,2930675,12989604,93920420` · 레시피
`69811710 x3, 703897 x3, 2930675 x3, 12989604 x3, 93920420 x3, 11091375 x25`.

🔴 **이 레시피는 동작 확인용이다.** 같은 카드 25장을 포함하므로 실제
대회용 합법 덱도 추천 덱도 아니다. 그리고 여기서 검사한 것은 *패가 레시피에
포함되는가* 이고, **금제·동명 카드 매수 제한은 다른 검사**다 — 출력이 그
둘을 "검증 불가 2건" 으로 따로 적는다.

실측 (`test_e01`, 로컬 `/combo` 명령 처리·렌더링 경로):

| 사용자가 확인한 것 | 이번 실측 |
|---|---|
| 실행 5걸음 · 상태 변경 5걸음 | ✔ 그대로 |
| 기르수 효과 1회 해결 | ✔ `효과가 실제로 해결된 걸음 1걸음` |
| 클리막스·열쇠·자각 세트 | ✔ 마법·함정 존 3장 |
| 몬스터 존 기르수 1장 | ✔ |
| 패: 성장 1장 | ✔ |
| 묘지: 덱에서 보낸 성장 1장 | ✔ |
| 남은 덱 34장 | ✔ |
| 마지막에 `end_phase` 만 남고 `activate_card` / `activation-timing` 으로 `unsupported` 종료 | ✔ `stopped_kind="unsupported"` |
| 패가 덱 보유 매수를 넘으면 실행 전 거절 | ✔ `test_e05` — 그 입력에는 정적 계획을 보여 주지 않는다 |

🔴 **달라진 것 하나 — 보고 계약이다** (행동이 아니다). 전개 요약에
`전체 지원 상태` 한 줄이 늘었다 (이 입력에서는 `stopped_kind` 와 같은
방향이다: 둘 다 미지원을 가리킨다). 걸음 수 · 판 · 종료 판정 · 정적 계획은
바뀌지 않았다 — 즉 **엔진 동작은 그대로이고 전달만 늘었다.**

### 9.1 포괄적인 `activate_card` 사유가 무엇인가

🔴 **실제로 생성한 후보의 UNKNOWN 이다** — 후보와 연결되지 않은 범용
안내가 아니다. 근거:

- 그 보류는 `_withheld_board_actions` 가 **그 자리의 패를 전부 묻고**
  (보완8 이 첫 장에서 멈추는 `break` 를 없앴다) 같은 `code`·`missing` 으로
  묶은 것이다.
- 멈춘 자리에서 P0 의 패는 **정확히 한 장**(`93920420`)이고, 그 카드의
  `activate_card` 판정이 UNKNOWN / `activation-timing (Phase 2-C/2-F)` 다.
  `test_e02` 가 그 자리에서 직접 확인한다.
- `scope` 가 범위를 적는다 — 걸음 1~4 에서는 "패 4장 중 4장이 같은 이유"
  처럼, 마지막 자리에서는 한 장이므로 `scope` 가 없다.

🔴 **그런데 어느 카드인지는 적지 않는다.** 문장에 카드 식별자가 없으므로
"특정 카드의 미지원" 으로 **추측해 표시하지 않았다.** 문구만 지워 정상
완료처럼 만들지도 않았다 — 종료 판정은 여전히 `unsupported` 이고, 출력이
*"정상 전개 종료가 아닙니다"* 라고 적는다.

종료 판정과 지원 범위 표현에 주는 영향: 이 사유 때문에 `/combo` 는 5걸음을
**"이 패의 전개를 다 했다"** 로 읽지 못하게 막는다. 그것이 옳다 — 같은
자리에 지원하지 않아 오르지 못한 후보가 있었다.

## 10. 출력의 상충 안내 수정

좁게 넷만 고쳤다. 출력 전체를 재설계하지 않았고 새 전략 기능도 만들지
않았다.

| 전 | 후 |
|---|---|
| 정적 계획이 *"덱 초안을 주지 않아 패 구성을 검사하지 않았다"* + 뒤에 *"위쪽이 이미 검사했다"* 해명 | `recipe:` 로 이미 판정했으면 그 항목을 **빼고** 한 줄로 적는다: *"패가 덱에서 나올 수 있는지는 이 요청에서 이미 검사했습니다 — 위쪽 `[실제 엔진 실행]` 절이 `recipe:` 로 판정했고, 그 결과가 이 응답의 판정입니다."* |
| 걸음 상태 **"확정"** | **"돌려볼 수 있음 (정적 확인)"** |
| 근거 **"엔진이 이 행위를 허가함"** | **"엔진의 행위 계층이 판정할 수 있음 (정적 확인)"** |
| 정적 계획 절의 제목이 실행과 섞여 읽혔다 | **`[아래는 실행하지 않은 정적 계획입니다]`** |

그대로 둔 것: 레시피 없는 입력의 동작 (실행 여부만 분명히 적는다), 지원
범위 내 실행을 전체 듀얼 합법성이나 최선 전개로 적지 않는 기존 경고.

### 10.1 🔴 정적 계획에 **남아 있던** 실행 허가 표현 (남은 세 항목 ③)

위 넷은 `StepStatus` · `StepBasis` 의 **표시**만 고쳤고, 걸음의 `note` ·
`expected` 는 그대로였다. 실측으로 `combo_messages` 출력에 다음이 남아
있었다:

```
비고: 엔진이 일반 소환을 허가합니다 — 특수 소환과 달리 조건 판정 계층이 있습니다
기대: 앞면 공격 표시로 몬스터 존에 놓입니다
기대: 엔진에 등록된 구현대로 상태가 바뀝니다
비고: 엔진에 실행 구현이 등록된 카드입니다 — 돌려볼 수 있습니다
```

정적 계획은 **엔진을 돌리지 않으므로** 어떤 판에서도 허가를 받지 않았고,
결과도 보장할 수 없다. 고친 뒤:

| 칸 | 전 | 후 |
|---|---|---|
| 일반 소환 `note` | "엔진이 일반 소환을 **허가합니다**" | "일반 소환은 **판정 계층이 있는 종류**입니다 (특수 소환과 달리) — **이 판의 허가가 아닙니다**" |
| 일반 소환 `expected` | "앞면 공격 표시로 … 놓입니다" | "**성공하면** 앞면 공격 표시로 … 놓입니다" |
| 효과 `expected` | "엔진에 등록된 구현대로 상태가 바뀝니다" | "**발동이 성공하면** 엔진에 등록된 구현대로 …" |
| 효과 `note` | "… 돌려볼 수 있습니다" | "… **돌려볼 수 있다**는 뜻이고 **이 판의 적법성이 아닙니다**" |
| `StepBasis.ENGINE_ACTION` docstring | "엔진이 이 행위 자체를 **허가**한다" | "엔진에 **이 행위 종류의 판정 계층이 있다**" + 이 판의 허가는 `ExecutedStep.accepted` 만 말할 수 있다 |

🔴 **실행 기록 쪽은 그대로다** — 수락 · 해결 · 적용된 효과 기록의 표현을
건드리지 않았다. 그리고 `test_e03` 은 **문구 하나의 부재**가 아니라 두 절의
뜻이 갈리는지를 센다: 실행 절에만 `수락 예` · `적용된 효과 기록:` ·
`를 해결했습니다` 가 있고 정적 계획 절에는 **없다.**

🔴 출력을 재설계하지 않았고 새 전략 기능도 만들지 않았다.

🔴 **Discord 전송은 하지 않았다.** 검증은 로컬 명령 처리·렌더링 경로
(`app.discord_bot.combo_messages`)로 했다.

## 12. 테스트 실측과 실패 분류

| 1 | **후보 생성 전에 빠지는 범위.** 옮긴 조작이 없거나(`executable=False`) 정의가 등록되지 않은 효과는 후보도 보류도 되지 않는다 (`test_b05` · `test_i02` 의 G1) | 관문에 닿지 않으므로 "관문의 말을 옮긴다" 로 고칠 수 없다. 새 실행 구현 · 새 카드 지원은 범위 밖. 🔴 **좁아졌다**: 마무리2 가 *조합을 만들 수 없어 침묵하던* 자리는 드러냈다 (§8.5). 남은 것은 `executable=False` 와 정의 미등록 둘이다 |
| 2 | **세트된 카드는 `activate_card` 보류 줄을 받지 못한다** — `_withheld_board_actions` 는 패만 훑는다 | 판 위 카드의 발동 타이밍 판정 자체가 없다 (`on-field-activation-timing`) |
| 3 | **비용 있는 효과는 관문을 지나지 않는다** (STRUCTURAL-120) | 등재된 효과 전부가 비용이 없어 지금은 아무것도 걸리지 않는다 |
| 4 | **`DuelStep` 에 `missing` 칸이 없다.** 빠진 규칙의 이름을 `reason` 문자열에 싣는다 | 칸을 더하면 공유 계약이 넓어진다. 문자열 규약은 보류 쪽(`line_ko`)과 같다 |
| 5 | **효과 식별이 `reason` 문자열에만 있다** | 식별자 칸을 더하면 `HIDDEN_CARD` 자리에서 가려진 카드의 정체가 새어 나간다 (3-E-41). 판정에 필요한 구분은 `code`·`scope`·`missing` 으로 구조적으로 제공한다 |
| 6 | **페이즈 · 스텝의 끝에서 우선권이 넘어가는 자리가 없다** (`test_i01`) | 우선권 모델 확장이고 6-S 이래 범위 밖 |
| 7 | **금제 · 동명 카드 매수 상한 데이터가 없다** | `/combo` 가 "검증 불가 2건" 으로 따로 적는다. 카드 · 금제 데이터 갱신은 범위 밖 |
| 8 | 🔴 **못 센 대상 범위는 "몇 장" 까지만 말한다.** 어느 조합이 미확인인지는 적지 않는다 | 그것을 적으려면 인스턴스를 가리켜야 하고, 그러면 가려진 카드의 정체가 새는 길이 열린다 (3-E-41). 수와 자리 이름이 *"어느 범위의 제한인가"* 에 답하는 최소값이다 |
| 9 | 🔴 **`/combo` 응답이 Discord 메시지 상한에 이미 닿아 있다.** 레시피를 준 전개에서 정적 계획 절의 뒤쪽이 잘린다 (실측: 줄 154 · 9,298자 / 상한 4×2,000자) | 이번 변경 **전에도** 그랬다 (153줄 · 9,071자). 메시지 배분을 늘리는 것은 출력 재설계이고 범위 밖이어서, 더하는 줄을 **수와 연결**로 압축해 잘리는 지점을 되돌렸다 |
| 10 | 🔴 **대상 독립 판정이 "확정 거절" 일 때만 대상 범위를 멈춘다.** 발동 자체가 `UNKNOWN` 이면 (예: 패의 함정 — `trap-activation-location`) 대상 범위도 함께 보고된다 | 그것이 옳다 — 발동 가능성이 남아 있으므로 모름을 확정 거부로 바꾸지 않는다. 다만 읽는 쪽에 **모름이 둘** 보인다 (발동 쪽 · 대상 쪽). 그 둘을 한 줄로 합치려면 "어느 모름이 먼저 풀려야 하는가" 를 모델링해야 하고, 그것은 이번 범위가 아니다 |
| 11 | 🔴 **등재된 효과 가운데 대상 독립 INVALID 와 가려진 대상을 **함께** 만들 수 있는 것은 `SET_THIS_TURN` 계열뿐이다.** 다른 코드(예: `SPELL_SPEED_TOO_LOW`)는 양쪽 필드를 보는 대상 규칙을 가진 등재 효과가 없어 같은 판을 만들 수 없다 | 새 카드 지원 확대가 범위 밖이다. 대신 **다른 단계**(발동 조건)의 대상 독립 INVALID 를 `test_h06` 이 실제 카드로 검증한다 — 이 수정이 한 코드에 묶인 것이 아님을 그 자리가 보인다 |
| 12 | 기존 실패 8건 (§12.2) | 이번 변경과 무관하다. 한국어 오버레이 · cid 매핑 · 공식 자료 대조 |
