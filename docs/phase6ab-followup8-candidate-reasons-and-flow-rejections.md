## 3. 기존 결함과 재현 절차

### 3.1 결함 ① — 자동 PASS 가 중간 기회의 사유를 버린다

`agent/simulation.py` 의 `_settle_forced_passes()` 는 PASS 만 남은 응답
기회를 자동으로 지나간다. 그런데 `simulate()` 는 **그 반복이 끝난 뒤**의
`legal.unsupported()` 만 모았다.

재현 (실행 경로를 전부 지난다 — 결과 객체를 주입하지 않는다):

```
① 기존 staged 도구로 P0 에게 세트 가능한 몬스터를 둔다
② P1 의 마법·함정 존에 뒷면 욕망의 선물(5915629)을 둔다
③ 테스트 전용 정의에서 그 효과의 activation_waits_for_event=True 로 바꾼다
   🔴 카드 수정 제안이 아니다 — 기존 미지원 사건 관문을 밟기 위한 합성 조건
④ duel_components(definitions=…) 로 그 정의를 넘긴다
⑤ P0 의 SET_MONSTER 를 Simulator().simulate(...) 로 실행한다
```

실측한 흐름과 결과:

```
[1] P0 빠른 효과 기회 → activate_card [activation-timing (Phase 2-C/2-F)]
[2] P1 빠른 효과 기회 → 🔴 activate_effect [trap-activation-event]
최종 (판이 다시 열림)  → activate_card [activation-timing (Phase 2-C/2-F)]

전: SimulationResult.unsupported = (activate_card … ,)      ← [2] 가 없다
후: SimulationResult.unsupported = (…activate_card…,
                                     🔴 …trap-activation-event…,
                                     …activate_card…)
```

🔴 **그 재현에서 `fully_supported` 는 전후 모두 거짓이다** — 다른 사유
하나가 이미 있었다. 그래서 *"`fully_supported=True` 로 잘못 성공했다"* 가
아니고, 확인된 결함은 **"진행 도중의 구체적인 중요 사유가 결과에서
유실된다"** 다. `test_a02` 가 그 구분을 함께 센다
(`assert result.fully_supported is False`).

`deck/opening.py` 의 `_settle_chain()` 도 같은 모양이었다 — 조용히 패스만
하고, 부르는 쪽은 반복이 끝난 뒤의 자리만 읽었다.

### 3.2 결함 ② — `apply` 경계가 "무엇이 빠졌는가" 를 잃는다

`DuelStep` 에는 `missing` 칸이 없다. 그래서 판정 계층이 `missing_rule` 로
들고 있던 사실이 `apply` 결과에서 사라졌다. 실측:

```
ActionValidator.validate(special_summon)
→ UNKNOWN / RULE_NOT_IMPLEMENTED
  missing_rule = "special-summon-condition (카드마다 다르다)"

DuelStep (전) "아직 구현하지 않은 규칙이 걸려 있습니다."
DuelStep (후) "아직 구현하지 않은 규칙이 걸려 있습니다.
               [special-summon-condition (카드마다 다르다)]"
```

고친 자리는 `Duel._refusal_sentence` 하나다. **확정 거부에는 아무것도
붙지 않으므로** ("규칙이 막았다" 는 `missing is None`) 두 사실의 구분은
그대로다. 보류 목록은 `WithheldAction.line_ko` 로 같은 규약을 이미 쓰고
있었고, 그것을 `apply` 결과에도 쓴 것이다.

### 3.3 결함 ③ — 출력이 서로 다른 말을 한다

같은 응답 안에서:

- 위쪽 `[실제 엔진 실행]` 절이 `recipe:` 로 패 구성을 **검사했다**
- 아래쪽 정적 계획이 *"덱 초안을 주지 않아 그 검사를 하지 않았다"* 고 적고
- 다시 *"위쪽이 이미 검사했다"* 는 해명이 붙고
- 실행하지 않은 정적 계획의 걸음이 **"확정"** · **"엔진이 이 행위를 허가함"**

## 5. 중간 사유 수집 · 중복 처리 · 관련성 판단 · 비공개 정보 보호

### 5.1 수집

```python
# agent/simulation.py
def _settle_forced_passes(self, fork) -> "tuple[int, tuple[tuple[int, WithheldAction], ...]]":
    #  각 기회에서 legal.unsupported() 를 (자리, 보류) 로 모은 뒤 PASS 한다
```

`simulate()` 가 그 중간 목록과 최종 자리의 목록을 **순서대로** 이어 붙인다.
`deck/opening.py` 는 같은 일을 `note` 콜백으로 한다 — `_settle_chain(duel,
note=None)` 이 반복마다 `note(legal, seat)` 를 부르고, `execute_opening` 이
`note_unsupported` 를 넘긴다.

### 5.2 중복

🔴 **완성된 한 줄을 열쇠로 묶는다.** 그 줄에 종류 · 규칙 이름 · (자기
자리면) 효과 이름이 들어 있으므로, **다른 효과의 사유가 합쳐지지 않는다.**

`WithheldAction.scope` 는 그 열쇠에서 **빠진다**. 그것이 이 작업에서 내가
만든 버그였다: 훑은 패의 장수를 `reason` 안에 넣었더니 문장이 걸음마다
달라져 `/combo` 의 미지원이 1줄 → 5줄(내용이 같은 다섯 줄)이 되었다.
그래서 `scope` 를 별도 칸으로 떼고 `line_ko(with_scope=False)` 를 누적
열쇠로 쓴다.

### 5.3 관련성

`Duel._refusal` 의 우선순위 — **행위 단위가 종류 단위보다 먼저다.**

| | 누가 | 무엇에 대해 |
|---|---|---|
| 1 | `_refusal_verdict` (발동 관문) | 그 **행위 하나** (발동에만 있다) |
| 2 | `_rule_verdict` (`ActionValidator`) | 그 행위 하나의 규칙 쪽 판정. 흐름 둘(`PASS`·`END_PHASE`)에는 묻지 않는다 |
| 3 | `_withheld_for` (보류 목록의 같은 종류) | 흐름 계층이 **종류 단위**로 낸 판정 |
| 4 | 예전 문장 | 남은 자리를 숨기지 않는다 |

같은 행위에 두 이유가 겹칠 때 (예: 빠른 효과 기회에 **가려진 카드**를
가리킨 소환) 더 좁은 쪽이 실제 이유다. 종류 단위의 단계 설명을 앞세우면
*"부수적으로 발견한 문제를 실제 제외 이유처럼"* 적는 일이 된다.

`_withheld_for` 가 **종류만 같은 다른 효과의 거절**을 가져오지 않는지는
`test_c02` 가 따로 센다 — 같은 종류에 줄이 여럿일 때 확정 거부를 먼저
고르고, 그 종류의 줄이 없으면 `None` 이다 (지어내지 않는다).

### 5.4 비공개 정보 보호

🔴 **여기에 긴장이 있었다.** 요구 §3 은 *"소비자가 효과를 구별하려고
문자열을 파싱해야 한다면 최소한의 구조적 연결을 검토하라"* 고 하고, 3-E-41
의 불변식(`test_26`)은 `WithheldAction` 에 `source`·`action`·`instance_id`
를 **금지**한다 — 후보별 식별자를 담으면 `HIDDEN_CARD` 처럼 **가려진 것을
가리키는 판정**에서 정체가 함께 새기 때문이다.

해결:

- 효과 참조는 **`reason` 문자열**에만 둔다 (이 저장소의 기존 규약이다).
- 데이터클래스에 더한 것은 `code` (**규칙의 이름**)와 `scope` (**개수**)
  뿐이다 — 둘 다 어느 카드인지 말하지 않는다. 소비자는 효과를 구별할
  필요 없이 `code` 로 "규칙 거절인가 모름인가" 를 읽는다.
- **자리를 넘어갈 때는 문장을 가린다.** `agent/simulation.py` 의
  `_encountered_line()` 과 `deck/opening.py` 의
  `unsupported_reasons_elsewhere()` 가 같은 일을 한다:

```
자기 자리   activate_effect [trap-activation-event]: 5915629:e[0] 를 지금 …
다른 자리   activate_effect [trap-activation-event]: P1 의 기회에서 만났고
                                어느 카드인지는 이 자리의 관측 밖입니다.
```

`test_a03` 이 그 경계를 양방향으로 센다: 카드 번호도 `EffectRef` 도 없고,
**그런데 사실은 남아 있고** ("누구의 기회였고 무엇이 없어서인지"), 지웠다는
것도 적는다 — "사유가 없다" 로 읽히지 않게. 그리고 같은 판에서 `viewer=P1`
로 보면 **자기 자리의 사유는 문장째로** 온다 (경계가 과하게 지우지 않는다).

## 6. 후보 제외 / 직접 `apply` / Simulator / `/combo` 사이의 계약

| 사실 | 후보 목록 | 직접 `apply` | Simulator | `/combo` |
|---|---|---|---|---|
| 지원 범위에서 진행 완료 | `allowed` 에 흐름만 남고 `unsupported()` 가 비었다 | `accepted=True` · `OK` | `SUPPORTED` + `fully_supported=True` | `stopped_kind="flow_only"` |
| 규칙상 불가능한 후보 | `withheld` · `code` 가 INVALID · `missing is None` | `accepted=False` · 그 코드 | `unsupported` 에 **들어가지 않는다** | 미지원 목록에 **없다** |
| 선택 정책이 고르지 않음 | `allowed` 에 있다 | — | 정책의 선택 기록 | `stopped_kind="not_chosen"` · 고른 방식을 `first_meaningful` 이라고 적는다 |
| 중요 미지원 때문에 검증 불가 | `withheld` · UNKNOWN · `missing` 에 규칙 이름 | `accepted=False` · 같은 코드 + `[빠진 규칙]` | `fully_supported=False` · `unsupported` 에 줄 | `stopped_kind="unsupported"` + 미지원 목록 |
| 실행 또는 해결 실패 | — | `accepted` 는 참일 수 있고 `code` 가 불발 사유 | 결과·기록이 말한다 | 걸음마다 `결과` 칸 |

핵심은 **같은 판정 하나를 네 자리가 읽는다**는 것이다. 보완8 이 새 규칙을
구현하지 않은 이유가 여기 있다 — 흐름 계층의 정확한 말은 이미
`legal.withheld` 에 있었고, `apply` 가 그것을 읽지 않았을 뿐이다.

`INVALID` 가 미지원으로 집계되지 않는다는 것은 `LegalActions.unsupported()`
가 `missing` 이 붙은 보류만 돌려주는 것으로 **구조적으로** 지켜진다. 그리고
`WithheldAction.__post_init__` 이 INVALID 코드에 `missing` 을 붙이면 예외를
던지므로, 그 규율을 어기는 자리는 만들 수 없다.

### 9.1 포괄적인 `activate_card` 사유가 무엇인가

🔴 **실제로 생성한 후보의 UNKNOWN 이다** — 후보와 연결되지 않은 범용
안내가 아니다. 근거:

- 그 보류는 `_withheld_board_actions` 가 **그 자리의 패를 전부 묻고**
  (보완8 이 첫 장에서 멈추는 `break` 를 없앴다) 같은 `code`·`missing` 으로
  묶은 것이다.
- 멈춘 자리에서 P0 의 패는 **정확히 한 장**(`93920420`)이고, 그 카드의
  `activate_card` 판정이 UNKNOWN / `activation-timing (Phase 2-C/2-F)` 다.
  `test_e02` 가 그 자리에서 직접 확인한다.
- `scope` 가 범위를 적는다 — 걸음 1~4 에서는 "패 4장 중 4장이 같은 이유"
  처럼, 마지막 자리에서는 한 장이므로 `scope` 가 없다.

🔴 **그런데 어느 카드인지는 적지 않는다.** 문장에 카드 식별자가 없으므로
"특정 카드의 미지원" 으로 **추측해 표시하지 않았다.** 문구만 지워 정상
완료처럼 만들지도 않았다 — 종료 판정은 여전히 `unsupported` 이고, 출력이
*"정상 전개 종료가 아닙니다"* 라고 적는다.

종료 판정과 지원 범위 표현에 주는 영향: 이 사유 때문에 `/combo` 는 5걸음을
**"이 패의 전개를 다 했다"** 로 읽지 못하게 막는다. 그것이 옳다 — 같은
자리에 지원하지 않아 오르지 못한 후보가 있었다.

### 13.2 남은 한계 (숨기지 않는다)

| | 무엇 | 왜 이번 범위가 아닌가 |
|---|---|---|
| 1 | **후보 생성 전에 빠지는 범위.** 옮긴 조작이 없거나(`executable=False`) 정의가 등록되지 않은 효과는 후보도 보류도 되지 않는다 (`test_b05` · `test_i02` 의 G1) | 관문에 닿지 않으므로 "관문의 말을 옮긴다" 로 고칠 수 없다. 새 실행 구현 · 새 카드 지원은 범위 밖 |
| 2 | **세트된 카드는 `activate_card` 보류 줄을 받지 못한다** — `_withheld_board_actions` 는 패만 훑는다 (`test_06` 가 `hand`/`set` 양쪽으로 고정) | 판 위 카드의 발동 타이밍 판정 자체가 없다 (`on-field-activation-timing`) |
| 3 | **비용 있는 효과는 관문을 지나지 않는다** (STRUCTURAL-120) | 등재된 효과 전부가 비용이 없어 지금은 아무것도 걸리지 않는다 |
| 4 | **`DuelStep` 에 `missing` 칸이 없다.** 빠진 규칙의 이름을 `reason` 문자열에 싣는다 (`_refusal_sentence`) | 칸을 더하면 공유 계약이 넓어진다. 문자열 규약은 보류 쪽(`line_ko`)과 같다 |
| 5 | **효과 식별이 `reason` 문자열에만 있다.** 소비자가 효과를 구별하려면 문자열을 봐야 한다 | 식별자 칸을 더하면 `HIDDEN_CARD` 자리에서 가려진 카드의 정체가 새어 나간다 (3-E-41). `code`(규칙 이름)와 `scope`(개수)로 **판정에 필요한 구분**은 구조적으로 제공한다 |
| 6 | **페이즈 · 스텝의 끝에서 우선권이 넘어가는 자리가 없다** (`test_i01`) | 우선권 모델 확장이고 6-S 이래 범위 밖 |
| 7 | **금제 · 동명 카드 매수 상한 데이터가 없다** | `/combo` 가 "검증 불가 2건" 으로 따로 적는다. 카드 · 금제 데이터 갱신은 범위 밖 |
| 8 | 기존 실패 8건 (§12.2) | 이번 변경과 무관하다. 한국어 오버레이 · cid 매핑 · 공식 자료 대조 |
